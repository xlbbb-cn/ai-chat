# Modules — tools, turn guards and project layout

> Part of the Rabbit Chat Studio developer docs. Read this when you are looking for the files of a feature or the turn/tool policies.
> The index for all of them is [`AGENTS.md`](../../AGENTS.md) — it also holds
> the rules that apply to every change, whatever file you ended up in.

## Skills — path isolation rule

> Except for explicitly requested paths, any operation executed by a skill MUST treat the directory containing the skill's `SKILL.md` as its root. Operating outside this root is forbidden; all in-skill paths are evaluated relative to it.

This is enforced by the skills/tools layer. Don't add code that lets a skill escape its `SKILL.md` directory.

## Tools & dangerous commands

- Tools: `run_cmd`, `run_shell`, `file_actions`, plus the `memory`, `todos`, `timer` and `calculator` tools — all in `src-tauri/src/tools/` (`skill_read` is auto-injected when skills are active). `calculator` is a self-contained expression evaluator (`tools/calculator.rs`): recursive-descent parser over an `Int(i64)`/`Float(f64)` value, no crate and no IO, so it needs no confirmation and runs in a parallel segment. It is the one tool with a **dependency** (`TOOL_DEPENDENCIES` in `lib.rs`): selecting it silently selects `run_cmd` — its tool description (`tools/schema.rs`) mandates that every computation-related result comes from a tool and falls back to `run_cmd` for what the expression grammar cannot express — so the pair is enforced together on every config write / load / read (`enforce_tool_dependencies`), patched into `effective_tools()`, mirrored for sub-agent `allowed_tools` in `agents/helper.rs`, and the Tools panel enables + locks `run_cmd` while the calculator is on (`TOOL_DEPENDENCIES` mirror in `ToolsPanel.tsx`). The former `knowledge_graph` tool is retired for now: its client is the standalone `knowledge-graph` crate at `src-tauri/src/utils/knowledge_graph/` (a workspace member with its own `Cargo.toml`; module-owned `Settings`, no `AppConfig` fields). The app crate does **not** depend on it, so `neo4rs` is not linked into the binary. It is neither advertised nor dispatchable until it is wired back: add `knowledge-graph = { path = "src/utils/knowledge_graph" }` to `src-tauri/Cargo.toml` plus a tool definition and a dispatch arm in `tools/mod.rs`.
- `mcp_self` belongs to the same family but is the only tool that writes **app-data** state (the MCP registry) instead of workspace state. It is advertised only while `config.self_evolution_mode` is on (injected by `tools::get_all_tools`, never part of `selected_tools`), and its dispatch arm in `tools/mod.rs` re-checks the flag, so a hand-crafted call is refused even when the tool was not advertised. Sub-agents strip it (`agents::drop_mcp_self`).
- **`run_shell` run types**: `direct` (default) waits for the script to exit and returns its output; `serve` starts a long-lived background child (HTTP server, watcher…) and returns a `serve_id` immediately. The same tool manages them: `action: "list"` shows running/finished entries with recent output, and `action: "stop"` with `serve_id` (or `"all"`) kills the whole tree. Serve state lives in `tools/serve.rs`; stopping a serve process never asks for confirmation because it only targets children this app started. **Serve processes live only for the chat turn that spawned them**: turn-end cleanup calls `ServeRegistry::shutdown_session` for the turn's own session (final answer, error or Stop), which removes that session's entries, kills each tree, polls until the pids are confirmed gone — escalating with a second whole-tree kill once — and logs the verified summary (`exit NOT confirmed` on the pathological leftover). `shutdown_all` remains the app-level teardown (app exit); another conversation's servers are never a target.
- **Child-process cleanup** (`src-tauri/src/process_guard.rs`): every long-lived child (stdio MCP server — the main pool or an `llm` agent task — `serve` process, `cli` sub-agent) is registered by pid. `RunEvent::Exit` and the main-window `CloseRequested` hook call `kill_all()`, which terminates each process tree. On Windows children are also assigned to a job object with `JOB_OBJECT_LIMIT_KILL_ON_JOB_CLOSE`, so even a hard crash cannot leave MCP servers / CLI agents / serve processes running. On Unix children opt into their own process group (`process_group(0)`) so `kill(-pid)` reaches grandchildren.
- **Path meaning is decided in Rust, spelling-insensitively** (`tools/paths.rs`). `resolve_safe_path` accepts an absolute path inside the workspace **even when the target does not exist yet**: the deepest existing ancestor is canonicalized and the rest re-appended, so `E:\ws\new.txt`, `E:/ws/new.txt`, a differently-cased directory and a symlinked root all land on the same file (before this, the raw spelling was compared against the canonical `\\?\`-prefixed root, so an absolute path to a *new* file was rejected while the same file written relatively resolved). `resolve_input_path` wraps it with the model-facing normalization (`\` → `/`, a leading `/` = workspace root on Windows, `./`, a `\\?\` prefix, surrounding whitespace) and also returns the workspace-relative form callers store and echo. Callers never re-derive containment: `file_actions` reports the real cause instead of a blanket "outside the workspace root", and `mcp_self` derives its folder/roster strings from `workspace::DATA_DIR` and repairs legacy absolute or `\`-separated `definition_path` values (`tools/mcp_self.rs::existing_rel_dir`, `mcp::normalize_self_built_paths`) instead of forking a second folder or leaking the old one.
- **Path policy** — the three execution tools have deliberately different scopes:
  - **`file_actions`** is strictly workspace-scoped — any path that resolves outside the workspace root is rejected outright, with no confirmation override. The workspace **includes the hidden `.data` state folder** (skills, scripts, memory, todos, skill status): it is listed, searched, read and written like any other folder. The single exception is the SQLite database (`.data/chat.db` and its `-wal`/`-shm`/`-journal` sidecars) — `file_actions` can only truncate or delete it, never rewrite it, so it would destroy the chat history, the API monitor, the interaction log and the agent missions; `tools/paths.rs::is_workspace_database` rejects it.
  - **`run_cmd`** runs a *program* or a *library script*, not an arbitrary file. The first word is resolved against `<workspace>/.data/scripts` by bare name (extension optional, so `build-frontend` finds `build-frontend.ps1`), and the library directory is prepended to the child's `PATH`, so a script wins over a PATH program with the same name. Otherwise it must be a bare name the OS resolves through `PATH` (`python`, `python3`, `git`, …). Absolute and relative paths are refused (`tools/process.rs::validate_path_resolved_program`, enforced both in the tool handler and in `build_command`). Use `run_shell` when a path is really needed. Shell interpreters are refused too (`tools/process.rs::reject_shell_interpreter`: `bash` / `sh` / `csh` / `zsh` / `cmd` / `powershell` / `wsl` / `busybox` / …): `run_cmd "bash script.sh"` would hand free-form code to an interpreter and bypass the script audit, so the handler only allows a shell when the name resolves to a *library* script (whose content is scanned and approved) — any other caller is pointed at `run_shell`. It starts in the caller's working directory (`current_dir` + `PWD`) — the workspace root for the main chat, the task's `cwd` inside a sub-agent mission. `action: "list"` returns the library (interpreter, `@description`, `@usage`, use count, safety status) without executing anything. The script body is scanned by `tools/risk.rs::scan_script_body`; a hit asks for confirmation once and the approved content hash is stored in `.data/scripts/.index.json`, so an edit re-prompts. Script metadata comes only from header comments (`#`, `//`, `REM`, `::`) — no sidecar or manifest.
  - **`run_shell`** has full freedom: it starts in the caller's working directory (workspace root or the task's `cwd`) but its working directory is **not** restricted — scripts may `cd` anywhere and run anything. Every script is audited by `tools/risk.rs` (risk score, syntax gate, confirmation for L0–L4) before it runs.
- **Cross-conversation file race protection** (`tools/file_locks.rs`): `file_actions`' mutating actions (write / patch / delete / move) take per-path async write locks first — sorted path order, so opposite-direction moves cannot deadlock — and run the backup + write + record sequence entirely inside the guards, so two sessions editing the same file are serialised and a `.bak` copy never snapshots a half-applied state. On top of the locks, a **stale-write rejection**: the registry remembers per path who wrote it last and when, plus each session's last read stamp — a session writing a file that ANOTHER conversation modified after this session's last read is refused with an explicit "STALE WRITE — re-read and retry" error instead of silently clobbering the other conversation's change. A session's own writes never count as stale; a fresh read clears the verdict; delete/move forget the path's history so a recreated file starts clean; anonymous (panel) callers are never blocked; a failed action (`tool_output_is_error`) publishes no "last write". Known boundary: `run_shell` / `run_cmd` bypass the registry by design, and `patch`'s own context matching remains the second line of defence.
- **Search cost is per file, not per byte** (`tools/search.rs`). On Windows one `stat`+`open`+`read` costs 40–57 µs regardless of file size, so what decides a search is how many files the walk touches: over this workspace (127k files, 167 GB) a default search descended into `target/`, spent its whole 20 000-file budget in 3.0 s and returned build artifacts, while the 764 project files hold 27 MB. Hence `respect_gitignore` defaults to **true**, plus a `!.data` override (this repo's `.gitignore` lists `.data/`, and an override outranks every ignore rule, so the state directory stays searchable), and `NOISE_DIR_NAMES` prunes `node_modules/target/dist/build/.git/…` *below* the search root — never the root itself, so `path: ./target/debug` still searches exactly what was asked for. The footer names why a scan stopped (`ExhaustReason::MatchBudget` vs `FileBudget`) and which directories were pruned, and a `glob`-rejected file is never opened and is charged to neither budget. A throwaway harness in `.data/tmp/bench-search` measures the engine (default search here: 4.0 s before, ≈40 ms after). The literal matcher then scans the whole buffer with `memchr`/`memmem` — `memchr2` on both cases of the first byte for case-insensitive ASCII — and derives line numbers from newline offsets, falling back to the line-oriented Unicode path only for a non-ASCII needle, an empty needle or one containing a newline; regexes now match bytes, so a file no longer has to be valid UTF-8. An absent needle costs 520 ms → 238 ms on the 17k-file tree and 392 ms → 86 ms on a 230 MB corpus.
- **Sub-agents are typed** (`agent_type` in `sub_agents.json`): `llm` runs the built-in autonomous loop, `cli` launches a headless coding CLI installed on this machine (`agents/cli.rs`: PATH + `PATHEXT` resolution, Windows `.cmd`/`.bat`/`.ps1` wrapping, output streaming on `agent-task-token`, process-tree kill on timeout/Stop; `default_timeout_seconds`, 0 = no timeout), `cloud` posts the task to a remote HTTP endpoint with optional job polling (`agents/cloud.rs`; `timeout_seconds`, 0 = no timeout; `request_timeout_seconds` per-request cap, 0 = the built-in 600 s — apiyi's gpt-image-2 docs: high quality / 4K takes 3–5 min and a 120–300 s client timeout misfires). The backend is generation-API aware. **Input side**: the delegating call (`call_subagent` args / planner task fields) may carry `images` (workspace-relative input files, ≤16, 20 MB each, sandbox-checked by `load_image_inputs`) and `params` (template variables, keys `[A-Za-z0-9_-]`, reserved placeholders protected by `sanitize_task_params`); the body template's `{image_b64}` / `{image_data_url}` / `{images_data_urls}` (a full JSON array value) inject them, so image-to-image and image-to-video work over JSON endpoints — a placeholder with no images fails the run loudly, images with no placeholder only note it. `cli` agents instead see the input paths listed in their prompt. **Result side**: when the extracted result (`result_path`) is a base64 payload (`b64_json`, bare or `data:`-prefixed — the sniff covers png/jpg/gif/webp/bmp/mp4/webm/mp3/wav/…), a media URL (saved when the `Content-Type` is image/video/audio, never an HTML error page), or a JSON wrapper containing one, the file is written into the task's deliverable directory (256 MB cap, collision-free names, URL stem when available) and the mission report carries only the workspace-relative paths plus a short summary — a multi-megabyte payload never reaches the model context; a non-media result over 200k chars is truncated with a hint instead. `call_subagent` creates a deliverable directory for `cloud` tasks too (`turn.rs`), and `format_subagent_delivery` lists the saved files for the main agent. **Polling**: `poll_first_delay_seconds` waits before the first query (video APIs spend their first ~20–30 s queueing) and `poll_method` selects `get` (default) or `post`. An `llm` agent's definition is the markdown file under `agents/` (see above); with `enable_mcp` on it also receives every enabled MCP server's tools, each task owning its own MCP processes (see the definitions section). The panel lists all three by name/description, grouped by category: panel-created agents (`custom/` definitions plus the file-less `cli` / `cloud` agents) come first, library folders follow, and top-level markdown files that belong to no category come last. All three are reachable from the main agent through `call_subagent` **only while the `use_agents` (子智能体系统) switch is on** — with it off the tool is neither advertised nor callable, and the main agent answers directly. The `auto_plan` (自动规划) switch is independent: off means no per-turn mission, while `call_subagent` still delegates on the model's own initiative. `cli`/`cloud` agents ask for approval once per app session unless their `require_approval` switch is off (kind `external_agent`). A `cli` agent's `model_args` are appended on every run — the model id is written there directly (`-m` and `opencode-go/…` on separate lines), nothing is inherited from the main config. Every run starts a fresh CLI session; no session state is carried across calls. Only a CLI process that exits 0 is a success: a non-zero exit or a timeout closes the mission as `failed` and emits `agent-task-error` instead of a green "done" badge.
- Some command patterns raise a frontend confirmation dialog. The Rust side blocks on `confirm_command` until the user replies. **If a tool call appears to hang, check the React tree for a pending `ConfirmDialog` / dangerous-command prompt before debugging the Rust side.**
- `ConfirmKind` values: `dangerous` (L0), `system_config` (L1), `user_software` (L2), `user_data` (L3), `external_agent` — the L0-L3 kinds mirror `RiskLevel::confirm_kind()` in `tools/risk.rs` (L4-L6 never prompt). Users can auto-accept kinds via `auto_accept_confirm_kinds` in config; the Tools panel only offers kinds the backend can actually emit (`external_agent` is approved per agent in the Sub Agents panel instead), plus a one-click master switch that stores the `"*"` wildcard (matches every kind, including future ones).
- **Todos Q&A (`todos` action `ask`)**: the model hands over 1–8 questions (`{ title, description?, options?, allow_custom? }`, capped/trimmed by `normalize_ask_questions`), the tool emits `todo-ask` and **blocks the tool loop** on the user's answers — the confirm-dialog mechanics (`AppState.todo_ask` payload + one-shot sender, `todo_ask_lock` serializing one open form, `todo_ask_reply` addressing the slot by `request_id`, 100 ms cancel-flag poll, 900 s timeout, `get_pending_todo_ask` restoring the panel after a webview reload). The frontend panel (`components/TodoAskPanel.tsx`, documented in docs/DESIGN.md) is a tab + card form hosted **inside the assistant bubble that owns the ask tool call** — App matches the payload's `call_id` against the message's `tool_calls` (the `Asking the user …` progress row exists before the event) and passes the panel to that `ChatMessage` as the `todoAskPanel` prop, rendered as the bubble's last block (after `message-content`, before the injection notes): the reply keeps streaming above it, so the card stays pinned on the line right after the assistant's output, and as a stable React child at a stable tree position the answers typed so far survive every streamed-token commit. When no transcript row can host it (form restored after a mid-turn webview reload, or a second window on the same session), the same panel falls back to its floating slot above the input row. Submit sends one `{id, value}` per question, Dismiss sends `None`. Every wait outcome returns **structured JSON** (`status: answered/dismissed/timeout/cancelled` + an English note), never an `Error:` prefix — a user who was away or pressed Stop must not count towards the tool-failure guard. Only malformed *arguments* are errors. The panel is not gated on the active session (the form is the only way to unblock that turn — a session switch just loses the host row and drops the panel to the floating slot) and is cleared when streaming ends, on Stop, or on `todo-ask-closed`.

### Turn guards — rounds, tool calls, repeated tool failures

- `src-tauri/src/turn/guard.rs` holds both guards; `chat_completion` → `run_chat_turn` is the only loop that spends a `TurnBudget`.
- **Round / tool-call budget** (`config.main_agent_max_rounds`, `config.main_agent_max_tool_calls`, Settings → Advanced; `0` = unlimited, hard caps 1000 / 5000 clamped by `AppConfig::normalize_turn_limits`): `begin_round()` counts every request, `record_tool_call()` every tool that actually runs. When either limit is spent the loop does **not** stop mid-flight: it sets `wrap_up`, emits `chat-notice {kind: "budget_exhausted"}`, appends `CONTEXT_BUDGET_MARKER` as a **`user`** message at the tail, and sends **one more request with the identical `tools` array but `tool_choice: "none"`**, so the model must answer with what it already collected (`BUDGET_FALLBACK_ANSWER` when that answer is empty). The remaining calls of the round are answered with `turn_guard::budget_notice`, so every `tool_call_id` still receives a `tool` message.
- **Prompt-cache invariant (why the wrap-up keeps `tools`)**: `tools` is rendered *before* the messages, so any change to that array — dropping it, adding a tool, filtering one out — moves every following token and invalidates the whole KV / prefix cache for that request. Keep the array byte-identical within one run and change it only at request-boundary-free moments (i.e. between turns). `tool_choice: "none"` still forbids calls, and the budget short-circuit answers a call that a gateway lets through anyway.
- **Tool failure guard** (`config.tool_failure_limit`; `0` = off, hard cap 50): consecutive failures per `(session_id, tool_name)`, kept in `AppState::tool_guard`. A success resets the counter; the failure that reaches the limit disables the tool for the rest of the session, appends `turn_guard::disabled_notice(…, just_now = true)` to that same result and emits `chat-notice {kind: "tool_disabled"}` (shown by `App.tsx` as a warning notice). **Removal from the payload is deferred**: all three loops snapshot `disabled_tools()` once at the start of the turn / helper run / agent run and filter `tools` from that snapshot, so a tool disabled *mid-run* stays advertised (cache-stable) and is only short-circuited with the same notice; it disappears from the payload on the next turn or run. The main agent, the sub-agent loop and `run_main_agent_helper` share one guard, so "disabled for this session" holds across all of them; `apply_config` calls `reset_all()` when the limit changes, because raising it is how a user releases tools without restarting.
- Failure detection is `turn_guard::tool_output_is_error` (`Error`/`Error:`, `MCP tool error`). Use it instead of a hand-written prefix check, so the interaction log's `tool_error` rows, the UI's `ok` flag and the guard all agree. Tool output and progress rows are plain text — no emoji glyphs as markers.
- **A cancelled tool result is not a tool failure.** Stop interrupts the tool that is still running, and its result then reads like an error (`Error: … cancelled by the user`). Three of those in a row used to disable the tool for the rest of the session — at exactly the moment the user asked to stop — so the next turn had no tools left to continue the plan with. Every guard call goes through `turn_guard::counts_as_failure(output, turn_cancelled)`, which ignores the failure while the turn's own flag is set. The interaction log still records the row as `tool_error`: what happened did not change, only its effect on the budget.

- **Rejected wrap-up**: a gateway that refuses `tool_choice: "none"` must not turn the end of a turn into an error bubble — the failed request is logged as `WARN` and `final_answer` falls back to `BUDGET_FALLBACK_ANSWER` instead of propagating the error.

- **Tool-pairing repair (strict DashScope rejection)**: a provider that 400s the request over tool_call_id pairing (`The tool_call_id in the response message does not match the tool_call_id in the tool_call: messages: message[N]`, observed on `deepseek-v4.1-flash-ms`) used to kill the whole turn. The main loop now sanitizes with `sanitize_tool_pairs_strict` (`llm_client.rs`) — the provider's own rule: every `tool` response must sit in the block directly following its assistant, one response per declared id; on the sequences the loop builds this is a no-op, but it cleans anything the lenient pairing would have blessed. If the request still dies with a pairing error, `is_tool_pairing_error` classifies it and the turn gets **one** round-drop retry (`pairing_repair_used` flag, same pattern as the reactive compression): `drop_tool_round` removes the round the reported `message[N]` index points at (assistant + its following tool block, injections after the block are kept; without a usable index the last round goes), a WARN log records `message_id_map` — the per-message role/id map of the rejected sequence, since `request_body` is deliberately not persisted in the monitor — and the request re-sends. The model loses that round's results but re-plans from the rest; a second failure propagates the error as before.

### Parallel tool calls

- **One round executes in segments, not as one `for` loop.** `tools/batch.rs` classifies every call (`call_mode`) and `plan_segments` turns the round into half-open index ranges. Neighbouring `Concurrent` calls run together through `futures_util::future::join_all`; a `Barrier` is a one-element range and therefore runs alone, in `tool_calls` order. `src-tauri/src/llm_complete/tool_call.rs::run_tool_call` is the per-call dispatcher (background routing, MCP, `call_subagent`, `tools::execute_tool`) — it never mutates loop state, which is what makes it safe to run several instances at once. `use_skill` is handled by `load_skill_for_call` in `turn.rs` instead, because it mutates the round's own state (merged allowed commands, active skill dirs, queued skill context).
- **Classification is an allowlist.** Concurrent: `file_actions` read/list/search/diff, `run_cmd`, `run_shell`, `calculator`, `skill_read`, `call_subagent`, and every MCP tool (decided by the caller, since MCP names are generated). Everything else is a barrier — `use_skill`, `memory`, `todos`, `timer_*`, `background_task`, `mcp_self`, `skill_merge`, `experience`, the mission tools, mutating `file_actions` actions, and any unknown tool. Silence stays sequential.
- **The sub-agent loop adds its own barriers** (`agents/helper.rs::run_llm_agent_body`): `mbus` (bus subscriptions) and **every MCP call** — `mcp::invoke_mcp_tool_in` borrows the owner's `McpSession` mutably, so two of them cannot share a segment. `evolution_maintenance` stays sequential on purpose.
- **Configuration**: `config.parallel_tools` (the bottom block of the Tools sidebar, default on) and `config.max_parallel_tools` (default 4, clamped 1–`MAX_PARALLEL_TOOLS` = 8; `1` is the old strictly sequential behaviour). `normalize_turn_limits` clamps them on every load/save. The system prompt advertises batching only while the switch can actually parallelise.
- **Order is preserved end to end**: results are written back by index, failure accounting (`tool_guard.record` + `chat-notice`) runs after the whole round in `tool_calls` order, and the `tool` messages carry the model's original order whatever order the calls finished in. One intentional semantic change: a call that trips the failure limit no longer blocks the calls beside it — they are already running — only the next round's calls.
- **`tool-call` events carry `call_id` + `phase`** (`progress` / `done`, `done` also carries `ok`). The frontend upserts the row of that exact call instead of settling every running row, which the sequential UI could do safely and a parallel round cannot. `emit_tool_call_done` closes the row (a tool that emits no progress still gets a visible row); `skill-loaded` carries the same `call_id` so the `use_skill` row is created and settled by the same call; `confirm-required` carries it so an inline `run_shell` approval row and the tool row are one row. Events without `call_id` (background tasks, conclusion notices, guide markers) keep the legacy "append and settle the previous row" behaviour.

### Turn identity — Stop, superseded turns, resumed plans

- **Every `chat-*` payload names the turn it belongs to.** `chat-token` / `chat-reasoning-token` / `chat-retry` / `chat-error` / `chat-done` carry `{ turn_id, … }`, where `turn_id` is the id the frontend minted in `chatCompletion` (`api.ts`, `newTurnId`) and passed to `chat_completion`. `api.ts` drops any payload that is not tagged with its own id. A stopped turn keeps emitting for seconds while its foreground tool returns, its sub-agents tear down and a background hold expires; before this, its `chat-done` closed the *next* turn's transcript (empty bubble, then nothing). New emitters must tag — an untagged `chat-*` payload is invisible to the UI.
- **`stream.rs` carries the id as `StreamOptions::turn_id`; the turn base emits through `turn.emit_token` / `turn.emit_done` / `turn.emit_error`.** Sub-agent, planner, summarizer and maintenance requests pass `turn_id: None`: their events are their own (`agent-task-*`, `agent-planner-*`, `evolution-maintenance-*`), never chat events.
- **Turn-end cleanup belongs to the turn that ended.** `end_turn_cleanup(app, turn)` skips all of it (background-task shutdown, `background-waiting: 0`, serve teardown, private MCP pool shutdown) when `TurnRegistry::superseded` already says a newer turn owns that session: the user pressed Stop and sent the next message before this one finished unwinding, and those tasks belong to the new turn. `chat_completion` publishes the base (`AppState::begin_turn`) before any side effect and removes it from the registry only after cleanup, so the window id is what cleanup and the removal key on.
- **Stop settles the plan.** `stop_chat_completion` calls `todos::settle_interrupted`, putting every `in_progress` item back to `pending` and emitting `todo-state` (`type: "todo_state"`, handled by `TodoList.tsx`). Nothing is running any more, so the next turn — and the goal loop, which resumes an unfinished list — must not resume against an item that looks busy.

## Composer attachments (paste / drop)

- **A pasted or dropped file is a workspace file plus a mention.** `save_pasted_file` (clipboard bytes from `Ctrl+V`) and `import_workspace_paths` (real OS paths from Tauri's native drag-drop — `dragDropEnabled` swallows HTML5 drops, so `onDragDropEvent` is the only source) copy into `<workspace>/.data/tmp/<name>.<ext>` — the file's own name, `-2`/`-3` on a collision — and return that relative path; `src/composerFiles.ts` splices the short `@@<name>` form into the draft at the caret, and the normal mention pipeline attaches it at send time. There is no second attachment channel, so `partsForContent` (`src/messageParts.ts`) stays the only place an attachment becomes a content part. A dropped file that already lives in the workspace is the one exception: `mentionable_workspace_path` returns it *where it is* instead of copying, so a project file is never duplicated and never lands on the paste clock — only a drop from outside (or a path the mention grammar cannot carry: space, `#`, `@`) is copied.
- **`.data/tmp` is the one state folder the composer may read and write.** `resolve_in_workspace` (`workspace_files.rs`) rejects `.data` with a *component-wise* exception for a leading `.data/tmp`, so a paste written there can be read back by its own `@` mention while the database, skills, scripts, memory and deliverables stay unreachable — and a lookalike sibling (`.data/tmpx/…`) is still refused. It is also the folder the Settings panel's "open temp dir" button shows and where `convert_pdf_mention` caches its Markdown. The scratch root has two writers with two lifetimes: `pdf/` is the PDF mention cache (entries older than a week are dropped when the next conversion runs) and `<name>` (the file's own name, `@@<name>` in a message) is a composer paste, swept after 24 h. That sweep only ever deletes *files* sitting directly in the folder and older than a day, so the `pdf/` cache — a directory — can never be removed by it. Sub-agent deliverables live in `.data/deliver` and are not part of the scratch clock.
- **Anything new in `.data/tmp` must own its expiry.** Anything that must outlive a day goes into a *subdirectory* — `pdf/` is the model to copy — because every plain file sitting directly in `.data/tmp` is treated as scratch and swept on the next paste.
- **Reports and user-facing deliverables go to the project folder, never `.data/tmp`.** The scratch folder's 24 h clock makes a report written there a report lost tomorrow, so the model is told twice: the `DELIVERABLES` block of the system prompt (`llm_complete/engine.rs`, injected when `file_actions` is enabled) and the `file_actions` description (`tools/schema.rs`) both send reports, documents and generated artifacts to `./<project>/…` inside the workspace — the folder the task is about, or one the model creates — and both require copying whatever a sub-agent left under `.data/deliver/…` there before calling the task done. The sub-agent exchange block (`agents/exchange.rs`) names its task directory the *handoff* copy, so the two rules cannot read as a contradiction; short-lived scratch may still use `.data/tmp`.
- **A format the model cannot read is handed over, not dropped.** `resolveFileMentions` (`src/fileMention.ts`) reports an unsupported mention in `MentionResolution.handoff` instead of `problems`: nothing is attached (a `file` part is rejected by the gateway, and decoded bytes would be mojibake), the `@@<name>` token stays in the draft — `insertMentionPaths` inserts every pasted/dropped path, and only the warning notice marks the unreadable ones — and `sendMessage` appends `handoffNote(...)` (`src/composerFiles.ts`) after the message text: the token, its workspace-relative path, and the order to inspect and parse the file with `run_shell` (python/pandas for xlsx, `unzip` for docx, `pdftotext` for pdf) before answering. The note lives in the user turn, so later requests replay it with the transcript.
- **Names are rebuilt, not escaped.** The mention grammar (`@@?[^\s@#<>]+`) ends a token at whitespace, `#`, `@`, `<` and `>`; `sanitize_tmp_name` (`workspace_files.rs`) keeps letters/digits/`-`/`_`/`.` (CJK included) and collapses everything else, so `my screenshot #2.png` cannot split its own token.
- **A reply and a user body are rendered by different markdown profiles.** `ChatMessage.tsx` builds `md` (reply: figures, KaTeX, `image` restricted to `https?:` / `data:image/<raster>;base64,`) and `mdLiteral` (the user's own text, `image` rule disabled). Raw HTML is off in both. Enabling image syntax for the user body — or raw HTML anywhere — turns typed text into live elements (`![a](b)` → `<img>`), which is the HTML-leak hole this split closes.
- **Rendering failures cost one row.** `renderMarkdown` catches a throwing renderer and degrades to escaped literal text; `ChatMessageBoundary` wraps every message, so a component-level throw shows a readable row instead of blanking the transcript.
- **The sent message never carries a paste path.** the draft already carries the short `@@<name>` form (`mentionTokenForPath`), and `canonicalTmpMentions` (`src/composerFiles.ts`) collapses a hand-typed `@.data/tmp/<name>` to it — keeping a `#12-24` range, because the inlined copy holds only those lines — before `partsForContent` (`src/messageParts.ts`) sees the text, and the inline summary reads `Attached File: @@name.ext — already provided below`. Both exist for one reason: a path the model can open is an invitation to `file_actions read` a file whose bytes are already in the request, which is one wasted tool round per attachment. Mentions outside the tmp folder keep their path (`src/App.tsx` is meaningful, and the model may need the rest of it), so the rewrite is keyed on the tmp folder rather than on "was it attached".
- **An attachment is named, never listed.** The transcript has no "Attached Files:" chip row: a file is represented by its accent `@name` token in the body (`highlightFileMentions` paints it in the colour a path mention wears), which is why the rewritten token keeps its `@`. A chip row repeats that name — and, before the rewrite existed, dragged the machine path back into the conversation, which is what the row was showing. The one exception is an image: it is the content rather than a reference to it, so it stays visible as a thumbnail (`ChatMessage.tsx`'s `imageAttachments`, no caption, since the body already names it).
- **`&path` is a reference without bytes — the only token that never reaches the attachment pipeline.** Typing `&` in the composer opens the same popup (`FileMentionPopup` with `mode="path"`, grammar in `src/pathRef.ts`) and inserts `&<path>`; `MENTION_RE` in `src/fileMention.ts` only matches `@`, so `resolveFileMentions` cannot see the token, `partsForContent` gets no attachment for it, and the request carries the path as text and nothing else. Three consequences follow from that one fact: the list has no capability filter (a model that cannot read a format can still be pointed at the path and parse it with a tool), there is no `#12-24` range (nothing is sliced), and `sendMessage` appends no `handoffNote` (there is no attachment being handed over) — while `highlightPathRefs` paints the token in the same accent `@` wears. A path the token grammar cannot carry (whitespace, `#`, `@`, `&`, `<`, `>`) is filtered out by `isPathRefExpressible` instead of being inserted as a reference that would resolve to the wrong file. And because the token is plain text, `&` is the only composer picker that stays available in injection mode (`syncPathRefFromInput` has no `streaming` guard, unlike its three siblings).
