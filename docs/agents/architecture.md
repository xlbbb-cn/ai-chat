# Architecture, runtime layout and Tauri 2 specifics

> Part of the Rabbit Chat Studio developer docs. Read this when you need to know how the pieces fit or where runtime data lives.
> The index for all of them is [`AGENTS.md`](../../AGENTS.md) — it also holds
> the rules that apply to every change, whatever file you ended up in.

## Architecture

- **Entry points**: `src/main.tsx` → `src/App.tsx`; Rust `src-tauri/src/main.rs` → `src-tauri/src/lib.rs` (command registration, state, app setup).
- **IPC contract — two halves, both explicit.** Invoke: every `#[tauri::command]` lives in `src-tauri/src/ipc/<domain>.rs` (`app`, `config`, `chat`, `evolution`, `history`, `skills`, `experiences`, `mcp`, `agents`, `tools`, `workspace`, `update`, `figures`, `notify`) and only forwards to the owning domain module (`pub(crate)` implementation) — `src/lib.rs` keeps the one `generate_handler!` list and no command bodies. Events: `src-tauri/src/events.rs` owns every backend → frontend event name as a constant plus the payload structs for the fixed-shape events (`ChatToken`, `ChatUsage`, `ChatNotice`, `ChatInjected`, `ToolCall`, `ConfirmRequired`, `AgentTask*`, `EvolutionMaintenanceState`, …); emit sites never carry a string literal, and a field renamed there must be renamed in `src/api.ts` / `src/types.ts` too. A few payloads stay `json!` because they are assembled incrementally or nest a domain type (`todo-state`, `risk-assessment`, `syntax-error`, `agent-selection`, planner/mbus events) — their names still come from `events`.
- **Dependency direction (the point of P3):** `llm_complete` → `agents` → `llm_client` + `tools`, never the reverse. `src/llm_client.rs` is the streaming transport (SSE chunks, retries, headers, `ChatMessage`, `content_to_text`, `sanitize_tool_pairs`) and depends only on `db`, `http`, `events` and `AppConfig`; both the chat engine and the sub-agents use it, so `agents` never imports `llm_complete`. Mission-ledger tools live in `agents/mission_tools.rs`; the callers (`llm_complete::run_tool_call` and the sub-agent loop) dispatch them before `tools::execute_tool`, so `tools` has no dependency on the agent system. `http.rs` owns the two reqwest clients (catalogue + stream) and `executable.rs` owns PATH/PATHEXT resolution, shared by `run_shell` and the CLI agents. `AppState.confirm` groups the three one-slot user-decision queues (tool confirmation, `todos ask`, external-agent approval).
- **Boot bundle (frontend)**: the first frame parses exactly two JS chunks — `main` (`App.tsx`, the composer, `api.ts`, i18n) and `App` (React, framer-motion, FontAwesome). Everything a *reply* needs is behind `lazy()`: `ChatMessage` (markdown-it, highlight.js with its language pack, the figure / mermaid card machinery), `ToolCallGroup`, the sidebar panels (Settings / Skills / Tools / MCP / Agents / History) and `MarkdownPreview`. A launch starts with `messages = []`, so none of that is on the boot path. `ChatMessageBoundary` is its own module on purpose — the boundary must be mounted before the chunk it wraps arrives — and its two classes (`.markdown-fallback`, `.message-render-error`) live in `App.css`, not `ChatMessage.css`. `warmTranscriptChunk()` (idle, plus the composer's first focus — `requestTranscriptChunk`) and the idle panel prefetch fetch the chunks after the first paint, so a first message or an opened panel does not wait for a round trip. KaTeX stays a dynamic `import("katex")` (`utils/markdownMath.ts` + `preloadKatex()`); when a heavy library (katex / markdown-it / highlight.js) is *statically* reachable from `App.tsx` again, Rollup inlines it into the boot chunk — that is exactly how a ~583 KB KaTeX copy used to sit in `main`, unnoticed, until the transcript was split out. Verify with the built `dist/index.html`: only `main` and `App` may be in the entry graph.
- **Streaming chat**: `chat_completion` command opens an SSE connection (`reqwest` + `futures-util`) and emits to the frontend:
  `chat-token`, `chat-reasoning-token`, `chat-done`, `chat-error`, `chat-usage`. Streamed tool calls are normalised before use: an empty or duplicate `id` (some relays omit it) gets a generated `call_…` id, so the assistant `tool_calls` and the following `tool` messages always agree and strict providers (DashScope) accept the next request.
- **`[System]` notices are transcript footnotes.** `ChatMessage` lifts the backend's `\n\n[System] …\n\n` paragraphs (context compression, output-token continuation, todo suspension) out of the reply *before* the markdown pipeline and renders them as one flat `.message-system-notes` card after the body (docs/DESIGN.md, *Transcript*). The paragraph shape is the wire format produced by `llm_complete/engine.rs`; the stored content is unchanged, so a reloaded turn parses the same card. The card lives beside `.message-content`, not inside it, which keeps it out of the PDF export and means the reply's markdown never contains a status line. The desktop notification line skips `[System]` lines for the same reason.
- **Retry** (`retryPendingUserMessage` in `src/App.tsx`): the button is offered only on the last user message of a failed turn. Clicking it truncates that turn *before* the new request — everything after the user row leaves the transcript in one `setMessages` replacement and is deleted from `history` (`db::delete_messages_after`, scoped by session). The turn's pending `saveHistory` write is awaited first, so the partial assistant row the failure persisted cannot land after the DELETE; without the database half a reload would replay the failed rows next to the retried reply. A new message typed after a failure still keeps the interrupted reply as context — only retry removes it.
- **Turn cost footer**: after a turn settles, the reply's action row shows `duration · total tokens · cache hit` as muted 12px text (`ChatMessage` → `.message-usage-meta`, documented in docs/DESIGN.md). The figures are turn-scoped, not the session-wide accumulation that feeds the context gauge: `turnStatsRef` in `src/App.tsx` is reset by `beginTurnStats()` at every turn start (send and retry) and each `chat-usage` of the turn adds to it. The terminal handlers (`onDone` × 2, `onError` × 2, `stopStreaming`) call `settleTurnStats()`, which returns `undefined` when no request reported usage — the footer is hidden rather than showing invented zeros — and derives the hit rate as `Σcached / Σprompt` (only when a cache dialect was reported; the event's `hit_ratio` is per-request and is not used). The record is stamped on the assistant `Message.usage_meta`, passed to `saveHistory` as its tenth argument and stored in `history.usage_meta` (lazy `ALTER TABLE`, copied by `fork_session`), so a reloaded session shows the same line. Sub-agent and planner requests run with `emit_usage: false`, so the totals cover the main chat's requests only.
- **Mid-turn injection** (`inject_user_message` → `turn::LlmTurn::inject`, the base's own inbox): the composer stays usable while a turn streams, and Enter then appends the text to the *running* turn instead of starting a new one. A turn is a sequence of requests, so the queue is drained at the top of the main tool loop — the only safe boundary, because an `assistant` message carrying `tool_calls` must stay adjacent to its `tool` results — **but only while the turn is not cancelled**: the loop breaks before the drains when `turn_cancelled` is set (Stop pressed during a foreground tool or a confirmation wait reaches this boundary seconds later; without the break the dead turn would announce deliveries the model never saw, and the announcement would land in whatever chat is open). The text is appended as a `user` message (never `system`: some OpenAI-compatible gateways reject mid-conversation system messages) and announced with `chat-injected`, which carries the turn's `session_id` — the UI drops events from another chat, the same rule the `background-task-state` / `background-waiting` listeners apply. A reply that already made its last request has no boundary left: the window closes with the turn (`LlmTurn::close_inbox`, called before the turn announces its end on every path) and the UI re-sends those items as a normal next turn. Deliveries are stored on the assistant row (`history.injections`) and replayed as user messages, since one turn is still one row.
- **Context compression** (`src-tauri/src/llm_complete.rs`): the main chat keeps its prompt inside the model's window in four layers. (1) **LLM structured summary** — when the post-response usage ratio crosses `CONTEXT_COMPRESSION_THRESHOLD` (0.8), the older region is summarized by the main model through a 9-section compact prompt (intent / concepts / files / errors & fixes / problem solving / **all user messages** / pending / current work / next step, adapted from Claude Code's compact prompt); the summary call reuses `stream_llm_request` with every UI event off and passes the turn's cancel flag, and on any failure/cancellation/degenerate answer the mechanical line summarizer runs instead, so compression can never fail the turn. (2) **Tool ledger** — tool rounds are no longer dropped without a trace: the summarizer input and the mechanical fallback both render each round as `name(args) → result preview` (chars-capped). The recent window (`CONTEXT_KEEP_RECENT_MESSAGES` = 12) is always kept verbatim and may only start on a clean round boundary (`is_clean_split_boundary`), so `sanitize_tool_pairs` never has to strip a kept tail. (3) **Summary replacement across turns** — `session_summaries` stores `covered_messages` (how many UI history messages the summary stands in for) plus `boundary_text` (flattened prefix of the last covered message); the next turn verifies the boundary and DROPS the covered prefix of the incoming history (Claude Code's compact semantics: the summary replaces the old transcript instead of being replayed on top of it). A boundary mismatch (edited/restored history) discards the stale summary and replays the full history — the old, always-safe additive behavior. The summary message is a `user` message with "This session is being continued…" framing (never a mid-conversation `system` turn) and sits BEFORE the remaining history, so it is a stable cache prefix. (4) **Predictive + reactive triggers** — a pre-request estimate (≈4 chars/token, tools JSON included; saturated when the static payload itself dominates) compresses before a request that would exceed ~90% of the window, and a provider `context_length_exceeded`-style rejection triggers one hard compression (`CONTEXT_REACTIVE_KEEP_RECENT_MESSAGES` = 6) and a single retry. The sub-agent loop in `agents.rs` has its own LLM episodic summarizer (`summarize_agent_memory`).
- **Evolution maintenance (the empty-state nap face)** (`src-tauri/src/evolution_maintenance.rs`): while `config.self_evolution_mode` is on, the empty-state smiley is a `<button>`; hovering shows a small speech bubble with "点击让我小憩一下" and clicking starts a **silent** maintenance turn. With the mode off the same face is a plain decorative `<div>` — no hint, hover treatment, focus target or click handler. It is deliberately not a chat turn: `start_evolution_maintenance` claims `AppState.evolution_maintenance` (a separate slot from the chat turn registry), emits `evolution-maintenance-state` (`running: true` with the live `phase` / `round` / `toolCalls` that replace the empty-state greeting with a status block, then a terminal `done` / `stopped` / `error` with the model's report; a `done` report becomes a clickable result bubble that restores the greeting when dismissed), and never writes history or a `chat-*` event, so the empty state stays visible and a maintenance finish cannot settle a real reply. The loop uses the main model with `memory`, `file_actions` and the maintenance-only `skill_merge`, capped at 100 rounds / 300 tool calls / 15 minutes, with `stream_llm_request` (`emit_tokens: false`, `emit_errors: false`). When the round, tool-call or wall-clock budget is nearly spent (80% of the 15 minutes) the last request gets a `user` budget notice and `tool_choice: "none"`, so the pass ends with a report (and explicitly deferred work) instead of a timeout error; the prompt also caps each pass at 10 duplicate groups / 10 skill groups / 10 memory clusters, leaving the rest for the next click. A hard allowlist refuses every other tool; `file_actions` may only read freely and write auxiliary files inside `.data/skills` (never `skill.md`, never `.data/memory`/`skills.status`; `delete`/`rename`/`move` are refused). Three inventory sections drive the pass (`build_inventory`): the skills list, **Memory to forget** (`memory::noise_candidates` — entries whose *name* reports its own activity, “报告已生成” / “完成task1” / “改完了…”, plus `source: auto` notes the recorder left at importance 2; nothing is offered when it is pinned, `source: user`, importance ≥ 4, confidence ≥ 4, evidence ≥ 3, `uses` ≥ 3 or a recipe/pitfall/location, and `evolution-maintenance-progress` is always excluded) and **Memory to merge** (`memory::duplicate_groups` — 2-4 notes stating one thing under different keys, grouped by token overlap over key/title/tags and body, noise entries excluded). The prompt forgets the noise entries it judges unusable with `memory delete`, merges each duplicate group into one dense `memory add` in the best-fitting scope *before* deleting the redundant keys, merges overlapping **self-evolution** skills through `skill_merge`, runs `memory consolidate` `plan`/`apply` per cluster, deletes stale entries with recorded conflicts, and reports what changed; `source: user` and unknown-source skills are off-limits. The `session` scope is in-memory and the pass runs under its own session id, so code sweeps it instead: `memory::prune_session_noise` drops progress-phrase notes from every session bucket when the pass starts, and the opening inventory states how many went. `skill_merge` (`src-tauri/src/tools/skill_admin.rs`) validates the target/sources, writes and enables the merged skill (`.bak.N` for the old file), then backs up each source folder as `<folder>.bak.N` and deletes it; the dispatcher also requires `mission_id == evolution-maintenance`, so the main agent and sub-agents cannot call it. Cancellation: `stop_evolution_maintenance` (two clicks within 320ms on the napping face; keyboard activation stops immediately), any chat turn start (`chat_completion`), a workspace switch, or turning the mode off. `get_evolution_maintenance_state` restores the napping face after a webview reload. The face parks, closes its eyes and breathes; a 4px bubble shows a **horizontal** random-glyph ticker plus drifting `z`s, all frozen under `prefers-reduced-motion`. A partial pass (user stop, budget exhaustion, upstream error or timeout) writes/updates the `evolution-maintenance-progress` entry in the `evolution` memory scope with the reason, round/tool/token counts and the last tool calls; the next pass's inventory includes it as "Previous maintenance progress" and resumes from it. That entry is excluded from consolidation clusters and cannot be archived or deleted by the `memory` tool; only a completed pass clears it.
- **Agent orchestration** (three switches, all in the Agents panel): `use_agents` = sub-agent system, `auto_plan` = a planning pass before every answer, `auto_configure` = the one-call agent selection. `run_chat_turn` gates `call_subagent` and the agent roster on `use_agents` but the mission on `use_agents && auto_plan`, so planning off keeps manual delegation. With `auto_plan` and `auto_configure` on (default), one non-streaming selection call (`select_agents` → `agent-selection`) proposes the roster for this turn; a declined selection (`delegate: false`) skips planning entirely and the main agent answers directly. When selection allows delegation, the planner call itself first answers `delegate` again (`PlanDecision`): an explicit `delegate:false` also skips the mission, returns a declined selection and leaves the answer to the main agent; `delegate:true` plans tasks (a single task is valid). The selection chip is emitted only after the planner confirms, so a declined plan never shows a stale roster. The plan is parsed with one repair retry and sanitized (fence/prose stripping, trailing commas, unknown `agent_id` dropped, duplicate task ids renamed, dangling and cyclic dependencies removed). Execution then runs in dependency waves (parallel, `max_concurrent`) or in list order (sequential). A task that never ran — unknown agent, skipped dependency, or Stop — is reported as `skipped` (`agent-task-skipped`) instead of being dropped silently, so the mission report is never shorter than the plan. The selected roster only narrows what the main session's system prompt advertises; `call_subagent` still accepts any enabled agent id. Events: `agent-selection`, `agent-plan-start`, `agent-task-start`, `agent-task-token`, `agent-task-reasoning`, `agent-task-tool`, `agent-task-done`, `agent-task-error`, `agent-task-skipped`, `agent-aggregate-done`. A task row owns its status: `agent-task-reasoning` (live thinking counter) and `agent-task-tool` (tool activity, phase `start`/`progress`/`done`) only feed the row's activity line, and the generic `tool-call` event is main-chat-only — tool progress inside a mission is routed to `agent-task-tool` through `tools::emit_tool_progress`. Settling a running task row on a main-chat event is what made a working sub-agent show a checkmark and stop updating. `agent-task-done` carries `status` (`success`/`stopped`) so a stopped task renders neutral rather than completed. Sub-agent requests use `emit_errors: false`: `chat-error` closes the user's turn in the UI, so a provider failure must surface as `agent-task-error` only. The aggregation step is instantaneous (the mission report is only rendered for the main agent), so `agent-aggregate-done` reports an already-completed step — never render it as "running".
- **Planner model (`AgentOrchestration.planner_model`, empty = `config.model`)**: one field decides the model for every planner call — the selection call, the task plan and the mbus supervisor — so a mission can plan on a smaller model while every sub-agent keeps its own `model`. `AgentOrchestration::planner_model_or` is the only resolver (an empty field inherits the main chat model, exactly the behaviour before the field existed), and `normalize_config` trims the id and turns a blank into `None` on both load and save. The Agents panel offers the composer's catalogue plus an explicit "follow the main model" row; the picker also keeps a configured id that has since left the catalogue.
- **Mission bus (`mbus`, `AgentOrchestration.mbus_enabled`, default on)**: every planner-dispatched batch creates one `MissionBus` (`src-tauri/src/agents/mbus.rs`) for the turn. It is an in-process MQTT-like pub/sub channel: peers are the planner and the plan's tasks; `broadcast` is auto-subscribed by everyone; subscriptions support `+`/`#`; direct messages use a task id, a unique agent id, or `planner`. A sub-agent drains its inbox at the top of a reasoning round (after context compression, before building the request) and appends each message as a `user` message carrying `mbus::MBUS_INJECTION_PREFIX` — the same request-boundary rule as the main agent's mid-turn injection, never mid-stream. The bus also keeps a live status registry (pending/running/completed/error/skipped, rounds, tools, tokens, last tool, queued messages, summaries, objectives, per-pair counts and the mission's active sub-tasks) and bounded message/inbox/rate limits. `cli` / `cloud` peers are status-only while running; they can absorb messages queued before their process starts. A message published by an agent can reach another agent, a topic subscriber, or the planner; the planner is a normal peer with its own inbox.
  - **Per-pair cap (`AgentOrchestration.mbus_pair_limit`, default 4, `0` = off)**: every successful delivery between two sub-agents increments one *unordered* counter (both directions combined); topic/broadcast counts each actual recipient separately, and the planner is exempt. The message that reaches the cap is still delivered and, once per pair, queues a `Mission bus` escalation into the planner's inbox (persisted in `agent_bus_messages` and emitted as `agent-mbus-message`). Later messages between that pair are rejected with an explicit "planner has been notified, do not retry"; a topic publish skips exhausted recipients and lists them under `skipped`. The sender's tool result reports `pair_limits` so it knows which message was the last.
  - The planner can therefore take over: `direct` (`to` + `objective` + optional `done_when`) stores an authoritative objective on the peer (re-rendered in that task's mission snapshot every round, so it survives context compression) and also queues it as a normal bus message; `end_task` (`to` + optional `note`) sets a conclusion the `llm` task notices at its next reasoning boundary — it then reports its current result as a success instead of spending another request. `cli` / `cloud` tasks cannot poll the bus, so `end_task` rejects them.
- **Planner supervisor (`src-tauri/src/agents/supervisor.rs`)**: when `mbus_enabled` is on and the plan contains at least one `llm` task, the planner stays alive concurrently with `execute_tasks` (a `oneshot` cancels its in-flight call when the last task settles). It is event-driven: the initial dispatch, terminal task events, messages addressed to the planner, broadcasts and per-pair limit escalations wake it; a 30 s heartbeat only activates when a running task has been idle for ~90 s. Its only tool is `mbus` (`send`, `status`, `history`, `subscribe`/`unsubscribe`, and planner-only `direct`, `end_task`, `finish`), so it cannot edit files or change the plan. Budget: 10 activations (1 for a single-task plan), 4 tool rounds per activation, 1 024 completion tokens, 60 s per request. Its final note reflects the bus statuses (`N completed / failed / skipped`) instead of assuming every settled task succeeded. Events: `agent-planner-state` (`thinking` / `monitoring` / `done` / `stopped` / `error`), `agent-planner-action` (one tool-group row per planner decision: `schedule`, `send`, `status`, `history`, `subscribe`/`unsubscribe`, `direct`, `end_task`, `finish`; a `running` event creates the row and the matching `done`/`error` event settles it), `agent-mbus-message` (one publish with recipients), `agent-mbus-delivered` (messages injected into a sub-agent round).
- **Sub-agent failure handling / capability fit**: every sub-agent LLM request, tool call and result is logged to the dated `app-<date>.log` (model, round, token count, tool name, clipped args/result; each line tagged `[primary-<pid>]` / `[shadow-<pid>]`, so multi-instance windows writing the same file stay attributable, and startup sweeps old files by `log_retention_days`). Provider balance/quota failures (`Insufficient account funds`, 402, free-usage limits) are classified and surfaced as `Upstream account balance/quota exhausted`, the task fails instead of retrying, and `close_mission` marks the mission's `agent_tasks` `failed`/`stopped` so they disappear from active-task lists; `agent_missions.created_at` is reset on a reused mission id. The selector/planner catalogue includes `mcp=enabled|none` and is instructed never to assign live web/browser/API retrieval to a file-only agent (if no agent has the data channel it declines delegation so the main agent's MCP tools handle it). A sub-agent without the required tool is told (the `TOOL FIT` block of its static prompt) to stop and report the missing capability instead of scanning local snapshots — the main agent then re-delegates with an agent that has the right channel.
- **Composer `+agent` roles** (`src/agentMention.ts`, `src/components/AgentMentionPopup.tsx`): typing `+` at the start of a line in a conversation with **no history** opens the third composer popup (same `.file-mention-*` surface as `@file` / `/skill`); it lists only enabled `llm` sub-agents whose `system_prompt` is non-empty (`list_agent_mentions` — a lightweight roster that never ships the prompts). The line grammar allows only `+token` words, so `2 + 2` and `C++` never trigger it. Selecting inserts `+token` and the token stays in the body. On the first send the frontend passes the selected ids (`embeddedAgentIds`); the backend freezes a `{id,name,description,prompt}` snapshot into `session_meta.embedded_roles` (`db::set_embedded_roles`) and refuses to do so once the incoming history contains an `assistant` row. `run_chat_turn` reads that snapshot every turn and appends `render_embedded_roles(...)` to the END of the main system prompt, so the role survives reload, history reopen and fork (`fork_session` copies the row) without a live agent lookup. Only the prompt is embedded: model, temperature, tools, skills, MCP and approval rules stay the main agent's, and safety/tool rules take precedence. Editing or deleting the agent afterwards never changes a started session. Tokens come from the display name when token-safe, else the md file stem, else a short id fragment, deduped with `-2`; the transcript highlights known `+tokens` the same way it highlights `/skill` names.
- **Mission bus persistence**: `agent_missions.bus_id` links a mission to its orchestration batch, and `agent_bus_messages` stores one row per publish (`bus_id`, sender, target kind/id, topic, body, recipient count, timestamp). `list_mission_bus_messages(mission_id, limit)` backs the “Message bus (mbus)” section of `components/AgentMissionPanel.tsx`; the task rows show live sent/received counts and the last note. Messages are in-memory for delivery and in SQLite for replay, so a bus is discarded with its turn while the Mission panel keeps the history.
- **Turn cancellation** (`turn::commands::stop_chat_completion` + `TurnRegistry::cancel`, session-addressed): every turn runs on a `turn::LlmTurn` base that owns its cancel flag; a new turn in the SAME session supersedes the previous one — the old flag is set `true` permanently, so a winding-down turn can never be resurrected — while turns of other sessions keep running untouched (multi-session), and Stop pressed while idle cannot leak into the next turn. The flag is threaded through `orchestrate` → `execute_*` → `run_sub_agent` → `cli::run`/`cloud::run` and into the main agent's tool loop: `cli` agents poll it every 250 ms and kill their process tree, `llm` agents break their loop, remaining tasks report as skipped, missions close as "stopped" (not "completed"), and a stop during planning/execution aborts the turn before the final answer streams. Plan-phase LLM calls (`plan_tasks`, `select_agents`) are checked between steps, not cancelled mid-request.
- **The LLM turn base (`src-tauri/src/turn/`, the class-organized tree).** Every chat turn runs on a `turn::LlmTurn` base that owns everything turn-scoped: identity (session id, monotonic `window_id`, the UI-minted `turn_id`), a **frozen `AppConfig` snapshot** taken at construction (the turn never re-reads live config), the cancel flag, the live progress snapshot (`TurnProgress`: accumulated content/reasoning, settled tool rows, delivered injections and per-turn usage totals), the injection inbox, the request/tool budget, turn-scoped emission (`emit_token` / `emit_done` / `emit_error`) plus a **private MCP stdio pool** (`mcp::McpSession`). Snapshot writes are funnelled through the base: the streaming transport holds a `&dyn turn::TurnProgressSink` implemented only by `LlmTurn` (`append_content` / `append_reasoning` / `rewind_attempt`), and the engine calls `record_tool_row` / `record_injection` / `record_usage` — no caller reaches into `Arc<Mutex<TurnProgress>>` (there is no public `progress_handle`). A re-attaching webview therefore rebuilds the same transcript, and `chat-retry` strips the failed attempt's tail through the same sink. The inbox closes on EVERY exit path: `emit_done` / `emit_error` close before announcing, and an `InboxGuard` in the engine covers errors/unwinds that announce nothing. The class family: `turn/mod.rs` (the base), `progress.rs` (DTOs + the sink trait), `registry.rs` (`TurnRegistry`, keyed by `window_id`), `guard.rs` (budget + tool-failure guard, ex `turn_guard.rs`), `commands.rs` (stop / inject / list / snapshot), `lifecycle.rs` (turn-end teardown: background tasks, serve processes, private MCP pool, with the registry's supersede check). The engine that RUNS on the base is `llm_complete/engine.rs`; its snapshot tool rows use the frontend's `ToolCallEntry` shape.
- **Multi-session turns** (`max_concurrent_turns`, default 4, `0` = unlimited, clamped to 16; Settings → Advanced): `chat_completion` publishes the base via `AppState::begin_turn` BEFORE any side effect — it supersedes a previous turn of the same session and enforces the limit; turns of OTHER sessions are never touched, so opening a new chat while a reply streams keeps the old turn running in the background. The registry is the History panel's running-badge source (`list_active_turns` + the `turn-state` event, emitted after turn-end cleanup so a badge never outlives its work) and `get_turn_snapshot` backs the frontend re-attach. `delete_history` refuses a running session's conversation; `set_workspace_dir` is refused while ANY turn runs.
- **Background turn driver (`src/backgroundTurns.ts`)**: handing off a streaming turn (New Chat, history switch) publishes the minted turn id plus the captured state (content, reasoning, tool rows, injections, turn stats) into a driver that keeps listening to that turn's events and persists the assistant row when the turn settles — the foreground machinery resets, and the global listeners skip driver-owned sessions, so nothing is double-processed. Switching BACK adopts the driver's live transcript; the composer's Enter / Stop route through the driver; the input draft is per session and restored on switch. On mount, still-running sessions are re-attached via `BackgroundTurnDriver.attach()` from `get_turn_snapshot` (whose tool rows now use the frontend's `ToolCallEntry` shape) + the persisted rows, so a webview reload no longer loses a background reply (a turn settling inside the re-attach gap remains the narrow window). `confirm-required` payloads carry `session_id`: a background conversation's ask surfaces as a waiting badge, and its dialog opens only while that chat is visible.
- **Turn-scoped events are routed by `session_id`.** A turn that was stopped keeps emitting for a while (a foreground tool returns, a confirmation wait ends, a task unwinds), and those events must not paint rows into whatever chat is open by then — so every turn-scoped event carries the publishing turn's session id and the frontend drops a payload whose id does not match `sessionIdRef.current`: `if (payload.session_id && payload.session_id !== sessionIdRef.current) return;`. A missing/`null` id passes, because a caller without a chat session (planner supervisor, evolution maintenance) has no transcript to leak into. Covered events: `chat-usage` (from `StreamOptions.session_id`), `chat-notice` (`budget_exhausted` / `tool_disabled`), `tool-call` and `skill-loaded` — both payloads are objects now (`{session_id, call_id, phase, ok, text}` / `{session_id, call_id, skill_name}`), they used to be plain strings — `agent-task-start` / `done` / `error` / `skipped`, `agent-task-token` / `reasoning` / `tool`, `agent-selection`, `agent-plan-start`, `agent-aggregate-done`. The tool layer threads it from `execute_tool`'s `session_id` into `emit_tool_progress(app, mission_id, session_id, text)`, whose parameter is `impl Into<Option<&str>>` so a handler that already unwrapped the id (todos/memory arms) can pass a bare `&str`; `None` serialises as `null`. The planner/mbus family already routed through `bus.session_id()` (`agent-planner-state/action`, `agent-mbus-message`), and `agent-task-state` is only an idempotent refresh trigger for the Mission panel, so its listener needs no guard. This is the same rule `chat-injected` / `background-task-state` / `timer-fired` already follow.
- **Backup**: `src-tauri/src/backup.rs` owns export / import of the application state (app menu `save-backup` / `restore-backup`, commands `app_export_backup` / `app_import_backup`). The zip holds `config.json`, `mcp_servers.json` (panel-owned servers only), `sub_agents.json`, `agents/`, `backgrounds/` (the chat photo, restored by replacing the folder), `workspace/{memory,todos,skills,scripts,mcp,deliver}/`, `workspace/skills.status`, `workspace/mcp.conf` and a `chat.db` snapshot; every `workspace/...` entry is read from and restored into the hidden `<workspace>/.data` directory of the (possibly switched) active workspace, while `agents/...` entries are merged into the app-global `agents/` definition store. There are no named in-app profiles: the zip is the only way to move a tools/agents/MCP setup between machines, and skill selection stays per-workspace state (`<workspace>/.data/skills.status`), so it rides along inside the workspace snapshot instead of a preset.
- **MCP warmup**: enabled stdio servers in `mcp_servers.json` are spawned at app startup (`mcp::start_stdio_process`). MCP stdio children start with the **active workspace** as their working directory (`current_dir` + `PWD` in `build_stdio_cmd`). `cli` sub-agents start in the **task's** working directory — `Task.cwd` is supplied per delegation by the planner or `call_subagent` (never by the agent definition), sandbox-checked by `resolve_task_cwd` and created when missing; `cli::run` applies it via `current_dir` + `PWD`. A `workspace_dir` switch stops running stdio children so the next tool call respawns them in the new workspace. Sub-agent tasks do **not** use this pool, and neither do chat turns: with `enable_mcp`, each task gets its own `mcp::McpSession` (historically `AgentMcpSession`, kept as a type alias), and every `turn::LlmTurn` base carries its own private pool that `build_turn_tools` / `run_tool_call` spawn into (`get_server_tools_in` / `invoke_mcp_tool_in`) and turn-end cleanup kills.
- **Self-built MCP servers** (`mcp_self`, self-evolution mode only): the assistant writes a stdio server script under `<workspace>/.data/mcp/<slug>/` and the backend registers it in the **workspace roster** `<workspace>/.data/mcp.conf` (YAML, `version` + `servers[]`, `source: "self-evolution"`, `definition_path` = workspace-relative script, `command` = an interpreter the backend picked from the whitelist `python` / `node` / `shell` — never a model-supplied command, `args` = the relative script path, which resolves because every stdio child starts in the workspace root, so the entry still works after a backup restore). Manually created servers stay in the app-data `mcp_servers.json`; `mcp::load_effective_servers` merges both rosters and is what the chat, the panel, the warmup and the sub-agents read (the app-data entry wins on an id clash). The split keeps the assistant out of the user's config and makes a self-built server follow its workspace — including the backup's workspace snapshot. The tool is the writer because turning code into a running server is more than a file write (whitelisted interpreter, `.bak.<n>` copy, roster upsert, start + `tools/list`, one confirmation, revision bump); `file_actions` may still hand-edit `mcp.conf`, and `restart` picks that up. Actions: `list` / `write` (create or update with a `.bak.<n>` copy, register disabled, then optionally start and run `tools/list`) / `enable` / `disable` / `test` / `restart` / `logs` / `remove`. `write`, `enable` and `remove` ask the user once (`user_software`); a start that fails `tools/list` leaves the entry **disabled** (an enabled server that cannot list would stall every later request); the tool only ever rewrites `mcp.conf`, and the MCP panel edits or deletes a self-built row through the same file (`save_mcp_server` / `delete_mcp_server` route by provenance instead of forking a copy into app data). Every mutation bumps `AppState::mcp_revision`, and `run_chat_turn` compares it at the top of each tool round and rebuilds the whole payload (`build_turn_tools`), so a server created mid-turn is callable in the *same* turn. Sub-agents drop the tool (`agents::drop_mcp_self`): they would race on the registry, their `AgentMcpSession` only loads servers at task start, and the confirmation dialog would block a mission.
- **Delay timers** (`src-tauri/src/tools/timer.rs`): the `timer` tool (`timer_set` / `timer_list` / `timer_cancel`, toggled in the Tools panel) lets the assistant wait for slow work instead of polling — the LLM arms a delay and ends its turn; when it fires the backend emits `timer-fired` and the frontend injects the timer's `message` into the same session as a new user turn (`timer-state` keeps the timer bar above the input box in sync). The queued resume prompt carries the timer's `session_id`, and the auto-send consumes it only while that chat is the active one — a timer firing after a session switch waits there instead of posting its text into another conversation. Timers are mirrored to `<workspace>/.data/timers.json` and re-armed at startup, where overdue ones fire immediately. The mirror is workspace-scoped because a timer resumes a session id that only exists in *that* workspace's database: a workspace switch flushes the current set back to the old file and arms the new one (`timer::rebase_workspace`), and a legacy `<app_data>/timers.json` is migrated once at startup. Sub-agents never receive the timer tools (`agents.rs` filters them out). A pending timer also **suspends the todo goal loop**: before nudging the model about unfinished todo items, `run_chat_turn` asks `TimerRegistry::count_for_session`, so a turn that armed a timer ends instead of being forced to keep working; a wait the app cannot schedule is declared by the model with `[WAIT_EVT: what it is waiting for]` in its final answer, which the goal loop treats the same way (the marker is stripped from the transcript by `stripControlMarkers` in `src/App.tsx` and by `strip_control_markers` before memory recording). The same file hosts the cross-platform **sleep lock** (`SleepLock`, ref-counted RAII): it is held while any timer is pending **and** for the whole duration of a chat turn (`chat_completion` wrapper in `llm_complete.rs`, released after turn-end serve cleanup), preventing idle system suspend via `SetThreadExecutionState` (Windows), an IOPM assertion (macOS) or a D-Bus inhibit (Linux); `sleep-lock` events + `get_sleep_lock_state` drive the badge above the input box.
- **Background tool tasks** (`src-tauri/src/tools/background.rs`): `run_cmd`, `run_shell` (`run_type: "direct"`), `file_actions` action `search`, MCP tools and `call_subagent` accept `run_in_background: true` (the flag is only advertised while `config.background_tools` is on — Settings → Run → “Background execution”; sub-agents never get it). The call returns a placeholder `tool` result carrying a `bg-…` id immediately, so the model keeps working; the real output is injected at the next request boundary as a `user` message (`[BACKGROUND TASK RESULT …]`) and announced via `chat-injected` with `kind: "background_result"`, so it lands on the assistant row's `injections` and is replayed like a mid-turn injection (tool results themselves are never persisted). The announcement carries the turn's `session_id`, and once the turn is cancelled the loop breaks before the drains — Stop during a foreground tool ends the turn with finished-but-undelivered results left undelivered, so a dead turn can never announce its delivery into a chat the user opened in the meantime. The turn is **held open** if the model tries to finish while a task is unsettled (max 3 rounds × 120 s, then the remainder is cancelled). `background_task` (`list`/`wait`/`get`/`cancel`) is the model-side control tool; `list_background_tasks` / `cancel_background_task` back the UI. Tasks are turn-scoped: Stop calls `cancel_session` (running → `cancelled`, entries kept until the turn unwinds) and `end_turn_cleanup` calls `shutdown_session` (set every cancel flag, drop the entries); each runner then kills its process tree, and `process_guard` covers app exit. Both methods **return** the terminal snapshots, because a torn-down runner's `finish()` finds no entry left to report into — teardown is the only thing that can tell the UI a row is gone: every caller emits one `background-task-state` per snapshot plus `background-waiting` with `pending: 0` before the turn returns, and the frontend drops any row still marked `running` once `streaming` ends (a task cannot outlive its turn), so the panel and the transcript row's cancel button can never outlive the task. Background `run_cmd`/`run_shell` run through `process::run_command_timed` (cancellable, tree-killing, 600 s default), a background `file_actions` search polls `SearchOptions.abort` inside the parallel walker, and a background **stdio MCP call gets its own short-lived process** (`mcp::invoke_mcp_tool_isolated`) because the shared pool serialises on `mcp_children` and caps a round trip at 10 s — using it would stall the next request's `tools/list`. Confirmation dialogs are serialised by `AppState.tool_confirm_lock`, and a cancelled task stops waiting for one.
- **Model metadata** (`src-tauri/src/model_metadata.rs`, `src-tauri/src/utils/model-catalog/`): the catalogue is **built in CI, never in the app**. The workspace-member crate `model-catalog` owns the whole merge — models.dev (`limit.context` / `limit.output` plus capability booleans, one entry per provider, ranked so the vendor's own entry beats the resellers), OpenRouter (`context_length`, `max_completion_tokens`, `supported_parameters`) and basellm/llm-metadata (the only one that ships `tags`, which still reach the merge because flags are OR-ed; its rounded size tags only fill a window nobody else reported) — into one entry per normalised model name: `merge_catalogs` keeps the highest-priority name, a lower-priority source only fills the fields that are still empty, flags are OR-ed and `sources` records the provenance; basellm's `tags` are expanded into capability flags. Its bin `build-catalog` runs as a **`pages.yml` deploy step** (weekly cron + every docs push): it writes `docs/site/model_metadata.json` (gitignored, like `architecture.html`) and gates the deploy through `ensure_usable` (> 500 entries, context windows known for > 75%) — a failed build aborts the deploy instead of publishing a stub. The app only *fetches* the finished file: `fetch_model_metadata` downloads `https://xlbbb-cn.github.io/ai-chat/model_metadata.json` (~1.2 MB instead of the ~7 MB of raw feeds) at most weekly (`CATALOG_TTL_SECS`, measured on the file's CI `updated_at` stamp — the data's age, not the local download time): memory → file → Pages. The fetch is validated with the same `ensure_usable` gate and written atomically to `<app_data>/model_metadata.json` as the offline fallback; a failed fetch serves the stale file with a `WARN` in `app.log`, and the command only errors when Pages is unreachable *and* no file exists. `src/utils/modelMetadata.ts` fuzzy-matches remote model ids against it (vendor prefixes, date stamps, modality guards); "Fetch Models From API" stores the matches per model in `config.model_metadata` and uses the catalogue context window when the provider reports none. The chat toolbar renders those flags as icons inside the model picker's options, plus a thinking-depth selector for reasoning-capable models (`config.model_reasoning_effort` → `reasoning_effort`, resolved by `llm_complete::resolve_reasoning_effort` and applied to chat + sub-agent requests). The attachment picker follows the same flags: text is always accepted (inlined into the prompt), images need `Vision` (`image_url` parts), `wav`/`mp3` need `Audio` (`input_audio` parts), and a non-image binary is not accepted at all — the app never emits a `file` part, so the `@` popup hides it (see the `file`-part gotcha under Common gotchas). A PDF needs none of them, because a PDF mention converts to Markdown text (next bullet) and every model can read it.
- **`@` file mentions** (`src-tauri/src/workspace_files.rs`, `src-tauri/src/pdf_mentions.rs`, `src/fileMention.ts`): the grammar is `@<workspace path>[#<start>[-<end>]]`, plus `@@<name>` for a file in the workspace tmp folder (`.data/tmp`, short because that folder is scratch), and the token stays in the message body, so the model sees which file was quoted. A text file is sliced by *line* (`read_workspace_file_range`), an image/audio file is attached whole, and a **PDF** counts *pages*: `convert_pdf_mention` renders `#2` / `#2-5` / `#2-` with the in-process `pdf2md-rs` library (a workspace member — a library, not a CLI: `src-tauri/src/utils/pdf2md-rs/README.md`), caches the Markdown at `<workspace>/.data/tmp/pdf/<stem>-<digest>.md` (digest over path + range + file size + `pdf2md-rs` version, so the same mention reuses one file while a converter upgrade invalidates it) and returns it; `fileMention.ts` then pushes it as a `kind: "text"` attachment whose `text_content` `partsForContent` (`src/messageParts.ts`) inlines as a `<details>` text part (the fence tag comes from `fenceLanguage`, so `kk.pdf#2` is fenced as `markdown`, not `pdf#2`). Consequences: no `supports_files` is involved (the popup filters with `supportsMentionName`, not `supportsAttachmentKind`), the Markdown's provenance comment names the cache file so a tool can read the full conversion later, a range-less mention converts at most 60 pages and the prompt keeps at most 60k characters while the cache file always keeps the full text, and failures (encrypted, scanned, page past the end) become per-mention problems that never block the message. Conversion runs in `spawn_blocking`; page range enforcement lives in `pdf2md-rs`'s `Options::page_range`. Progress is a `tauri::ipc::Channel<PdfMentionProgress>` fed from the library's own ticks (deduped on stage + page + total, `percent` monotonic), which the composer renders as a muted strip above the input row (see `docs/DESIGN.md`) and clears in a `finally`; the persisted copy of the message goes through `compactAttachmentsForDb`, which drops `text_content` from any attachment that has a `path` — the Markdown is already in the message `content`, so a stored PDF mention keeps one string plus the cache path, while live attachments keep their text and sending never depends on a cache file that may since have been pruned.
- **Update check** (`src-tauri/src/update.rs`): `check_update` reads the releases of `xlbbb-cn/ai-chat` from the GitHub API, keeps the highest semver (drafts are always skipped, pre-releases behind `include_prerelease_updates`), ranks the attached bundles for the current OS/arch and flags the preferred one as `recommended`. `download_update` streams into the downloads folder while emitting `update-download-progress`; `open_update_file` / `reveal_update_file` / `open_release_page` hand off to the OS (URLs are restricted to this repository). UI: startup probe + banner in `App.tsx`, dialog in `components/UpdatePanel.tsx`, toggles under Settings → About & Updates.
- **API layer**: `src/api.ts` wraps `invoke` + `listen`. `src/types.ts` is the canonical TS shape for `AppConfig`, `Skill`, `SkillsStatus`, `McpServer`, `SubAgent`, `AgentOrchestration`, `AgentMissionSnapshot`, `ModelMetadata`.
- **PDF export writes a file** (`src/utils/pdfExport.ts`, `src/utils/printDocument.ts`, `src-tauri/src/html_pdf.rs`): a reply's export button and the Markdown editor's "Export PDF" share one route — `exportHtmlAsPdf` opens the save dialog, then `app_export_pdf` prints the document with a headless Chromium. `printDocument` is imported *inside* `exportHtmlAsPdf` (after the dialog): its shell carries the KaTeX stylesheet as text plus ~20 font URLs, which no launch needs, so it must not return to the boot graph — the editor's `MARKDOWN_PRINT_CSS` is loaded the same way. What is exported is rendered HTML (a clone of the reply with its figure cards frozen, or the editor's preview), so `buildPrintDocumentHtml({ standalone: true })` makes it self-contained for another process: the KaTeX CSS with its woff2 faces fetched from the bundled assets as data URLs, and system faces instead of the RazerF5 web font, because the file is opened from a temp directory where the app's asset URLs mean nothing. Only the no-engine fallback — `NO_PDF_ENGINE` — goes through `printHtmlDocument`, the hidden-iframe dialog printer; the shared shell (light palette, A4 page box, prose rules) plus each caller's `extraCss` keeps both routes looking the same. Titlebar `⋯` → "Markdown edit…" opens a `.md` in a two-column overlay (`app_open_markdown` → `markdown-edit-open`). Success is confirmed by revealing the file: `ChatNotice` is reserved for warnings and errors.
- **Theming**: three independent dimensions in `AppConfig` — `theme` (`auto` / `light` / `dark`), `palette` (`default` / `cream` / `macaron`; a legacy `sakura` value is migrated to `default`) and `glass_effect` (`off` / `subtle` / `standard` / `strong`, the frosted-glass level; missing means `standard`). `applyTheme()` writes the first two to `<html>` as `data-theme` / `data-palette` and `applyGlassEffect()` writes the third as `data-glass`; the token blocks in `src/App.css` do the rest (`--glass-blur`, `--glass-blur-scrim`, `--glass-saturate`, `--glass-backdrop`; `off` swaps the fill to `--c-surface` because a 0px blur over a translucent bar reads as a hole). Settings → Appearance previews all three immediately and persists them on "Save Changes". All three fields live in the Rust `AppConfig` too, so they survive a config write.
- **Chat background photo** (`src-tauri/src/background.rs`): Settings → Appearance → Chat background copies the picked photo into `<app_data>/backgrounds/chat-background-<id>.<ext>` and stores only that app-data-relative path in `AppConfig.chat_background` (commands `set_chat_background` / `clear_chat_background` / `read_chat_background` in `ipc/app.rs`). The "Use default wallpaper" button installs the image embedded at build time from `docs/wallpaper.png` under the stable name `chat-background-default.png` (`use_default_chat_background`): no picker, no orphan on repeated clicks, and the same backup path as a picked photo. The choice is applied immediately, not staged behind "Save Changes"; `backgrounds/` is included in backups and follows MSIX's app-data redirect. `html[data-chat-bg] .messages` paints a fixed `--chat-bg-scrim` over `--chat-bg-photo` behind the messages only — the toolbar and composer keep their fills, and the photo stays put while the transcript scrolls. The frontend converts the IPC `data:` URL to a Blob URL and keeps the generation guard in `src/App.tsx`; never put the data URL itself in a CSS custom property.
- **UI language** (`src-tauri/src/system_locale.rs`): `config.language` (`en` / `zh-CN` / `zh-TW`) is a *decision*, not a default. When it is missing or carries anything else, `setup` adopts the OS user-interface language once and persists it in the same single startup write that seeds `workspace_history` — Windows `GetUserDefaultUILanguage` → `LCIDToLocaleName`, macOS `defaults read -g AppleLocale`, Linux `LC_ALL` / `LC_MESSAGES` / `LANG`. Chinese with a `Hant` / Taiwan / Hong Kong / Macau marker is `zh-TW`, any other Chinese tag `zh-CN`, everything else `en` — the rule in `detectSystemLocale()` (`src/i18n/index.tsx`), which stays the fallback for the first paint before the config arrives. A pick in Settings or an imported backup is never overwritten (only a missing/unknown value is claimed), and a shadow window claims only its own config copy.
- **Workspace state** (`src-tauri/src/workspace.rs`): single source of truth for the per-workspace layout. Everything workspace-scoped (SQLite database, memory, todos, skills, skill status, pending timers) lives in the hidden `<workspace>/.data` directory, so switching `workspace_dir` in config swaps the whole state — `apply_config` closes and re-opens the SQLite connection at `<workspace>/.data/chat.db` and re-points the timer mirror when the workspace changes.
- **Persistence**: SQLite (`<workspace>/.data/chat.db`) for history, API request monitor, interaction log, and agent missions. Dated `app-<date>.log` files stay in the app data dir (startup sweeps them by `log_retention_days`; `0` keeps them forever).
- **Multiple windows** (`src-tauri/src/instance.rs`): `single_instance` decides whether a second launch focuses the running window (plugin) or starts a second process. The first process takes the **primary** role via `<app_data>/shadow/primary.lock` (pid liveness; a crashed run's lock is reclaimed) and keeps using the shared `config.json` unchanged. Every later process is a **shadow**: it copies the current config into `<app_data>/shadow/config-<timestamp>-<id>/config.json` — same settings, but `workspace_dir` is rewritten to that directory's own `workspace/` — writes only that copy and deletes it on exit. Clearing `workspace_dir` in a shadow falls back to its own fork (never the shared default workspace), so clearing the workspace cannot put two windows on one database. `collect_garbage` sweeps copies left behind by killed windows at startup, `Instance::write_config` serialises writers of the shared file with `shadow/main-config.lock`, and a shadow merges just its `workspace_history` back into the shared config on exit (its own temporary workspace is filtered out). `get_instance_info` tells the UI which window it is (the titlebar switcher shows a shadow window's note). The pre-Tauri path helper (`app_data_dir_before_tauri`) must stay `dirs::data_dir()/<identifier>` — Tauri's `app_data_dir()` uses the Roaming directory on Windows, not `%LOCALAPPDATA%`; `setup` re-claims if the two ever disagree.

## Plugin system (LLM → tool → message bus → instance × N)

`src-tauri/src/plugins/` adds workspace plugins as a tool-visible extension point. The chain is fixed: the model calls a tool, the tool publishes on the **plugin message bus**, the bus routes it to one of **N long-lived instances** of that plugin, and the reply comes back through the same bus id.

- **On disk**: `<workspace>/.data/plugins/<id>/plugin.json` plus an entry script. Manifest: `name`, `version`, `description`, `runtime` (`auto` / `python` / `node` / `shell` / `exec`), `entry` (relative to the folder), `command` + `args` (escape hatch for a compiled binary or a vendored interpreter), `env`, `instances` (default 1, clamped to 8), `enabled`, `auto_start`, `call_timeout_ms`, `subscriptions`, `tools[]`. Workspace-scoped exactly like skills / scripts / the self-built MCP roster; the `id` **is** the folder name (a mismatching `id` is rejected) and a broken manifest becomes an entry in `PluginDiagnostics.issues` instead of failing the whole load.
- **Protocol is line-delimited JSON on stdin/stdout** (no JSON-RPC framing — a plugin is an app extension, not an MCP server). Host → instance: `hello`, `request` (`id`, `topic`, `tool`, `args`), `event`, `ping`, `shutdown`. Instance → host: `ready`, `reply` (`id`, `ok`, `result` / `error`), `event`, `log`, `pong`. The child has 15 s to answer `hello` with `ready`; a non-JSON stdout line is logged and ignored (a plugin that `print`s must not die), and stderr is drained into the plugin's own log ring.
- **Two tool surfaces, one bus.** The built-in `plugin` tool (`list` / `call` / `publish` / `events` / `status` / `logs` / `start` / `stop` / `reload`) is added by `tools::get_all_tools` when `plugin` is selected; every manifest-declared tool is also advertised as a first-class `plugin_<id>_<tool>` function, appended by `build_turn_tools` and sorted by function name (the tool list sits in the cached request prefix). Both routes end in `PluginHost::call`, and the dispatcher resolves a dynamic name against the workspace manifests in `plugins::tool::handle` — a plugin's own tools need no second dispatcher.
- **The bus** (`plugins/bus.rs`) mints request ids, correlates replies with a `oneshot`, owns MQTT-style topics (`+` one level, terminal `#` — the same grammar as the mission bus) and keeps a bounded audit ring emitted as `plugin-bus`. A caller that gave up `expire`s its slot, so a late reply is recorded as a discarded reply instead of waking nobody.
- **Instances** (`plugins/instance.rs`) are spawned from an explicit interpreter + entry path — never a shell string — with `PLUGIN_ID` / `PLUGIN_INSTANCE` / `PLUGIN_DIR` / `PLUGIN_WORKSPACE` in the environment and the plugin folder as the working directory (a plugin is self-contained; the workspace reaches it through the env + the `hello` line). Children join the `process_guard` job object / process group, so app exit kills the tree; `instances` is what buys parallel capacity and failover. Starting is **on demand**: `ensure_started` spawns the missing ones, prunes dead ones and retries the whole pool on the next call.
- **Scheduling**: least in-flight instance wins, round-robin breaks ties, and a request that cannot be written fails over once to a sibling instance before the tool answers with an error.
- **Config + mid-turn rebuild**: `AppConfig.plugins_enabled` (default **off**) forces `plugin` into `effective_tools()` the same way self-evolution forces `file_actions` / `memory`; `plugins.revision()` joins `mcp_revision` in the turn loop's rebuild condition, so a manifest written or reloaded mid-turn is callable in the *same* turn.
- **Packages** (`plugins/package.rs`) move one plugin between workspaces. `export_plugin_package` writes a `.zip` with `plugin.json` at the archive root, skipping hidden files, `*.bak.*`, `node_modules/` and the cache directories; `config.yaml` travels only when the plugin declares a schema, with every `secret` field removed first — and left behind entirely, with the parser's message in `settings_note`, when the schema does not parse, so an export never leaks a value it could not prove safe and never fails over settings. `import_plugin_package` accepts that shape or a single wrapper folder, derives the id from the manifest (falling back to the folder or the file name), unpacks into `<workspace>/.data/plugin-backups/.staging-<uuid>/` — never into `plugins/`, where a half-written folder would load as a broken plugin — validates the manifest plus the declared `entry` / `config_schema`, retires the instance the package replaces (`package_id` reads the id before anything is written, because Windows refuses to rename a folder a process still has open), moves the installed copy to `.data/plugin-backups/<id>-<ms>/` and renames staging into place. The loader has the last word: a manifest it refuses rolls the folder back and reports the issue. `safe_join` is the zip-slip guard, `MAX_PACKAGE_FILES` / `MAX_PACKAGE_BYTES` the zip-bomb one; the manifest is written once from the text already read, so a package never holds two `plugin.json` entries.
- **No confirmation prompt.** A plugin is workspace content the user installed (the same trust level as a skill's scripts) and it never receives a shell; `run_cmd` / `run_shell` remain the risk-scored path.
- **Lifecycle**: a workspace switch runs `PluginHost::stop_all()` (instances are rooted in the old tree), `process_guard` kills whatever is left at app exit. IPC lives in `ipc/plugins.rs` (`list_plugins`, `get_plugin_diagnostics`, `reload_plugins`, `start_plugin`, `stop_plugin`, `save_plugin_manifest`, `delete_plugin`, `get_plugin_logs`, `clear_plugin_logs`, `get_plugin_bus_records`, `get_plugin_events`, `export_plugin_package`, `import_plugin_package`); events are `plugin-state`, `plugin-bus`, `plugin-log` in `events.rs`. `.data/plugins/echo/` is the reference plugin the tests and the docs point at.

### Services, settings and the manager window

- **Two ways onto the bus.** `transport` in `plugin.json` is `spawn` (default — the app starts the child and speaks stdio), `service` (the Rust/Node/Python service runs under its own supervisor and dials the bus), or `both`. A service dials `127.0.0.1:<port>` (`link::LinkEndpoint`) and opens with `{"type":"hello","plugin":"<id>","token":"…"}`; the token is the workspace secret in `.data/plugins/.link-token`, and the listener is bound lazily on first use. One connection = one instance, so a service scales itself to N instances by connecting N times — the manifest's `instances` only governs the spawned pool. `InstanceOwner::External` marks an attached instance: shutting it down drops the socket and never kills a process the app did not start.
- **Settings pages.** A plugin renders its settings one of two ways: `config.schema.yaml` next to the manifest (declarative, drawn as a generic form — text/number/integer/boolean/enum/path/secret/json, `min`/`max`/`max_length`/`options`/`advanced`/`reveal_when`, grouped in `sections`; `key` is identity on both levels and a section that omits it borrows its title's slug, while `label` / `help` read as `title` / `description` because schemas are hand-written), or `config_page` pointing at its own HTML when a form is not enough. Either way the schema owns values and validation. Values live in `config.yaml` in the plugin folder (a folder stays self-contained and copyable); `FieldKind::Secret` values are stored but read back masked (`has_value`), and a save echoes the mask to mean "unchanged". A save validates per field, writes, then hot-pushes `{"type":"config","config":{…}}` to every ready instance — no restart. A spawned or attached service also learns its settings in `welcome.config` / the `hello` handshake, and may simply read `config.yaml` from its own folder (`PLUGIN_DIR`).
- **Manager window.** Settings → **Plugins** opens a *separate* webview (`openPluginManager()` → the sync command `open_plugin_manager`, label `plugin-manager`, entry `plugin-manager.html` → `src/plugin-manager.tsx`, third Rollup input after `index` / `notify`, its own `capabilities/plugin-manager.json` with `core:default` plus `dialog:allow-open` / `dialog:allow-save` for the package pickers (`notify.json` stays `core:default` only); window creation blocks on WebView2, hence the sync command off the async workers). `PluginManagerPanel` draws the plugin list, live instance table, the generic settings form (schema mode), the log tail and the bus audit strip; it reads the theme/palette/glass from `config` before its first frame and seeds `localStorage["ai-chat.locale"]` from `config.language`, so both windows agree. It talks only to `ipc/plugins_config.rs`: `get_plugin_manager_state` (plugins + instances + endpoint + issues + revision), `get_plugin_config`, `save_plugin_config` (per-field `FieldError` back), `reset_plugin_config`, and `export_plugin_package` / `import_plugin_package` (`plugins/package.rs`) that move one plugin folder in and out as a `.zip`; `plugin-state` / `plugin-bus` keep it live, `plugin-manager-select` preselects a plugin. The model never edits settings — there is deliberately no `plugin` tool action for writing config; a prompt-injected turn must not be able to retarget a plugin's webhook.

### Sub-agent definitions (`llm`)

`sub_agents.json` is **configuration only**. For an `llm` agent it stores the runtime knobs (`enabled`, `model`, token limits, `allowed_tools`, `allowed_skills`, `max_iterations`) plus a `file` reference; `cli` / `cloud` agents keep their full definition there. An `llm` agent's `name`, `description`, `emoji`, `color` and system prompt live in its markdown file (YAML frontmatter + body), mirroring the skill format. `src-tauri/src/agents/files.rs` owns parsing, serialization (unknown frontmatter keys are preserved), scanning, path safety and write/delete.

- Discovery runs **only from the panel's Refresh** (`refresh_agent_index`): it scans the `agents/` tree for `.md` files (`.bak.*` and hidden entries skipped) and **replaces** `agents/index.yaml` with the list. Opening the panel reads that manifest instead of scanning, so a file added after the last refresh stays invisible until the next one. A discovered file with no config entry is returned as a disabled **virtual** agent (`configured: false`) and is never written to `sub_agents.json` until the user enables or edits it.
- `agents/index.yaml` is a derived manifest (`version`, `refreshed_at`, `agents[]` with `id`, `file`, `name`, `description`, `emoji`, `color`, optional `error`). The markdown files stay authoritative for the prompt; the manifest decides which files are listed. Delete it (or press Refresh) to rebuild.
- Only `agents/custom/**` may be deleted from the panel. Library files (`engineering/…`, other imported collections) are read-only there: disable the agent instead. A panel save rewrites a file only when its parsed definition actually changed, and keeps a `.bak.<n>` copy before overwriting.
- `enable_mcp` is runtime config for `llm` agents (default off; panel toggle under Capabilities; ignored and never persisted for `cli` / `cloud`). When on, the agent receives the tools of every **enabled** MCP server in `mcp_servers.json`, using the same `mcp::adapt_tool_for_llm` adapter as the main agent — identical `mcp_<server-hash>_<name>` function names and `[MCP: server]` descriptions.
- **Shared sub-agent memory (default on).** Every `llm` sub-agent starts with the `memory` tool (v5 config migration adds it once; the panel offers it and the user can uncheck it per agent). The scopes are shared: `session` is keyed by the main chat's `session_id` (main agent + every sibling task), `user` / `repo` are workspace files under `<workspace>/.data/memory`, and `evolution` exists in self-evolution mode. The sub-agent static prompt tells it to search before starting, add one concise conclusion before finishing, use a task-specific key prefix for mission notes, never store credentials and never run `consolidate`. `cli` / `cloud` agents cannot call app tools, so they do not receive a memory digest.
- **Working directory is per task, never per agent.** `Task.cwd` (workspace-relative; `None` = workspace root) is produced by the planner (`plan_tasks` sees the workspace root and the conversation) or passed by the main agent as the `cwd` argument of `call_subagent`. `run_sub_agent` resolves it once with `resolve_task_cwd`: `tools::resolve_safe_path` enforces the workspace sandbox and a missing directory is created. A `cli` agent starts its process there (`current_dir` + `PWD`), a `cloud` agent receives it through the `{cwd}` body placeholder, and an `llm` agent gets it in its static system prompt while `run_cmd` / `run_shell` / `serve` start there. `file_actions`, memory and todos stay rooted at the workspace (`.data` must not move). `CliAgentSettings` deliberately has no `cwd` field.
- **Conversation summary in every task prompt** — a sub-agent receives only `description` + `context` from its delegator, so the compact transcript of the real conversation (`build_conversation_summary` over `db::query_recent_session_messages`: 12 entries, 2 000 bytes each, 12 000 bytes total) is appended to its static system prompt as `MAIN CONVERSATION`. It is the information a task used to request through the retired `ask_main_agent` helper, at the cost of one DB read instead of a second model run.
- Each **task** and each chat turn owns an `mcp::McpSession` with its own stdio process pool. Agent and turn processes never enter `AppState.mcp_children` (the panel's warmup pool), so the main chat, parallel tasks and parallel sessions are all isolated. SSE / HTTP / Streamable HTTP servers have no long-lived process.
- `run_sub_agent_inner` creates the session, runs `run_llm_agent_body`, and calls `McpSession::shutdown` on every return path (success, error, max iterations, Stop); `Drop` kills anything left on unwind. Every child is also tracked by `process_guard`, so app exit kills it. MCP logs from an agent are prefixed `[agent:<name>]`.
- MCP tools must be advertised before the agent's first request (`tools/list`), so enabling MCP spawns every enabled stdio server at task start. A server whose `tools/list` fails is logged and skipped; it does not block the task.
- Legacy inline `llm` prompts (old `sub_agents.json` bodies) are migrated when configured agents are resolved and during Refresh. `load_agents_config` reads the raw config; `load_configured_agents` resolves only the files referenced by configured entries (no directory scan) and is what orchestration/chat use; `load_sub_agent_list` adds the manifest's virtual agents for the panel.

Everything that belongs to the *current workspace* lives in a hidden `.data` directory inside it (see `src-tauri/src/workspace.rs`):

```text
<workspace>/.data/
  chat.db                  SQLite: history / API monitor / interaction log / agent missions
  memory/{user,repo,evolution}/…  memory tool file backend (evolution has front matter + archive/)
  todos/<session>/…        todos tool
  skills/<name>/skill.md   the only skills root
  scripts/<name>.{ps1,sh,py,js,…}  run_cmd script library (created at startup, on the child PATH)
  scripts/.index.json      app-managed use stats + approved script content hashes
  tmp/                     scratch: composer pastes + PDF mention cache
  deliver/<session-id>/<batch-id>/  sub-agent deliverables (shared/ + one dir per task)
  mcp/<slug>/server.{py,js,sh,ps1}  self-built MCP servers (evolution mode, `mcp_self`)
  mcp.conf                 roster of those servers (YAML), merged with the app-data
                           mcp_servers.json into the effective server list
  skills.status            per-workspace skill enablement + metadata (JSON)
```

- `.data` is hidden (Windows: file-system hidden attribute) but it is **part of the workspace**: `file_actions` lists, searches, reads and writes it like any other folder (skills, scripts, memory, todos, skill status). The one exception is the SQLite database — see the path policy below.
- **Self-evolution mode** (`config.self_evolution_mode`):
  - **Skill edits are restricted to `<workspace>/.data/skills`** — the one and only skills root, produced by `skills::self_evolution_skill_root` (a single `Option<PathBuf>`, never a list: a second skills location cannot be introduced). `tools/paths.rs` refuses to delete the skills root itself, and only that folder gets the automatic `.bak.<n>` backups.
  - **The main chat and the sub-agents both get that root.** `llm_complete.rs` / `agents.rs` pass it to `tools::execute_tool` as `protected_skill_root`; without it every skill write is rejected.
  - **`file_actions` and `memory` are forced on.** `AppConfig::effective_tools()` adds them whenever the mode is on, and `apply_config` / the startup load persist them — so the Tools panel, a backup restore or a hand-edited `config.json` cannot switch them off. The Tools panel shows them locked.
  - **A dedicated `evolution` memory scope** (`tools/memory.rs`, `EVOLUTION_SCOPE`) holds verified, reusable facts (default interpreter / runtime environment, the correct way to operate a tool, frequently used file locations). It is file-backed at `<workspace>/.data/memory/evolution`, only exists while the mode is on, and receives the automatic conclusion recording. **Nothing is preloaded as a block**: a `VERIFIED FACTS` block used to dominate the first request's prefill, so the prompt only *points* at the scope ("search it when a problem needs earlier experience") and the model queries it on demand (`memory list` / `get` / `search`). What does ride along is one tiny hint: `memory::build_memory_hint` keyword-matches the newest user message (`tokenize`: jieba dictionary segmentation + Snowball English stemming, the 32 longest kept) against the evolution entries and the `user`/`repo` notes, keeps the hits on a title > tag > body priority (a key or title hit is a hit on its own, a tag hit outranks prose, a body-only match needs two keywords), drops `confidence <= 2` and the maintenance note, ranks by `confidence -> hit weight -> importance -> line density -> key`, and renders one single line of at most `MEMORY_HINT_BUDGET_CHARS` (200) characters holding just the matched **titles** (a title is the pointer, the body is fetched on demand), which `build_initial_messages` prefixes to that user message only. Request-only and read-only: it never enters the stored history (so it cannot accumulate or show up in the transcript), never bumps `uses` / `evidence` / `confidence`, and `config.memory_hint` (Settings -> Advanced, on by default) turns it off. Sub-agents do not get it. Entries carry YAML front matter (`key`, `title`, `kind`, `tags`, `importance`, `confidence`, `evidence`, `uses`, `pinned`, `source`, timestamps) and are ranked by `importance + confidence + ln(evidence) + ln(uses) + recency` for `list` and the panel. `search` instead matches **tokens** (the same `tokenize` the hint uses, so the two paths cannot drift), orders by TF-IDF relevance (field-weighted `title`/`key` > `tags` > `body`, plus a phrase bonus when consecutive query words appear in the name), then phrase / tier / coverage, then that experience score, and prints the tier, the phrase flag and the coverage on every line. `uses` only grows for a credible hit (a name/tag hit or two body keywords) — a stray common word that merely appears in the prose cannot rank an entry up over time. A query with no token hit falls back to a literal `run_integrated_search` sweep, so an archived file or a phrase that does not tokenize is still findable. `render_ranked_entries` still renders the three tiers (full distilled fact → title-only → a `+ N lower-ranked` pointer) inside `EVOLUTION_CONTEXT_BUDGET_CHARS`; that budget now only drives the panel's top-tier marking and the consolidation planner, not a request. Re-adding a key is an upsert (`evidence += 1`), similar titles merge into the existing entry, and identical bodies are collapsed at read time. Legacy files (`# key` + free text) are upgraded lazily by `persist_evolution_migration`; the prompt builder never writes. Automatic conclusion recording distils (first sentence + up to three bullets, ≤320 chars) instead of dumping the answer, and caps `source: auto` entries.
  - **Memory consolidation** (`memory` action `consolidate`, only in this mode): `phase: plan` clusters the hot entries by tags/title tokens/kind and reports the blocks that occupy ≥20% of the prompt budget (≥4 entries); the model then writes one skill whose front matter `source-memory` lists every archived key and calls `phase: apply` with the full `skill_md`. `apply` is a single transaction in a fixed order — validate name → parse skill → verify coverage → write the skill (`.bak.<n>`) → enable it in `skills.status` → move the entries to `<workspace>/.data/memory/evolution/archive/<skill>/`. The archive is excluded from injection/`list`/`search`, while `memory get` still resolves it and `phase: restore` moves entries back. A consolidated skill is enabled automatically so its one-line description reaches the prompt; its body is loaded on demand via `use_skill`, and `allowed-commands` is deliberately left empty (enabled skills merge their command allowlist globally). The read-only panel (`components/MemoryPanel.tsx`) is opened from Settings → Debug, directly below the agent missions monitor (the row only appears while the mode is on); it renders the same ranking and marks which entries fit the current budget.
  - **Memory trust calibration** (`memory` `add` with `confidence` / `conflict` / `note`): a retrieved fact is a claim, not the truth, and the entry is now calibrated the moment reality answers back. A plain re-add is one confirmation (`evidence + 1`, `confidence + 1` capped at 5); `add` on the same key with `conflict: true` (plus the corrected `content` when known and a one-line `note`) rewrites that entry in the same call — `confidence` drops straight to 1, `contradictions` grows, `last_conflict` / `last_conflict_at` record the reason, and `evidence` stays untouched because a conflict is not a confirmation. Fast to distrust, slow to trust on purpose. An explicit `confidence` is the only field that overwrites (it must be able to fall; `importance` keeps its `max`), a conflict on an unknown key is refused rather than inventing a low-trust fact, and `evolution-maintenance-progress` has no trust to calibrate. Low trust is surfaced instead of hidden: `memory get` / `search` append a warning for entries at `confidence <= 2` and list the contradicted matches, `list` and `EvolutionMemoryView` carry `contradictions` + `last_conflict`, and the panel shows `trust N/5` plus an `N× contradicted` badge in warning colour below confidence 3. `skills::self_evolution_prompt` states the standing rule (never leave a known-wrong entry at its old wording) and the maintenance pass must not make a merged entry more trusted than its most trusted source — a contradicted entry is stale and gets deleted, not folded into a trusted one.
  - **Self-built MCP servers** (`mcp_self`): the third capability the mode owns, next to skills and the evolution memory. The assistant writes a stdio server script under `<workspace>/.data/mcp/<slug>/` and the backend registers + starts it (roster entry lands in the workspace file `<workspace>/.data/mcp.conf`, merged into the effective list — the app-data `mcp_servers.json` is left to the panel). See the tools section for the actions, the confirmation kind and the mid-turn `mcp_revision` rebuild. The capability exists only while the mode is on: the tool is injected into the main agent's payload from `config.self_evolution_mode`, never stored in `selected_tools`, and sub-agents never see it.
  - **Script library** (`<workspace>/.data/scripts`, `tools/scripts.rs`): in this mode the prompt instructs the model to save a multi-step command as a script once it has succeeded at least twice, or whenever the user asks to keep/reuse it. Prefer a shell script (`.ps1` on Windows, `.sh` elsewhere), give it an `@description` / `@usage` header, make it argument-driven and self-contained, then run it once by name to verify. Scripts are shared by the whole workspace; never store credentials in them. The library is also listed to the model in normal mode (compact block) so an existing script is reused instead of retyped.
  - **Library shape**: `experience::{scan, load, search, resolve_for_path}` take the **experiences root** (`root_for(app_data)`), not the app-data folder. Passing app-data resolves to `experiences/experiences/…` and silently finds nothing — the tool layer therefore keeps `store = root_for(app_data)` and joins slugs, `.archive/` and staging folders directly onto it.
  - **Maintenance sees the experience store read-only** (`evolution_maintenance.rs::experience_inventory`): the pass inventory gains a global section (slug / state / parts / when / guide / source workspace) plus deterministic `overlap:` lines when two packages claim the same matcher, and the rules forbid editing app-data — the pass may only *propose* a `distill` or a retire. `build_inventory(workspace_dir, app_data)` takes the app-data dir as an option so the store is only read when one is available.
  - **`requires` is metadata, not a check** (`experience.rs::Requires`): `pack` and `distill` scan the payload sources (python `import`/`from`, node `require(`/`from '…'`) and record the interpreters plus every non-stdlib module, with the producing host in `checked`; the stdlib/builtin lists exist so the metadata stays honest. Nothing in the app runs those probes — installing dependencies is the caller's job, and `install` prints the list. A package packed before the field existed has an empty `requires` and skips the section.
  - **Experiences are a portable folder, not an execution engine** (the single source of truth for this subsystem): `<app_data>/experiences/<slug>/` holds `experience.json` + `guide.md` + optional `skill/`, `scripts/`, `mcp/`. The `experience` tool only does `search | load | install | pack | distill | forget`. `install` copies those parts into the current workspace — `.data/skills/<slug>/`, `.data/scripts/<name>` (flat, so `run_shell`/`run_cmd` resolve the bare name; a collision is refused unless `overwrite`), `.data/mcp/<slug>/` — and the ordinary tools run them: `use_skill`, `run_shell`/`run_cmd`, `mcp_self`. The app spawns nothing for an experience: no contracts, no `.trust.json`, no AppContainer/job objects, no runtime probing (the `check_experience_environment` command is the only leftover prober and no UI calls it). `requires` is metadata for the human/main agent — installing dependencies is not the app's job. `pack` is the exact inverse of `install`: it snapshots workspace artifacts into a package. `experience.json.schema` must be `1` (the loader rejects anything else and the package silently fails to load).
- `chat.db` moves with the workspace: `apply_config` re-opens the SQLite connection when `workspace_dir` changes, so history, monitor logs and missions are per workspace.
- **Workspace history** (`config.workspace_history`): `apply_config` records the *resolved* workspace path before `config.json` is written (newest first, deduped case-insensitively, capped at `WORKSPACE_HISTORY_LIMIT` = 10), so a Settings save, a titlebar switch and a backup restore all feed the same list. The list belongs to `config.json`, so it travels with a backup, and it never switches a workspace by itself. The **titlebar workspace indicator** is the only picker: clicking the label opens the recently used workspaces and applies the chosen workspace immediately (closing the sidebar first — every panel reads workspace-scoped state, so none of them repaints against the workspace being replaced). Every Settings save path (`handleSave`, `handleLanguageChange`, `applyMessageEditor`) takes `workspace_dir` from a fresh `getConfig()` instead of writing the copy it loaded, for the same reason `selected_tools` comes from there. The switch itself goes through `set_workspace_dir`, never through `save_config` — the command writes that one field onto the live `AppConfig`, because a UI copy that predates another panel's edit must not be round-tripped back — and it is refused while ANY turn is running (`TurnRegistry::any` — several sessions can run at once, and a streaming reply owns the paths and the database handle of the workspace it started in; the UI disables the rows for the same reason). `workspace_history_entries` is the popup's single read: deduped history plus the *resolved* current path (`current`) and a `Path::is_dir()` check per entry (`exists`), so the UI never reconstructs the list from `AppConfig` — that only knows `workspace_dir: None` for the default workspace. A switch from a shadow window is window-local like every other setting of that window; only the history merges back on exit.
  Startup also seeds it with the workspace it opens (`remember_workspace` returns whether the list changed, so an already-newest entry costs no write), which means one switch is enough to make the previous workspace selectable.
- `.data/skills` is **not** created automatically; skill listing and the memory store create what they need on demand. `.data/scripts`, `.data/tmp` and `.data/deliver` **are** created at startup (`ensure_data_layout`), so the script library, the composer scratch area and the deliverables root exist from the first launch.
- **Sub-agent deliverables** (`<workspace>/.data/deliver/<session-id>`, `src-tauri/src/agents/exchange.rs`): every planner-dispatched mission and every `call_subagent` call gets one batch directory `<workspace>/.data/deliver/<session-id>/<batch-id>/` with `shared/` plus one directory per task id (sanitized, deduplicated). The session id is validated as a path component (`workspace::session_deliver_root`), never sanitized silently. The sub-agent's static prompt names its own directory and the shared directory; large deliverables go there instead of into the answer, and a dependent task reads `<exchange-root>/<task-id>/<file>`. The mission report and the `call_subagent` tool result list the files and their sizes, so the main agent can read them with `file_actions`. `cli` agents receive the same paths; `cloud` agents get one too — they cannot write the workspace themselves, but the runtime saves the media their endpoint returns into the task directory (see the `cloud` backend bullet). Nothing prunes the area automatically: it **is** part of the backup (`workspace/deliver/...`), and deleting the chat session (`delete_history`) removes that session's directory. The Agent Mission panel lists the session's batches (`list_deliverables`, newest first, empty batches skipped) with a size and a **“Show in folder”** action per file (`revealItemInDir` on the absolute path the backend returned), and its “Deliverables folder” button opens `<workspace>/.data/deliver/<session-id>` (`app_open_session_deliver_dir`); the titlebar `⋯` menu opens the area root (`app_open_ws_data_dir`). It is a folder action, not a preference, so it lives outside Settings.
- `skills.status` is the source of truth for which skills are enabled. It is per workspace and entries are never pruned automatically — a skill folder that disappears stays recorded (and simply stops reaching the model) until the folder returns. `config.selected_skills` no longer exists.
- **Skill identity is the frontmatter `name`**, not the folder name (`refresh_skill_status` keys entries by the declared name; the folder is only a fallback while the file does not parse). Two consequences, both enforced in `src-tauri/src/skills.rs`: when such a fallback entry later becomes parseable, `refresh_skill_status` folds it into the declared name (carrying `enabled` / `enabled_at` over) and drops the stale key, so one skill never owns two identities; and `filter_existing_skills` counts a name only when it round-trips (`resolves_to_name`) — `resolve_skill_by_name` still accepts a folder name as an alias for zip-imported skills, but an alias is not something the Skills panel can toggle, and counting one left the toolbar badge showing an enabled skill that no switch could turn off.

- **Identifier**: `com.leonard.aichat` (set in `tauri.conf.json`). The display name lives in `productName`/`title`; the binary is `rabbit-chat-studio.exe`.
- **Window label**: `main` (the only window).
- **Window chrome is custom**: `decorations: false` + `shadow: true`; `src/components/TitleBar.tsx` draws the drag region (`data-tauri-drag-region`) and the window buttons via `@tauri-apps/api/window`. The required permissions live in `capabilities/default.json` (`allow-start-dragging`, `allow-minimize`, `allow-toggle-maximize`, `allow-close`, …). - **Plugins registered in `lib.rs`**: `tauri-plugin-opener`, `tauri-plugin-dialog`, `tauri-plugin-clipboard-manager`, plus `tauri-plugin-single-instance` — registered **first**, **release builds only** (`#[cfg(not(debug_assertions))]`, so `tauri dev` can run alongside an installed copy of the same identifier) and only while `config.single_instance` is on. If you need them, add the crate to `Cargo.toml`, register with `.plugin(...)`, AND add the permission to `src-tauri/capabilities/default.json` (Tauri 2 denies by default).
- **The single-instance plugin only decides whether a second process survives.** When it does (switch off), `instance.rs` turns that process into a shadow window: it claims no primary lock, materialises its own config copy in `setup` (never before — a launch the plugin aborts must not leave a directory behind) and releases everything on `RunEvent::Exit` / `CloseRequested`.
- **App menu**: defined in `lib.rs` — items include `open-app-data-dir`, `open-workspace-dir`, `save-backup`, `restore-backup`, `markdown-edit`, `open-issue` (GitHub new-issue page, also the last action of the titlebar `⋯` menu). The macOS `Help` submenu holds only `open-issue`: the About dialog and its menu entries are gone from both the native menu and the titlebar.
- **Vite dev server**: port `1420`, `strictPort: true`. If the port is busy, Tauri dev fails. HMR uses `1421` if `TAURI_DEV_HOST` is set.
- **Vite watcher ignores** `**/src-tauri/**` (so Rust edits don't trigger Vite reloads — recompile via `cargo`).
- **Commands return** `Result<T, String>` (or another `Serialize` error). Frontend `invoke()` rejects on `Err` — always `await`.
