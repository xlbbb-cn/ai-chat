# 桌面宠物：把 `notify` 窗口改造成常驻宠物（可行性探索）

> 状态：**已实施**。规范性内容已按仓库惯例落进 `docs/DESIGN.md`（PATCH v1.10：
> 视觉规则与动效例外）、`docs/agents/architecture.md`（双面窗口、焦点契约、
> 拖动持久化、单例门槛）与 `docs/agents/modules.md`（`src/notify.rs` 的文件职责）；
> 本文保留为设计与取舍的记录。
>
> 落地与本文的四处差异：
> ①宠物默认边长取 **120**（§3.2 的 m 档），并新增 `desktop_pet_scale`
> （96 / 120 / 160）与 `desktop_pet_hide_when_focused`（默认开）；
> ②通知到达时**先让宠物下潜 180 ms 再放大窗口**——卡片 348×112、
> 宠物 120×120，卡片高 112 比宠物矮 8 px，不先让宠物离开就会露出头顶；
> ③通知卡片的美术**仍是 `notice1.png`**：§5.5 的“顺手收益”没有做，避免改动既有
> 卡片观感；宠物本身是内联 SVG，没有引入新位图；
> ④宠物被**单实例模式**门控（`config.single_instance`）——多实例会在屏幕同一角落
> 各放一只，设置面板里该开关在单实例关闭时是锁定状态。
>
> 配套原型：`docs/pet-prototype.html`（浏览器直接打开，看形态 / 节奏 / 卡片遮挡）。

## 1. 结论

**可行，而且这几乎是 `notify` 窗口唯一的“下一步”用途。** 理由：

- 窗口本身已经具备宠物需要的全部“非交互”属性：无边框、透明（非 macOS）、无阴影、
  不进任务栏、`always_on_top`、创建时不抢焦点、`CloseRequested` 被拦截后只隐藏
  （`src-tauri/src/notify.rs:83` 的 `ensure_notify_window`）。
- 位置计算、工作区查询（含 Windows `GetMonitorInfoW` 的可用区域）、
  玻璃底（Acrylic / Mica / macOS vibrancy / Linux 回退水洗）、
  主题 × 配色 × 玻璃的实时刷新，全部已经在 `notify.rs` 里跑通。
- 前端已经有一张**同一角色的兔子脸**：空状态里那枚会眨眼、会小憩、会呼吸的
  SVG（`src/App.tsx:240` 的 `DREAM_FACE` + `src/App.css:1892` 起的 `.rabbit-hop-*`），
  用两层色（`--c-muted` 填充 / `--c-bg` 眼孔）就够，不需要新的美术资产。
- “通知挡住宠物”在单窗口里是**几何自动成立**的：卡片和宠物共用右下角锚点，
  卡片（348×112）覆盖宠物（≤120×120）所在的那一格。

**不建议新建第三个窗口。** 一条 webview 已经要付一次渲染进程 + 共享样式表的代价，
宠物再开一条就是双份；而“盖住”一旦跨窗口就退化成 z-order 竞争，反而要做
`always_on_top` 的先后博弈。

一句话方案：**`notify` 窗口 = 一块双形态的透明画布**，`PET`（120×120，活动）与
`CARD`（348×112，卡片）两种形态由同一个 Rust 状态机切换，通知到达时宠物先“下潜”，
窗口原地长成卡片把它盖住，卡片消失后再缩回宠物。

## 2. 现状审计（可复用的与硬约束）

### 2.1 窗口

| 事实 | 证据 |
|---|---|
| 隐藏创建、无边框、`shadow(false)`、`skip_taskbar`、`focused(false)`、`always_on_top`、`resizable(false)` | `src-tauri/src/notify.rs:83-121` |
| 非 macOS 才 `transparent(true)`（无 `macos-private-api` feature） | `src-tauri/src/notify.rs:104-112` |

| 6s 自动消失（悬停暂停）、点击隐藏并聚焦主窗、30s 硬上限兜底 | `src/notify.tsx:39-40,157-186` |

### 2.2 前端与资产

- `src/notify.tsx` 每次 `notify-show` 都重新拉 config 刷 `data-theme` / `data-palette`
  / `data-glass`，再向 Rust 要 `refresh_notify_backdrop`（顺手是“webview 已挂载”的
  就绪信号，`NOTIFY_READY`）。宠物形态可以完全复用这条通路。
- 卡片美术是 `src/assets/notice1.png`，**363,285 字节（≈355 KB）**，只被
  `notify.tsx` 引用。换成内联 SVG 兔子脸可以顺便把这块体积从包里去掉
  （见 §5.5 的“顺手收益”）。
- 设计系统里已经给这张脸开过口子：`docs/DESIGN.md:889-941` 明确写了空状态脸
  “never travels or tilts — its only idle motion is the eye blink”，
  呼吸 / 眨眼 / `z` / 粒子都被当作**背景动效**处理。宠物要“活动”，需要在
  `DESIGN.md` 里补一条与空状态脸同级的显式例外，而不是偷偷绕过规则。

### 2.3 权限面（关键：不需要放宽能力）

`core:window:default` 的清单里**不含** `allow-start-dragging`、`allow-set-size`、
`allow-set-position`、`allow-show` / `allow-hide`
（`tauri-2.11.1/permissions/window/autogenerated/reference.md` 的
“This default permission set includes…”）。而本仓库的既有做法是**前端不碰窗口 API**
——`hide_notify_card`、`focus_main_from_notify`、`refresh_notify_backdrop` 都是自定义
命令，窗口操作留在 Rust 里。

宠物沿用这条线即可：**拖拽、改尺寸、改位置、显隐全部走自定义命令**，
`capabilities/notify.json` 仍然是 `core:default`，一行都不用改。
（反面方案：用 `data-tauri-drag-region` 让前端直接拖，那就必须加
`core:window:allow-start-dragging`，还得再讨论一次权限面。）

## 3. 需求映射

需求原话：**没有 notify 的时候是活动的宠物；有 notify 的时候 notify 挡住宠物。**

| 需求 | 机制 |
|---|---|
| 常驻的“活动”宠物 | 同一个 `notify` 窗口的 `PET` 形态：120×120 透明画布，CSS 关键帧 idling（呼吸 + 眨眼），状态驱动更多动作 |
| 通知出现时挡住宠物 | 同一窗口的 `CARD` 形态：窗口从**同一右下角锚点**向左上扩张成 348×112，卡片层覆盖宠物那 120×120 |
| 通知消失后回到宠物 | 卡片淡出 → 窗口缩回 120×120 → 宠物“浮出” |
| 不抢前台 | 已有 `focused(false)`；宠物再加 `focusable(false)`（tao 0.35 有 `with_focusable`） |
| 点宠物 = 打开主窗 | 复用 `focus_main_from_notify`（`notify.rs:192`） |
| 宠物可拖、位置可记 | 新命令 `pet_begin_drag` → Rust `window.start_dragging()`；`WindowEvent::Moved` 去抖后写回 config |
| 宠物“状态”有意义 | 新增 `companion-state` 事件：后台回合运行 → thinking，结束 → done，失败 → error，`todos ask` / 风险确认 → ask，长时间空闲 → sleeping，自进化整理 → dreaming（直接复用空状态那套“小憩”动作） |

### 3.1 为什么宠物必须先“下潜”再变大

卡片高 112，宠物 120 —— **卡片比宠物矮**。如果让窗口原地长成 348×112，
宠物顶上有 8px 会露在卡片外面。所以时序是：

```
通知到达
  → 宠物下潜（180ms，translateY + 淡出，还在 120×120 窗口内）
  → 窗口 set_size(348×112) + set_position(同一右下角锚点)   ← 此时窗口里只有卡片
  → 卡片淡入（沿用现成的 .notify-card-shown）
消失（6s / 悬停后 / 点击 / 主窗聚焦）
  → 卡片淡出（200ms）
  → 窗口 set_size(120×120) 回锚点
  → 宠物浮出
```

反过来（先变大再让宠物躲）会在放大动画里露出半个宠物，观感崩。

### 3.2 几何

沿用现在的锚点定义（`notify.rs:315` 的 `work_area_bottom_right`）：

```
anchor = (workArea.right - 12, workArea.bottom - 12 - shellMargin)
CARD   = (anchor.x - 348, anchor.y - 112, 348, 112)   // 现值，不变
PET    = (anchor.x - 120, anchor.y - 120, 120, 120)   // 新增
```

- 两者共享 `anchor`，所以 `PET ⊂ CARD`（120×120 落在 348×112 的右下角内，
  高度差 8px 由 §3.1 的下潜吸收）。
- 宠物被用户拖走后，`anchor` 变成“宠物当前位置的右下角”，卡片依然从同一锚点长出
  ——**无论宠物在哪，卡片都会盖住它**，这就是需求里那句话的严格实现。
- 尺寸档位：`s=96 / m=120 / l=160`（4px 网格的整数倍）。`l` 需要回到 §3.1 的
  下潜逻辑，行为一致。
- 记忆位置：存**逻辑坐标**（用户把显示器缩放从 100% 改成 150% 后仍然对），
  启动时按“最近显示器的工作区”clamp 一次，防止拔掉副屏后宠物落在屏幕外。

### 3.3 状态机

```
                    app 启动 & desktop_pet=on
                              │
              ┌───────────────▼───────────────┐
              │           PET (可见)           │
              │  idle ⇄ thinking ⇄ done/error  │
              │        ⇄ ask / sleeping        │
              └───┬───────────────────────▲───┘
   通知到达        │                       │ 卡片消失
                  ▼                       │
              ┌───────────────────────────┴───┐
              │        CARD (348×112)         │
              │  6s / 悬停后 / 点击 / 主窗聚焦  │
              └───────────────────────────────┘
                  │
                  │ 主窗聚焦 & desktop_pet_hide_when_focused
                  ▼
              ┌───────────────────────────────┐
              │  HIDDEN（window.hide()，动画停）│──主窗失焦──► PET
              └───────────────────────────────┘
```

Rust 侧只存一个枚举 + 一个锚点 + 一个 generation（现成的 `NOTIFY_SEQ`
已经用于“只有最新一次 show 能强制隐藏”，宠物沿用同一套）：

```rust
enum CompanionMode { Hidden, Pet, Card }

struct Companion {
    mode: CompanionMode,
    anchor: (f64, f64),   // 逻辑坐标，宠物右下角
    gen: u64,
}
```

## 4. 约束与风险

| # | 约束 | 证据 | 影响 | 处置 |
|---|---|---|---|---|
| R1 | **macOS 没有透明窗口** | `notify.rs:104-112` 刻意跳过 `transparent`（没有 `macos-private-api`） | 宠物会顶着一块不透明底，透明画布方案失效 | ① 打开 `macos-private-api` feature（本应用不进 Mac App Store，MSIX 分发，私有 API 的顾虑不适用）；② 或 macOS 降级成“卡片里的宠物”（圆角底 + hairline，与通知卡片同款），功能不减、观感不同 |
| R2 | **Linux Wayland 无法定位/置顶** | winit/tao 在 Wayland 下 `set_outer_position` 被合成器忽略；`always_on_top` 依合成器 | 宠物位置不可控、可能被压在全屏窗口下 | 本机是 **X11**（`$XDG_SESSION_TYPE=x11`），可实测；Wayland 下退化为“由 WM 放，不记忆位置、不保证置顶”，并在设置项 hint 里写清楚 |
| R3 | **透明区域的点击热点** | 没有 per-pixel hit-test API；窗口矩形内透明像素照样吃鼠标 | 宠物周围会有一块“点不到桌面”的死区 | ① 窗口贴合轮廓（120×120 头身已经比较紧）；② 不要用“固定 348×112 大窗口常驻”的方案（死区 3 倍）；③ 进阶（不建议 v1）：`set_ignore_cursor_events(true)` + Rust 轮询指针位置动态放行 |
| R4 | **焦点** | 常驻置顶窗口一旦可聚焦，点它就会把前台从用户当前应用抢走 | 用户点宠物本想“打开主窗”，中间会闪一下空焦点 | `with_focusable(false)`（tao 0.35 提供）+ 点击命令里直接 `focus_main_window`。**需在 Windows 上实测**：不可聚焦窗口的 `start_dragging` 是否照常（X11 上通常可以，Windows 上要给 `WM_NCHITTEST` 之外的常量做验证） |
| R5 | **主窗聚焦即隐藏的旧规则会杀掉宠物** | `lib.rs:2280-2290` 无条件 `hide()` | 宠物刚出现就被隐藏 | 规则改成按形态分支：`Card` 必隐藏；`Pet` 仅在 `desktop_pet_hide_when_focused` 为真时隐藏 |
| R6 | **退出路径** | `lib.rs:2250-2275`：主窗关闭先 `destroy` 卡片，靠 `windows.is_empty()` 自然退出 | 宠物常驻会不会让 app 退不出去？ | 不会：宠物就是同一个窗口，`destroy` 那条路径原样生效，**不需要改动** |
| R7 | **功耗 / 内存** | 第二条 webview + 常驻 CSS 动画 | 笔记本续航、GPU 占用 | 只在可见时跑动画（`window.hide()` 后 WebView 自动停 rAF / 动画）；只动画 `transform` / `opacity`（合成器层）；小窗口（120×120）；`prefers-reduced-motion` 直接静止；打包时 CSS 只留宠物所需规则 |
| R8 | **右键菜单放不进小窗口** | HTML 菜单会被 120×120 的窗口裁掉 | 想给“隐藏宠物 / 设置 / 打开主窗”做个菜单就没地方画 | 用 Tauri 2.11 的 `WebviewWindow::popup_menu`（原生菜单，`tauri-2.11.1/src/webview/webview_window.rs:1669`），Rust 侧调用不需要新权限；Linux 上由 muda 走 GTK 菜单，需实测 |
| R9 | **设计系统** | `DESIGN.md` 非协商项：4px 圆角、不做 `translate` 位移动效、一个 spring | 宠物会跳、会走、会歪头 | 与空状态脸同级的**显式例外**：宠物窗口的 idle loop 属于“背景动效”，位移/呼吸/眨眼都在此列，且必须 `prefers-reduced-motion` 可静止；不在应用 chrome 里复用这些动作 |
| R10 | **事件注册表有硬断言** | `events.rs:421` 的 `assert_eq!(names.len(), 50)` | 加事件不改测试会直接红 | 新增 2 个事件 → 同步把 50 改成 52 |

## 5. 建议方案（B：单窗口双形态 + 默认“主窗失焦时出现”）

### 5.1 三个候选，选 B

| 方案 | 做法 | 评价 |
|---|---|---|
| A | 新建 `pet` 窗口 + 保留 `notify` | 两条 webview；“盖住”变成跨窗口 z-order；退出/生命周期要再走一遍 `lib.rs` 的分支 | ✗ |
| **B** | `notify` 窗口双形态（PET / CARD） | 0 新窗口、0 新权限、几何天然覆盖、退出路径不动 | ✓ **推荐** |
| C | 常驻一个 348×112 固定窗口，宠物画在里面 | 不 resize，实现最省；但 3 倍透明死区常年在桌面上吃点击 | ✗ |

### 5.2 可见性策略（默认值）

- **默认：主窗失焦 / 最小化时宠物出现，主窗获得焦点时隐藏**
  （`desktop_pet_hide_when_focused = true`）。
  好处：与现有 `Focused(true)` 规则同源、不挡用户正在看的窗口、功耗最低；
  而且“后台回合在跑”本来就是宠物最有信息量的时刻。
- 想让它常驻桌面：把该开关关掉即可（同等支持，但要在设置 hint 里写明
  “会一直盖在其它窗口上方”）。

### 5.3 契约

**事件**（`src-tauri/src/events.rs`，新增 2 个）

| 事件 | 载荷 | 触发 |
|---|---|---|
| `companion-mode` | `{ mode: "pet"\|"card"\|"hidden", anchor: [f64;2], scale: "s"\|"m"\|"l" }` | 形态切换（后端 → 宠物 webview） |
| `companion-state` | `{ state: "idle"\|"thinking"\|"done"\|"error"\|"ask"\|"confirm"\|"sleeping"\|"dreaming" }` | 主窗推送语义状态 |

`notify-show` 保持不变（卡片文案继续走它），只是到达时机挪到“下潜之后”。

**命令**（`src-tauri/src/ipc/notify.rs`，新增 3 个；窗口操作全在 Rust）

| 命令 | 作用 |
|---|---|
| `pet_begin_drag()` | 前端 `mousedown` → `window.start_dragging()`；拖动结束后由 `Moved` 事件回写锚点 |
| `pet_set_state(state)` | 主窗推送宠物语义状态（App.tsx 在 turn 开始 / settle / ask / dreaming 时调用） |
| `pet_context_menu()` | 可选：原生右键菜单（隐藏宠物 / 打开设置 / 打开主窗） |

现有 4 个命令语义调整：
`show_notify_card`（先下潜再切 CARD）、`hide_notify_card`（回到 PET 而不是隐藏）、
`focus_main_from_notify`（不变）、`refresh_notify_backdrop`（不变，两种形态都需要）。

**config**（`AppConfig` / `types.ts` / SettingsPanel / i18n ×3）

```rust
#[serde(default)] pub desktop_pet: bool,                              // 默认 false（新行为，opt-in）
#[serde(default = "update::default_true")]
                  pub desktop_pet_hide_when_focused: bool,            // 默认 true
#[serde(default)] pub desktop_pet_scale: Option<String>,              // "s" | "m" | "l"，默认 "m"
#[serde(default)] pub desktop_pet_anchor: Option<[f64; 2]>,           // 逻辑坐标（宠物右下角）
```

## 6. 交互细节（P1 就要定下来的）

- **单击** → `focus_main_window`（主窗 unminimize + show + focus），宠物随后按策略隐藏。
- **拖动** → `mousedown` 立即 `start_dragging`（原生拖拽，自身不吃 `mousemove`），
  松手后 `Moved` 触发，800ms 去抖写回 config。
- **双击** → 暂不绑定（与单击冲突，且没有第二个合理动作）。
- **右键** → 原生菜单：`隐藏宠物（本次运行）` / `打开设置` / `打开 Rabbit Chat Studio`。
- **悬停** → 不做位移；最多把眼睛“看向指针”（纯 `transform`，减动效下静止）。
  悬停是否需要暂停 idle 动画：**不需要**（宠物没有自动消失）。
- **通知卡片** → 保持现有 6s / 悬停暂停 / 点击聚焦主窗 / 主窗聚焦即消失。
- **宠物正在 thinking 时通知到达** → 下潜、卡片、回来继续 thinking（状态由 Rust 记着，
  不靠前端记忆）。

## 7. 未决问题（需要产品决定）

1. **常驻还是“失焦才出现”**？本文默认后者（省电、不挡视线）；前者只需关一个开关。
2. **宠物形态**：复用空状态兔子脸（零新美术、品牌一致，但只有头），
   还是画一只带头身脚的兔子（更像宠物，需要新 SVG + 一次设计评审）？
3. **尺寸**：默认 120 是否偏大？（96 更克制，160 才“可见地活着”）
4. **状态语言取舍**：`sleeping` / `dreaming` 两个状态是否都暴露给用户，
   还是只在自进化整理时复用“小憩”那套而不新增文字。
5. 是否需要 **WebM / 帧动画**（表情更多、但打包和内存都更贵，且失去 token 着色）。

## 8. 附：原型怎么看

`docs/pet-prototype.html`（无构建、无依赖，浏览器双击打开）：

- 右下角是 **120×120 的模拟窗口**，展示 7 种状态（空闲 / 思考 / 完成 / 出错 / 提问 /
  睡觉 / 整理记忆）与三档尺寸；
- 点「模拟通知」走完整时序：宠物下潜 → 窗口长成 348×112 → 卡片淡入盖住宠物 →
  6s 自动消失（悬停暂停，点击关闭）→ 缩回宠物；
- 顶栏可切浅色 / 深色、开关 hairline 轮廓与“减少动效”；
- 面板上实时打印窗口几何（锚点、尺寸、形态），对照 §3.2 的公式。

原型只覆盖“看得见的部分”（形态、节奏、遮挡、状态语言）。透明窗口、置顶、
不抢焦点、拖拽、退出路径这些**只能由 Tauri 侧验证**，见 §5.5 的 P0 手动清单。
