# AI Chat — Tauri 2.0 (Rust + React)

Desktop AI chat client (Tauri 2 + React 19 + TS + Vite, Rust backend) that talks to any OpenAI-compatible API and adds **Skills**, **Tools**, and **Sub-Agents**.

## UI design — mandatory

**Any change that affects the interface MUST follow [`DESIGN.md`](./DESIGN.md).** It is the single source of truth for colours, typography, spacing, components, motion and both themes. Do not invent visual language and do not copy a style from another project — if a value is not in the spec, add it to the spec first.

Non-negotiables, repeated here so they are impossible to miss:

- **Tokens only.** Colours, radii, shadows, durations and easings come from `src/App.css` (`:root` + `[data-theme="dark"]` + the palette blocks). A literal hex outside those blocks is a bug.
- **One accent colour.** Electric Blue (`--c-accent` = `#3E6AE1`) marks the primary action of a view — never decoration, never a second chromatic accent. Semantic `--c-danger` / `--c-success` / `--c-warning` are for status only. An accent used as a *label or line* is `--c-accent-text`; a label on an accent *fill* is `--c-on-accent`.
- **No elevation.** `--shadow-*` are `none`; layering is z-index, opacity and the frosted `--c-toolbar` surface. Never write `box-shadow: <literal>, var(--shadow-sm)` — the mixed declaration is invalid and is dropped silently.
- **4px radius** on interactive elements. No pills, no large radii. Toggles/badges square off at 4px too.
- **One motion curve:** `--t-dur` (`0.33s`) + `--t-ease`. Colour/border transitions only — no `scale`/`translate` on hover.
- **Hairlines separate.** 1px `--c-border` for structure, 1px `--c-border-i` for interactive outlines. No gradient surfaces.
- **Reuse the shared primitives.** `.close-btn`, `.btn-primary`, `.btn-secondary`, `.inline-edit-btn`, `.field-title-row` are defined once in `src/App.css` — never re-declare them in a component stylesheet (that is exactly how the Skills/MCP/Tools panels drifted apart).
- **Compact zone = 34px controls** (chat input row, sidebar panels, Settings). Settings also uses 13px text. Do not introduce 40px inputs.
- **Sentence case, weights 400/500 only, `letter-spacing: normal`.** No `text-transform: uppercase`, no negative tracking.
- **Check light *and* dark** (`data-theme` is driven by `config.theme` via `applyTheme()` in `src/App.tsx`), plus `prefers-reduced-motion` for any animation. The colour scheme is a second, independent dimension: `data-palette` (`default` / `fig` / `cream`) comes from `config.palette`, and every palette ships a light *and* a dark token set — check all four combinations of a change.

When a needed value has no token, **add a token** to `src/App.css` — do not hardcode it at the call site.

Verify style work with `npx tsc --noEmit && npx vite build` (not `npm run build`, which requires a git tag).

## Commands

```sh
# Dev (hot-reload). Runs `npm run dev` (Vite on :1420) then launches Tauri.
npm run tauri dev

# Frontend only (Vite on :1420, strictPort — must be free)
npm run dev

# Production build. NOTE: this runs `sync-version:git-tag` first, so the
# repo must have a git tag (e.g. v1.1.1) or the build aborts.
npm run tauri build

# Type-checks
npx tsc --noEmit                                  # frontend
cargo check --manifest-path src-tauri/Cargo.toml  # rust

# Version sync (package.json ↔ Cargo.toml ↔ tauri.conf.json)
node scripts/sync-version.cjs --from-git-tag
node scripts/sync-version.cjs --bump patch
npm run sync-version:git-tag
npm run sync-version:bump-patch

# Rust unit tests (inside the `tools` module: dispatcher, `tools/todos`, `tools/timer`)
cargo test --manifest-path src-tauri/Cargo.toml
```

### Cargo mirror (CN / restricted networks)

`~/.cargo/config` may point at the USTC git registry, which can be unreachable. If `cargo` fails to fetch deps, override the source:

```sh
cargo check --manifest-path src-tauri/Cargo.toml \
  --config 'source.crates-io.replace-with="rsproxy-sparse"' \
  --config 'source.rsproxy-sparse.registry="sparse+https://rsproxy.cn/index/"'
```

## Releases (CI)

`.github/workflows/release.yml` (trigger: `v*` tag push, or manual `workflow_dispatch`) builds via
`tauri-apps/tauri-action@v1` on 4 runners — `macos-latest` ×2 (`aarch64-apple-darwin`, `x86_64-apple-darwin`),
`ubuntu-22.04`, `windows-latest` — and uploads `.dmg` / `.AppImage` + `.deb` + `.rpm` / `.msi` + NSIS `.exe`
to a **published** (non-draft) GitHub Release for the tag (also kept as workflow artifacts).

- **The tag drives the version.** `tauri build` runs `beforeBuildCommand` → `npm run build` → `sync-version:git-tag`, which reads the newest tag; a workflow step fails fast when the pushed tag is not the newest one.
- CI runs `rm -f .cargo/config.toml` so the committed rsproxy.cn mirror is not used on GitHub runners.
- macOS uses `APPLE_SIGNING_IDENTITY='-'` (ad-hoc) — replace with real signing/notarization secrets when available.
- `.github/workflows/winget.yml` auto-submits each published release's NSIS `-setup.exe` to `microsoft/winget-pkgs` via `winget-releaser`; it first waits for the asset upload to finish and needs the `WINGET_TOKEN` secret (classic PAT, `public_repo` + `workflow`) plus a `microsoft/winget-pkgs` fork under `xlbbb-cn`.
- `releaseDraft: false` publishes the Release as soon as the first platform finishes; remaining assets upload afterwards, so downstream consumers (e.g. winget) must wait for the NSIS `.exe` to appear.

## Architecture

- **Entry points**: `src/main.tsx` → `src/App.tsx`; Rust `src-tauri/src/main.rs` → `src-tauri/src/lib.rs` (command registration, state, app setup).
- **Streaming chat**: `chat_completion` command opens an SSE connection (`reqwest` + `futures-util`) and emits to the frontend:
  `chat-token`, `chat-reasoning-token`, `chat-done`, `chat-error`, `chat-usage`. Streamed tool calls are normalised before use: an empty or duplicate `id` (some relays omit it) gets a generated `call_…` id, so the assistant `tool_calls` and the following `tool` messages always agree and strict providers (DashScope) accept the next request.
- **Mid-turn injection** (`inject_user_message` + `AppState::turn_inbox`): the composer stays usable while a turn streams, and Enter then appends the text to the *running* turn instead of starting a new one. A turn is a sequence of requests, so the queue is drained at the top of the main tool loop — the only safe boundary, because an `assistant` message carrying `tool_calls` must stay adjacent to its `tool` results. The text is appended as a `user` message (never `system`: some OpenAI-compatible gateways reject mid-conversation system messages) and announced with `chat-injected`, so the UI can tell "delivered to a request" from "still queued". A reply that already made its last request has no boundary left: the window closes with the turn (`InjectionWindow`, keyed by turn id so a winding-down turn cannot touch a newer one) and the UI re-sends those items as a normal next turn. Deliveries are stored on the assistant row (`history.injections`) and replayed as user messages, since one turn is still one row.
- **Agent orchestration** (toggle via `use_agents`): with `auto_configure` on (default), one non-streaming selection call (`select_agents` → `agent-selection`) proposes the roster for this turn; a declined selection (`delegate: false`) skips planning entirely and the main agent answers directly. When selection allows delegation, the planner call itself first answers `delegate` again (`PlanDecision`): an explicit `delegate:false` also skips the mission, returns a declined selection and leaves the answer to the main agent; `delegate:true` plans tasks (a single task is valid). The selection chip is emitted only after the planner confirms, so a declined plan never shows a stale roster. The plan is parsed with one repair retry and sanitized (fence/prose stripping, trailing commas, unknown `agent_id` dropped, duplicate task ids renamed, dangling and cyclic dependencies removed). Execution then runs in dependency waves (parallel, `max_concurrent`) or in list order (sequential). A task that never ran — unknown agent, skipped dependency, or Stop — is reported as `skipped` (`agent-task-skipped`) instead of being dropped silently, so the mission report is never shorter than the plan. The selected roster only narrows what the main session's system prompt advertises; `call_subagent` still accepts any enabled agent id. Events: `agent-selection`, `agent-plan-start`, `agent-task-start`, `agent-task-token`, `agent-task-reasoning`, `agent-task-tool`, `agent-task-done`, `agent-task-error`, `agent-task-skipped`, `agent-aggregate-done`. A task row owns its status: `agent-task-reasoning` (live thinking counter) and `agent-task-tool` (tool activity, phase `start`/`progress`/`done`) only feed the row's activity line, and the generic `tool-call` event is main-chat-only — tool progress inside a mission is routed to `agent-task-tool` through `tools::emit_tool_progress`. Settling a running task row on a main-chat event is what made a working sub-agent show a checkmark and stop updating. `agent-task-done` carries `status` (`success`/`stopped`) so a stopped task renders neutral rather than completed. Sub-agent requests use `emit_errors: false`: `chat-error` closes the user's turn in the UI, so a provider failure must surface as `agent-task-error` only. The aggregation step is instantaneous (the mission report is only rendered for the main agent), so `agent-aggregate-done` reports an already-completed step — never render it as "running".
- **Mission bus (`mbus`, `AgentOrchestration.mbus_enabled`, default on)**: every planner-dispatched batch creates one `MissionBus` (`src-tauri/src/agents/mbus.rs`) for the turn. It is an in-process MQTT-like pub/sub channel: peers are the planner and the plan's tasks; `broadcast` is auto-subscribed by everyone; subscriptions support `+`/`#`; direct messages use a task id, a unique agent id, or `planner`. A sub-agent drains its inbox at the top of a reasoning round (after context compression, before building the request) and appends each message as a `user` message carrying `mbus::MBUS_INJECTION_PREFIX` — the same request-boundary rule as the main agent's mid-turn injection, never mid-stream. The bus also keeps a live status registry (pending/running/completed/error/skipped, rounds, tools, tokens, last tool, queued messages, summaries, objectives, per-pair counts and the mission's active sub-tasks) and bounded message/inbox/rate limits. `cli` / `cloud` peers are status-only while running; they can absorb messages queued before their process starts. A message published by an agent can reach another agent, a topic subscriber, or the planner; the planner is a normal peer with its own inbox.
  - **Per-pair cap (`AgentOrchestration.mbus_pair_limit`, default 4, `0` = off)**: every successful delivery between two sub-agents increments one *unordered* counter (both directions combined); topic/broadcast counts each actual recipient separately, and the planner is exempt. The message that reaches the cap is still delivered and, once per pair, queues a `Mission bus` escalation into the planner's inbox (persisted in `agent_bus_messages` and emitted as `agent-mbus-message`). Later messages between that pair are rejected with an explicit "planner has been notified, do not retry"; a topic publish skips exhausted recipients and lists them under `skipped`. The sender's tool result reports `pair_limits` so it knows which message was the last.
  - The planner can therefore take over: `direct` (`to` + `objective` + optional `done_when`) stores an authoritative objective on the peer (re-rendered in that task's mission snapshot every round, so it survives context compression) and also queues it as a normal bus message; `end_task` (`to` + optional `note`) sets a conclusion the `llm` task notices at its next reasoning boundary — it then reports its current result as a success instead of spending another request. `cli` / `cloud` tasks cannot poll the bus, so `end_task` rejects them.
- **Planner supervisor (`src-tauri/src/agents/supervisor.rs`)**: when `mbus_enabled` is on and the plan contains at least one `llm` task, the planner stays alive concurrently with `execute_tasks` (a `oneshot` cancels its in-flight call when the last task settles). It is event-driven: the initial dispatch, terminal task events, messages addressed to the planner, broadcasts and per-pair limit escalations wake it; a 30 s heartbeat only activates when a running task has been idle for ~90 s. Its only tool is `mbus` (`send`, `status`, `history`, `subscribe`/`unsubscribe`, and planner-only `direct`, `end_task`, `finish`), so it cannot edit files or change the plan. Budget: 10 activations (1 for a single-task plan), 4 tool rounds per activation, 1 024 completion tokens, 60 s per request. Its final note reflects the bus statuses (`N completed / failed / skipped`) instead of assuming every settled task succeeded. Events: `agent-planner-state` (`thinking` / `monitoring` / `done` / `stopped` / `error`), `agent-planner-action` (one tool-group row per planner decision: `schedule`, `send`, `status`, `history`, `subscribe`/`unsubscribe`, `direct`, `end_task`, `finish`; a `running` event creates the row and the matching `done`/`error` event settles it), `agent-mbus-message` (one publish with recipients), `agent-mbus-delivered` (messages injected into a sub-agent round).
- **Sub-agent failure handling / capability fit**: every sub-agent LLM request, tool call and result is logged to `app.log` (model, round, token count, tool name, clipped args/result). Provider balance/quota failures (`Insufficient account funds`, 402, free-usage limits) are classified and surfaced as `Upstream account balance/quota exhausted`, the task fails instead of retrying, and `close_mission` marks the mission's `agent_tasks` `failed`/`stopped` so they disappear from active-task lists; `agent_missions.created_at` is reset on a reused mission id. The selector/planner catalogue includes `mcp=enabled|none` and is instructed never to assign live web/browser/API retrieval to a file-only agent (if no agent has the data channel it declines delegation so the main agent's MCP tools handle it). A sub-agent without the required tool is told to call `ask_main_agent` (when enabled) before spending rounds scanning local snapshots.
- **Mission bus persistence**: `agent_missions.bus_id` links a mission to its orchestration batch, and `agent_bus_messages` stores one row per publish (`bus_id`, sender, target kind/id, topic, body, recipient count, timestamp). `list_mission_bus_messages(mission_id, limit)` backs the “Message bus (mbus)” section of `components/AgentMissionPanel.tsx`; the task rows show live sent/received counts and the last note. Messages are in-memory for delivery and in SQLite for replay, so a bus is discarded with its turn while the Mission panel keeps the history.
- **Turn cancellation** (`stop_chat_completion` + `AppState::chat_cancelled`): every `chat_completion` installs a fresh `Arc<AtomicBool>` as its own cancel flag (a `Mutex<Arc<…>>` slot); the previous turn's flag is set to `true` permanently, so a superseded turn can never be resurrected and Stop pressed while idle cannot leak into the next turn. The turn's flag is threaded through `orchestrate` → `execute_*` → `run_sub_agent` → `cli::run`/`cloud::run` and into the main agent's tool loop: `cli` agents poll it every 250 ms and kill their process tree, `llm` agents break their loop, remaining tasks report as skipped, missions close as "stopped" (not "completed"), and a stop during planning/execution aborts the turn before the final answer streams. Plan-phase LLM calls (`plan_tasks`, `select_agents`) are checked between steps, not cancelled mid-request.
- **Profiles / backup**: `src-tauri/src/backup.rs` owns profile export/import (app menu `save-profile` / `restore-profile`). The zip holds `config.json`, `profiles.json`, `mcp_servers.json`, `sub_agents.json`, `agents/`, `workspace/{memory,todos,skills,scripts}/`, `workspace/skills.status` and a `chat.db` snapshot; every `workspace/...` entry is read from and restored into the hidden `<workspace>/.data` directory of the (possibly switched) active workspace, while `agents/...` entries are merged into the app-global `agents/` definition store. Named profiles inside the app (`save_profile_config` / `apply_profile_config` / `delete_profile_config`) are separate and stay in `lib.rs`; a profile carries tools/agents/MCP but **no** skill selection (that is per-workspace state). An `llm` agent's markdown file is materialized on apply (identical content is left untouched), so old profiles with inline prompts keep working.
- **MCP warmup**: enabled stdio servers in `mcp_servers.json` are spawned at app startup (`mcp::start_stdio_process`). MCP stdio children start with the **active workspace** as their working directory (`current_dir` + `PWD` in `build_stdio_cmd`). `cli` sub-agents start in the **task's** working directory — `Task.cwd` is supplied per delegation by the planner or `call_subagent` (never by the agent definition), sandbox-checked by `resolve_task_cwd` and created when missing; `cli::run` applies it via `current_dir` + `PWD`. A `workspace_dir` switch stops running stdio children so the next tool call respawns them in the new workspace. Sub-agent tasks do **not** use this pool: with `enable_mcp`, each task gets its own `AgentMcpSession` (see the sub-agent definitions section).
- **Delay timers** (`src-tauri/src/tools/timer.rs`): the `timer` tool (`timer_set` / `timer_list` / `timer_cancel`, toggled in the Tools panel) lets the assistant wait for slow work instead of polling — the LLM arms a delay and ends its turn; when it fires the backend emits `timer-fired` and the frontend injects the timer's `message` into the same session as a new user turn (`timer-state` keeps the timer bar above the input box in sync). Timers are mirrored to `timers.json` and re-armed at startup, where overdue ones fire immediately. Sub-agents never receive the timer tools (`agents.rs` filters them out). The same file hosts the cross-platform **sleep lock** (`SleepLock`, ref-counted RAII): it is held while any timer is pending **and** for the whole duration of a chat turn (`chat_completion` wrapper in `llm_complete.rs`, released after turn-end serve cleanup), preventing idle system suspend via `SetThreadExecutionState` (Windows), an IOPM assertion (macOS) or a D-Bus inhibit (Linux); `sleep-lock` events + `get_sleep_lock_state` drive the badge above the input box.
- **Background tool tasks** (`src-tauri/src/tools/background.rs`): `run_cmd`, `run_shell` (`run_type: "direct"`), `file_actions` action `search`, MCP tools and `call_subagent` accept `run_in_background: true` (the flag is only advertised while `config.background_tools` is on — Settings → Runtime & Debug → “Background execution”; sub-agents never get it). The call returns a placeholder `tool` result carrying a `bg-…` id immediately, so the model keeps working; the real output is injected at the next request boundary as a `user` message (`[BACKGROUND TASK RESULT …]`) and announced via `chat-injected` with `kind: "background_result"`, so it lands on the assistant row's `injections` and is replayed like a mid-turn injection (tool results themselves are never persisted). The turn is **held open** if the model tries to finish while a task is unsettled (max 3 rounds × 120 s, then the remainder is cancelled). `background_task` (`list`/`wait`/`get`/`cancel`) is the model-side control tool; `list_background_tasks` / `cancel_background_task` back the UI. Tasks are turn-scoped: `end_turn_cleanup` and Stop call `shutdown_session` (set every cancel flag, drop the entries), each runner then kills its process tree, and `process_guard` covers app exit. Background `run_cmd`/`run_shell` run through `process::run_command_timed` (cancellable, tree-killing, 600 s default), a background `file_actions` search polls `SearchOptions.abort` inside the parallel walker, and a background **stdio MCP call gets its own short-lived process** (`mcp::invoke_mcp_tool_isolated`) because the shared pool serialises on `mcp_children` and caps a round trip at 10 s — using it would stall the next request's `tools/list`. Confirmation dialogs are serialised by `AppState.tool_confirm_lock`, and a cancelled task stops waiting for one.
- **Model metadata** (`src-tauri/src/model_metadata.rs`): `fetch_model_metadata` pulls the public basellm/llm-metadata catalogue (6 h in-memory cache) and expands its `tags` into capability flags. `src/utils/modelMetadata.ts` fuzzy-matches remote model ids against it (vendor prefixes, date stamps, modality guards); "Fetch Models From API" stores the matches per model in `config.model_metadata` and uses the catalogue context window when the provider reports none. The chat toolbar renders those flags as icons inside the model picker's options, plus a thinking-depth selector for reasoning-capable models (`config.model_reasoning_effort` → `reasoning_effort`, resolved by `llm_complete::resolve_reasoning_effort` and applied to chat + sub-agent requests). The attachment picker follows the same flags: text is always accepted (inlined into the prompt), images need `Vision` (`image_url` parts), PDFs need `Files` (`file` parts), `wav`/`mp3` need `Audio` (`input_audio` parts); an unmatched model keeps the permissive default.
- **Update check** (`src-tauri/src/update.rs`): `check_update` reads the releases of `xlbbb-cn/ai-chat` from the GitHub API, keeps the highest semver (drafts are always skipped, pre-releases behind `include_prerelease_updates`), ranks the attached bundles for the current OS/arch and flags the preferred one as `recommended`. `download_update` streams into the downloads folder while emitting `update-download-progress`; `open_update_file` / `reveal_update_file` / `open_release_page` hand off to the OS (URLs are restricted to this repository). UI: startup probe + banner in `App.tsx`, dialog in `components/UpdatePanel.tsx`, toggles under Settings → About & Updates.
- **API layer**: `src/api.ts` wraps `invoke` + `listen`. `src/types.ts` is the canonical TS shape for `AppConfig`, `Skill`, `SkillsStatus`, `McpServer`, `SubAgent`, `AgentOrchestration`, `Profile`, `AgentMissionSnapshot`, `ModelMetadata`.
- **Theming**: two independent dimensions in `AppConfig` — `theme` (`auto` / `light` / `dark`) and `palette` (`default` / `fig` / `cream`). `applyTheme()` in `src/App.tsx` writes them to `<html>` as `data-theme` / `data-palette`; the token blocks in `src/App.css` do the rest. Settings → Appearance previews both immediately and persists them on "Save Changes". The palette field lives in the Rust `AppConfig` too, so it survives a config write.
- **Workspace state** (`src-tauri/src/workspace.rs`): single source of truth for the per-workspace layout. Everything workspace-scoped (SQLite database, memory, todos, skills, skill status) lives in the hidden `<workspace>/.data` directory, so switching `workspace_dir` in config swaps the whole state — `apply_config` closes and re-opens the SQLite connection at `<workspace>/.data/chat.db` when the workspace changes.
- **Persistence**: SQLite (`<workspace>/.data/chat.db`) for history, API request monitor, interaction logs, and agent missions. `app.log` stays in the app data dir.

## On-disk layout (runtime)

Application files live in the OS app data dir (`name` from `tauri.conf.json` identifier `com.leonard.aichat`):

- macOS: `~/Library/Application Support/ai-chat/`
- Linux: `~/.local/share/ai-chat/`
- Windows: `%APPDATA%/../Local/ai-chat/`

App-data contents: `config.json`, `mcp_servers.json`, `sub_agents.json`, `profiles.json`, `timers.json`, `app.log`, a `workspace/` dir (default — overridable via `workspace_dir` in config), and an `agents/` dir holding the `llm` sub-agent definitions plus the `index.yaml` discovery manifest.

```text
<app_data>/agents/
  <category>/<slug>.md   # imported/library definitions (read-only from the panel)
  custom/<slug>.md       # agents created from the Sub Agents panel
  index.yaml             # discovery manifest, replaced on Refresh
```

### Sub-agent definitions (`llm`)

`sub_agents.json` is **configuration only**. For an `llm` agent it stores the runtime knobs (`enabled`, `model`, token limits, `allowed_tools`, `allowed_skills`, `max_iterations`) plus a `file` reference; `cli` / `cloud` agents keep their full definition there. An `llm` agent's `name`, `description`, `emoji`, `color` and system prompt live in its markdown file (YAML frontmatter + body), mirroring the skill format. `src-tauri/src/agents/files.rs` owns parsing, serialization (unknown frontmatter keys are preserved), scanning, path safety and write/delete.

- Discovery runs **only from the panel's Refresh** (`refresh_agent_index`): it scans the `agents/` tree for `.md` files (`.bak.*` and hidden entries skipped) and **replaces** `agents/index.yaml` with the list. Opening the panel reads that manifest instead of scanning, so a file added after the last refresh stays invisible until the next one. A discovered file with no config entry is returned as a disabled **virtual** agent (`configured: false`) and is never written to `sub_agents.json` until the user enables or edits it.
- `agents/index.yaml` is a derived manifest (`version`, `refreshed_at`, `agents[]` with `id`, `file`, `name`, `description`, `emoji`, `color`, optional `error`). The markdown files stay authoritative for the prompt; the manifest decides which files are listed. Delete it (or press Refresh) to rebuild.
- Only `agents/custom/**` may be deleted from the panel. Library files (`engineering/…`, other imported collections) are read-only there: disable the agent instead. A panel save rewrites a file only when its parsed definition actually changed, and keeps a `.bak.<n>` copy before overwriting.
- `enable_mcp` is runtime config for `llm` agents (default off; panel toggle under Capabilities; ignored and never persisted for `cli` / `cloud`). When on, the agent receives the tools of every **enabled** MCP server in `mcp_servers.json`, using the same `mcp::adapt_tool_for_llm` adapter as the main agent — identical `mcp_<server-hash>_<name>` function names and `[MCP: server]` descriptions.
- **Shared sub-agent memory (default on).** Every `llm` sub-agent starts with the `memory` tool (v5 config migration adds it once; the panel offers it and the user can uncheck it per agent). The scopes are shared: `session` is keyed by the main chat's `session_id` (main agent + every sibling task), `user` / `repo` are workspace files under `<workspace>/.data/memory`, and `evolution` exists in self-evolution mode. The sub-agent static prompt tells it to search before starting, add one concise conclusion before finishing, use a task-specific key prefix for mission notes, never store credentials and never run `consolidate`. `cli` / `cloud` agents cannot call app tools, so they do not receive a memory digest.
- **Working directory is per task, never per agent.** `Task.cwd` (workspace-relative; `None` = workspace root) is produced by the planner (`plan_tasks` sees the workspace root and the conversation) or passed by the main agent as the `cwd` argument of `call_subagent`. `run_sub_agent` resolves it once with `resolve_task_cwd`: `tools::resolve_safe_path` enforces the workspace sandbox and a missing directory is created. A `cli` agent starts its process there (`current_dir` + `PWD`), a `cloud` agent receives it through the `{cwd}` body placeholder, and an `llm` agent gets it in its static system prompt while `run_cmd` / `run_shell` / `serve` start there. `file_actions`, memory and todos stay rooted at the workspace (`.data` must not move). `CliAgentSettings` deliberately has no `cwd` field.
- **Main-agent assistance (`ask_main_agent`, `config.sub_agent_main_help`)** — an `llm` sub-agent may request material it cannot obtain itself. The call is handled inside `run_llm_agent_body` by `run_main_agent_helper`: a bounded helper run with the **main model** (`config.model`), the real session history from `history`, the enabled workspace skills, the main `effective_tools()` selection (minus `timer`) and every enabled MCP server on the task's private `AgentMcpSession`. It returns the material as the tool result and the sub-agent continues its own loop. Bounds: 3 requests per task, 8 tool rounds and 180 s per request. The helper never receives `ask_main_agent`, `call_subagent` or mission tools, so it cannot recurse. `agent-help-start` / `agent-help-done` / `agent-help-error` drive the chat task row, and one line per exchange is appended to `agent_missions.help_notes` for the mission panel. `cli` / `cloud` agents cannot use it (external processes cannot call app tools). The Settings → Runtime & Debug switch disables the tool globally (it is then neither advertised nor executable).
- Each **task** owns an `mcp::AgentMcpSession` with its own stdio process pool. Agent processes never enter `AppState.mcp_children` (the main agent's warmup pool), so the main chat and every parallel task are isolated. SSE / HTTP / Streamable HTTP servers have no long-lived process.
- `run_sub_agent_inner` creates the session, runs `run_llm_agent_body`, and calls `AgentMcpSession::shutdown` on every return path (success, error, max iterations, Stop); `Drop` kills anything left on unwind. Every child is also tracked by `process_guard`, so app exit kills it. MCP logs from an agent are prefixed `[agent:<name>]`.
- MCP tools must be advertised before the agent's first request (`tools/list`), so enabling MCP spawns every enabled stdio server at task start. A server whose `tools/list` fails is logged and skipped; it does not block the task.
- Legacy inline `llm` prompts (old `sub_agents.json` or old profiles) are migrated when configured agents are resolved and during Refresh. `load_agents_config` reads the raw config; `load_configured_agents` resolves only the files referenced by configured entries (no directory scan) and is what orchestration/chat use; `load_sub_agent_list` adds the manifest's virtual agents for the panel.

Everything that belongs to the *current workspace* lives in a hidden `.data` directory inside it (see `src-tauri/src/workspace.rs`):

```text
<workspace>/.data/
  chat.db                  SQLite: history / API monitor / interaction log / agent missions
  memory/{user,repo,evolution}/…  memory tool file backend (evolution has front matter + archive/)
  todos/<session>/…        todos tool
  skills/<name>/skill.md   the only skills root
  scripts/<name>.{ps1,sh,py,js,…}  run_cmd script library (created at startup, on the child PATH)
  scripts/.index.json      app-managed use stats + approved script content hashes
  tmp/<batch-id>/          sub-agent deliverable exchange area (shared/ + one dir per task)
  skills.status            per-workspace skill enablement + metadata (JSON)
```

- `.data` is hidden (Windows: file-system hidden attribute) but it is **part of the workspace**: `file_actions` lists, searches, reads and writes it like any other folder (skills, scripts, memory, todos, skill status). The one exception is the SQLite database — see the path policy below.
- **Self-evolution mode** (`config.self_evolution_mode`):
  - **Skill edits are restricted to `<workspace>/.data/skills`** — the one and only skills root, produced by `skills::self_evolution_skill_root` (a single `Option<PathBuf>`, never a list: a second skills location cannot be introduced). `tools/paths.rs` refuses to delete the skills root itself, and only that folder gets the automatic `.bak.<n>` backups.
  - **The main chat and the sub-agents both get that root.** `llm_complete.rs` / `agents.rs` pass it to `tools::execute_tool` as `protected_skill_root`; without it every skill write is rejected.
  - **`file_actions` and `memory` are forced on.** `AppConfig::effective_tools()` adds them whenever the mode is on, and `apply_config` / the startup load persist them — so the Tools panel, a profile, a backup restore or a hand-edited `config.json` cannot switch them off. The Tools panel shows them locked.
  - **A dedicated `evolution` memory scope** (`tools/memory.rs`, `EVOLUTION_SCOPE`) holds verified, reusable facts (default interpreter / runtime environment, the correct way to operate a tool, frequently used file locations). It is file-backed at `<workspace>/.data/memory/evolution`, only exists while the mode is on, is injected into the system prompt as "VERIFIED FACTS", and receives the automatic conclusion recording. Entries carry YAML front matter (`key`, `title`, `kind`, `tags`, `importance`, `confidence`, `evidence`, `uses`, `pinned`, `source`, timestamps) and are ranked by `importance + confidence + ln(evidence) + ln(uses) + recency` — the injector renders three tiers (full distilled facts → title-only → a `+ N lower-ranked facts` pointer) inside the shared `EVOLUTION_CONTEXT_BUDGET_CHARS` budget, so the order is experience-weighted instead of alphabetical. Re-adding a key is an upsert (`evidence += 1`), similar titles merge into the existing entry, and identical bodies are collapsed at read time. Legacy files (`# key` + free text) are upgraded lazily by `persist_evolution_migration`; the prompt builder never writes. Automatic conclusion recording distils (first sentence + up to three bullets, ≤320 chars) instead of dumping the answer, and caps `source: auto` entries.
  - **Memory consolidation** (`memory` action `consolidate`, only in this mode): `phase: plan` clusters the hot entries by tags/title tokens/kind and reports the blocks that occupy ≥20% of the prompt budget (≥4 entries); the model then writes one skill whose front matter `source-memory` lists every archived key and calls `phase: apply` with the full `skill_md`. `apply` is a single transaction in a fixed order — validate name → parse skill → verify coverage → write the skill (`.bak.<n>`) → enable it in `skills.status` → move the entries to `<workspace>/.data/memory/evolution/archive/<skill>/`. The archive is excluded from injection/`list`/`search`, while `memory get` still resolves it and `phase: restore` moves entries back. A consolidated skill is enabled automatically so its one-line description reaches the prompt; its body is loaded on demand via `use_skill`, and `allowed-commands` is deliberately left empty (enabled skills merge their command allowlist globally). The read-only panel (`components/MemoryPanel.tsx`) is opened from Settings → Runtime & Debug, directly below the agent missions monitor (the row only appears while the mode is on); it renders the same ranking and marks which entries fit the current budget.
  - **Script library** (`<workspace>/.data/scripts`, `tools/scripts.rs`): in this mode the prompt instructs the model to save a multi-step command as a script once it has succeeded at least twice, or whenever the user asks to keep/reuse it. Prefer a shell script (`.ps1` on Windows, `.sh` elsewhere), give it an `@description` / `@usage` header, make it argument-driven and self-contained, then run it once by name to verify. Scripts are shared by the whole workspace; never store credentials in them. The library is also listed to the model in normal mode (compact block) so an existing script is reused instead of retyped.
- `chat.db` moves with the workspace: `apply_config` re-opens the SQLite connection when `workspace_dir` changes, so history, monitor logs and missions are per workspace.
- `.data/skills` is **not** created automatically; skill listing and the memory store create what they need on demand. `.data/scripts` and `.data/tmp` **are** created at startup (`ensure_data_layout`), so the script library and the deliverable exchange root exist from the first launch.
- **Sub-agent deliverable exchange area** (`<workspace>/.data/tmp`, `src-tauri/src/agents/exchange.rs`): every planner-dispatched mission and every `call_subagent` call gets one batch directory `<workspace>/.data/tmp/<batch-id>/` with `shared/` plus one directory per task id (sanitized, deduplicated). The sub-agent's static prompt names its own directory and the shared directory; large deliverables go there instead of into the answer, and a dependent task reads `<exchange-root>/<task-id>/<file>`. The mission report and the `call_subagent` tool result list the files and their sizes, so the main agent can read them with `file_actions`. `cli` agents receive the same paths; `cloud` agents cannot access the local workspace and return deliverables inline. The area is **permanent** (no automatic cleanup) and is deliberately **not** part of the profile backup; Settings → Workspace → “Open deliverable exchange folder” (`app_open_workspace_tmp_dir`) opens it for manual cleanup.
- `skills.status` is the source of truth for which skills are enabled. It is per workspace and entries are never pruned automatically — a skill folder that disappears stays recorded (and simply stops reaching the model) until the folder returns. `config.selected_skills` no longer exists.

## Skills — path isolation rule

> Except for explicitly requested paths, any operation executed by a skill MUST treat the directory containing the skill's `SKILL.md` as its root. Operating outside this root is forbidden; all in-skill paths are evaluated relative to it.

This is enforced by the skills/tools layer. Don't add code that lets a skill escape its `SKILL.md` directory.

## Tools & dangerous commands

- Tools: `run_cmd`, `run_shell`, `file_actions`, `knowledge_graph` (Neo4j backend), plus the `memory`, `todos` and `timer` tools — all in `src-tauri/src/tools/` (`skill_read` is auto-injected when skills are active).
- **`run_shell` run types**: `direct` (default) waits for the script to exit and returns its output; `serve` starts a long-lived background child (HTTP server, watcher…) and returns a `serve_id` immediately. The same tool manages them: `action: "list"` shows running/finished entries with recent output, and `action: "stop"` with `serve_id` (or `"all"`) kills the whole tree. Serve state lives in `tools/serve.rs`; stopping a serve process never asks for confirmation because it only targets children this app started. **Serve processes live only for the chat turn that spawned them**: the `chat_completion` wrapper calls `ServeRegistry::shutdown_all` after every turn (final answer, error or Stop), which drains the registry, kills each tree, polls until the pids are confirmed gone — escalating with a second whole-tree kill once — and logs the verified summary (`exit NOT confirmed` on the pathological leftover).
- **Child-process cleanup** (`src-tauri/src/process_guard.rs`): every long-lived child (stdio MCP server — the main pool or an `llm` agent task — `serve` process, `cli` sub-agent) is registered by pid. `RunEvent::Exit` and the main-window `CloseRequested` hook call `kill_all()`, which terminates each process tree. On Windows children are also assigned to a job object with `JOB_OBJECT_LIMIT_KILL_ON_JOB_CLOSE`, so even a hard crash cannot leave MCP servers / CLI agents / serve processes running. On Unix children opt into their own process group (`process_group(0)`) so `kill(-pid)` reaches grandchildren.
- **Path policy** — the three execution tools have deliberately different scopes:
  - **`file_actions`** is strictly workspace-scoped — any path that resolves outside the workspace root is rejected outright, with no confirmation override. The workspace **includes the hidden `.data` state folder** (skills, scripts, memory, todos, skill status): it is listed, searched, read and written like any other folder. The single exception is the SQLite database (`.data/chat.db` and its `-wal`/`-shm`/`-journal` sidecars) — `file_actions` can only truncate or delete it, never rewrite it, so it would destroy the chat history, the API monitor, the interaction log and the agent missions; `tools/paths.rs::is_workspace_database` rejects it.
  - **`run_cmd`** runs a *program* or a *library script*, not an arbitrary file. The first word is resolved against `<workspace>/.data/scripts` by bare name (extension optional, so `build-frontend` finds `build-frontend.ps1`), and the library directory is prepended to the child's `PATH`, so a script wins over a PATH program with the same name. Otherwise it must be a bare name the OS resolves through `PATH` (`python`, `python3`, `git`, …). Absolute and relative paths are refused (`tools/process.rs::validate_path_resolved_program`, enforced both in the tool handler and in `build_command`). Use `run_shell` when a path is really needed. It starts in the caller's working directory (`current_dir` + `PWD`) — the workspace root for the main chat, the task's `cwd` inside a sub-agent mission. `action: "list"` returns the library (interpreter, `@description`, `@usage`, use count, safety status) without executing anything. The script body is scanned by `tools/risk.rs::scan_script_body`; a hit asks for confirmation once and the approved content hash is stored in `.data/scripts/.index.json`, so an edit re-prompts. Script metadata comes only from header comments (`#`, `//`, `REM`, `::`) — no sidecar or manifest.
  - **`run_shell`** has full freedom: it starts in the caller's working directory (workspace root or the task's `cwd`) but its working directory is **not** restricted — scripts may `cd` anywhere and run anything. Every script is audited by `tools/risk.rs` (risk score, syntax gate, confirmation for L0–L4) before it runs.
- **Sub-agents are typed** (`agent_type` in `sub_agents.json`): `llm` runs the built-in autonomous loop, `cli` launches a headless coding CLI installed on this machine (`agents/cli.rs`: PATH + `PATHEXT` resolution, Windows `.cmd`/`.bat`/`.ps1` wrapping, output streaming on `agent-task-token`, process-tree kill on timeout/Stop; `default_timeout_seconds`, 0 = no timeout), `cloud` posts the task to a remote HTTP endpoint with optional job polling (`agents/cloud.rs`; `timeout_seconds`, 0 = no timeout). An `llm` agent's definition is the markdown file under `agents/` (see above); with `enable_mcp` on it also receives every enabled MCP server's tools, each task owning its own MCP processes (see the definitions section). The panel lists all three by name/description, grouped by category: panel-created agents (`custom/` definitions plus the file-less `cli` / `cloud` agents) come first, library folders follow, and top-level markdown files that belong to no category come last. All three are reachable from the main agent through `call_subagent` **only while the `use_agents` (自动编排) switch is on** — with it off the tool is neither advertised nor callable, and the main agent answers directly. `cli`/`cloud` agents ask for approval once per app session unless their `require_approval` switch is off (kind `external_agent`). A `cli` agent's `model_args` are appended on every run — the model id is written there directly (`-m` and `opencode-go/…` on separate lines), nothing is inherited from the main config. Every run starts a fresh CLI session; no session state is carried across calls. Only a CLI process that exits 0 is a success: a non-zero exit or a timeout closes the mission as `failed` and emits `agent-task-error` instead of a green "done" badge.
- Some command patterns raise a frontend confirmation dialog. The Rust side blocks on `confirm_command` until the user replies. **If a tool call appears to hang, check the React tree for a pending `ConfirmDialog` / dangerous-command prompt before debugging the Rust side.**
- `ConfirmKind` values: `dangerous` (L0), `system_config` (L1), `user_software` (L2), `user_data` (L3), `external_agent` — the L0-L3 kinds mirror `RiskLevel::confirm_kind()` in `tools/risk.rs` (L4-L6 never prompt). Users can auto-accept kinds via `auto_accept_confirm_kinds` in config; the Tools panel only offers kinds the backend can actually emit (`external_agent` is approved per agent in the Sub Agents panel instead), plus a one-click master switch that stores the `"*"` wildcard (matches every kind, including future ones).

## Tauri 2 specifics for this repo

- **Identifier**: `com.leonard.aichat` (set in `tauri.conf.json`).
- **Window label**: `main` (the only window).
- **Window chrome is custom**: `decorations: false` + `shadow: true`; `src/components/TitleBar.tsx` draws the drag region (`data-tauri-drag-region`) and the window buttons via `@tauri-apps/api/window`. The required permissions live in `capabilities/default.json` (`allow-start-dragging`, `allow-minimize`, `allow-toggle-maximize`, `allow-close`, …). The titlebar is fixed above overlays; fullscreen pages start at `top: var(--titlebar-h)` (`src/App.css`). The native File/Tools/About menu stays for macOS, and the same 5 actions are exposed as commands (`app_open_data_dir`, `app_open_workspace_dir`, `app_open_markdown`, `app_export_profile`, `app_import_profile`) for the titlebar's `⋯` menu.
- **Plugins registered in `lib.rs`**: `tauri-plugin-opener`, `tauri-plugin-dialog`, `tauri-plugin-clipboard-manager`, plus `tauri-plugin-single-instance` — registered **first**, **release builds only** (`#[cfg(not(debug_assertions))]`, so `tauri dev` can run alongside an installed copy of the same identifier) and only while `config.single_instance` is on. Because the plugin has to be installed before the builder exists (a second process is exited by the plugin itself), the switch is pre-read from `config.json` via `dirs::data_local_dir()/<identifier>`; a change applies on the next launch. The second launch hands its arguments to the first instance, which unminimizes/shows/focuses the `main` window (setters only — on Windows the callback runs on the main thread inside `WM_COPYDATA`, where Tauri dispatches window messages inline). No `fs` / `shell` / `http` plugins. If you need them, add the crate to `Cargo.toml`, register with `.plugin(...)`, AND add the permission to `src-tauri/capabilities/default.json` (Tauri 2 denies by default).
- **App menu**: defined in `lib.rs` — items include `open-app-data-dir`, `open-workspace-dir`, `save-profile`, `restore-profile`, `markdown-edit`, `about`.
- **Vite dev server**: port `1420`, `strictPort: true`. If the port is busy, Tauri dev fails. HMR uses `1421` if `TAURI_DEV_HOST` is set.
- **Vite watcher ignores** `**/src-tauri/**` (so Rust edits don't trigger Vite reloads — recompile via `cargo`).
- **Commands return** `Result<T, String>` (or another `Serialize` error). Frontend `invoke()` rejects on `Err` — always `await`.

## Common gotchas

- **Production build fails on missing git tag.** `npm run build` → `sync-version:git-tag` calls `git tag --sort=-creatordate`; no tag = hard error. Tag first or use `--version x.y.z`.
- **Tauri 2 permissions are runtime, not compile-time.** A new `fs`/`shell`/`http` call will fail at runtime if the permission is missing from `capabilities/default.json`.
- **`async` commands returning `Result<T, E>`** — `E` must be `Serialize`. Use `String` for ad-hoc errors.
- **Vite `strictPort: 1420`** — don't change the port; Tauri expects it.
- **Workspace dir** is mutable at runtime via `get_workspace_dir` / config; skills, profiles, and the in-app browser operate on it. Hot-swap carefully — open handles may be invalidated.
- **Tauri codegen**: `src-tauri/gen/` is auto-generated (gitignored). If IPC types look stale, run `npm run tauri dev` once to regenerate.
- **Draft releases are invisible to the update check.** `GET /releases` never returns drafts, so an in-app “update available” only shows up after the draft created by CI is published.
