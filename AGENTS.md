# Rabbit Chat Studio — Tauri 2.0 (Rust + React)

Desktop AI chat client (Tauri 2 + React 19 + TS + Vite, Rust backend) that talks to any OpenAI-compatible API and adds **Skills**, **Tools**, and **Sub-Agents**.

## UI design — mandatory

**Any change that affects the interface MUST follow [`DESIGN.md`](./DESIGN.md).** It is the single source of truth for colours, typography, spacing, components, motion and both themes. Do not invent visual language and do not copy a style from another project — if a value is not in the spec, add it to the spec first.

Non-negotiables, repeated here so they are impossible to miss:

- **Tokens only.** Colours, radii, shadows, durations, easings and glass blur radii come from `src/App.css` (`:root` + `[data-theme="dark"]` + the palette blocks + the `[data-glass]` blocks). A literal hex — or a literal `blur(20px)` / `saturate(180%)` — outside those blocks is a bug.
- **One accent colour.** Electric Blue (`--c-accent` = `#3E6AE1`) marks the primary action of a view — never decoration, never a second chromatic accent. Semantic `--c-danger` / `--c-success` / `--c-warning` are for status only. An accent used as a *label or line* is `--c-accent-text`; a label on an accent *fill* is `--c-on-accent`.
- **No elevation.** `--shadow-*` are `none`; layering is z-index, opacity and the frosted `--glass-backdrop` surface. Never write `box-shadow: <literal>, var(--shadow-sm)` — the mixed declaration is invalid and is dropped silently.
- **4px radius** on interactive elements. No pills, no large radii. Toggles/badges square off at 4px too.
- **One motion curve:** `--t-dur` (`0.33s`) + `--t-ease`. Colour/border transitions only — no `scale`/`translate` on hover.
- **Hairlines separate.** 1px `--c-border` for structure, 1px `--c-border-i` for interactive outlines. No gradient surfaces.
- **Reuse the shared primitives.** `.close-btn`, `.btn-primary`, `.btn-secondary`, `.inline-edit-btn`, `.field-title-row` are defined once in `src/App.css` — never re-declare them in a component stylesheet (that is exactly how the Skills/MCP/Tools panels drifted apart).
- **Compact zone = 34px controls** (chat input row, sidebar panels, Settings). Settings also uses 13px text. Do not introduce 40px inputs.
- **Sentence case, weights 400/500 only, `letter-spacing: normal`.** No `text-transform: uppercase`, no negative tracking.
- **Check light *and* dark** (`data-theme` is driven by `config.theme` via `applyTheme()` in `src/App.tsx`), plus `prefers-reduced-motion` for any animation. The colour scheme is a second, independent dimension: `data-palette` (`default` / `sakura` / `cream`) comes from `config.palette`, and every palette ships a light *and* a dark token set — check all four combinations of a change. Frosted glass is a third: `data-glass` (`off` / `subtle` / `standard` / `strong`) comes from `config.glass_effect` via `applyGlassEffect()`, and it changes the bar fill as well as the blur, so an `off`-level check is part of any surface change. On Windows the level also drives the *window* backdrop (`set_window_vibrancy` → DWM Acrylic, then `<html data-vibrancy>` + `--c-window`): the frame turns translucent over the desktop while the transcript keeps its opaque `--c-bg`, so a surface change has to be checked with the frame glassy too — and with `data-glass-fallback` set (`applyWindowVibrancy()` writes it whenever that native call reports nothing), which is what Linux and macOS look like: the same translucent frame, over a wash the app paints itself instead of a desktop (DESIGN.md, *Window-less backdrop*).

When a needed value has no token, **add a token** to `src/App.css` — do not hardcode it at the call site.

Verify style work with `npx tsc --noEmit && npx vite build` (not `npm run build`, which requires a git tag).

## Commands

```sh
# Dev (hot-reload). Runs `npm run dev` (Vite on :1420) then launches Tauri.
npm run tauri dev

# Frontend only (Vite on :1420, strictPort — must be free)
npm run dev

# Production build. NOTE: this runs `sync-version:git-tag` first, so the
# repo must have a git tag (e.g. v1.1.1) or the build aborts.
npm run tauri build

# Type-checks
npx tsc --noEmit                                  # frontend
cargo check --manifest-path src-tauri/Cargo.toml  # rust

# Version sync (package.json ↔ Cargo.toml ↔ tauri.conf.json)
node scripts/sync-version.cjs --from-git-tag
node scripts/sync-version.cjs --bump patch
npm run sync-version:git-tag
npm run sync-version:bump-patch

# Rust unit tests (inside the `tools` module: dispatcher, `tools/todos`, `tools/timer`)
cargo test --manifest-path src-tauri/Cargo.toml

# Standalone library crates under `src-tauri/src/utils/` are workspace members,
# so the app crate's `cargo test` skips them — target them by package name.
cargo test --manifest-path src-tauri/Cargo.toml -p knowledge-graph
cargo test --manifest-path src-tauri/Cargo.toml -p pdf2md-rs
```

### Cargo mirror (CN / restricted networks)

`~/.cargo/config` may point at the USTC git registry, which can be unreachable. If `cargo` fails to fetch deps, override the source:

```sh
cargo check --manifest-path src-tauri/Cargo.toml \
  --config 'source.crates-io.replace-with="rsproxy-sparse"' \
  --config 'source.rsproxy-sparse.registry="sparse+https://rsproxy.cn/index/"'
```

## Releases (CI)

`.github/workflows/release.yml` (trigger: `v*` tag push, or manual `workflow_dispatch`) builds via
`tauri-apps/tauri-action@v1` on 4 runners — `macos-latest` ×2 (`aarch64-apple-darwin`, `x86_64-apple-darwin`),
`ubuntu-22.04`, `windows-latest` — and uploads `.dmg` / `.AppImage` + `.deb` + `.rpm` / NSIS `.exe`
(Windows ships the NSIS bundle only, no `.msi`)
to a **published** (non-draft) GitHub Release for the tag (also kept as workflow artifacts).

- **The tag drives the version.** `tauri build` runs `beforeBuildCommand` → `npm run build` → `sync-version:git-tag`, which reads the newest tag; a workflow step fails fast when the pushed tag is not the newest one.
- CI runs `rm -f .cargo/config.toml` so the committed rsproxy.cn mirror is not used on GitHub runners.
- macOS uses `APPLE_SIGNING_IDENTITY='-'` (ad-hoc) — replace with real signing/notarization secrets when available.
- `.github/workflows/winget.yml` is **inactive for now**: the package is not in `microsoft/winget-pkgs` (the earlier PR was closed), so nothing can be submitted and winget / Homebrew / Scoop must not be documented as install options. Keep the file — once a package entry is accepted it needs the `WINGET_TOKEN` secret (classic PAT, `public_repo` + `workflow`) plus a fork under `xlbbb-cn`, and it waits for the NSIS `-setup.exe` upload first.
- `releaseDraft: false` publishes the Release as soon as the first platform finishes; remaining assets upload afterwards, so downstream consumers (e.g. winget) must wait for the NSIS `.exe` to appear.

### Microsoft Store (MSIX)

`scripts/build-msix.ps1` (`npm run msix`) packs the release exe into an unsigned `.msix` with the Windows
SDK (`makeappx`); the identity lives in `src-tauri/msix/store.config.json` (Partner Center product
identity) and the manifest in `Package.appxmanifest.template`, so a name/publisher change is one JSON
edit. Tauri has no MSIX target, hence our own step; the Store re-signs what you upload, so submission
uses the unsigned file. The `windows-x86_64` CI job runs the same script with `-SkipBuild` after
`tauri-action` and keeps the `.msix` as an Actions artifact (never a Release asset — end users cannot
install an unsigned package). Runbook, submission fields and policy mapping: `docs/store/store-publishing.md`.

- **Live listing**: <https://apps.microsoft.com/detail/9MV82J9G95GS> (Store ID `9MV82J9G95GS`,
  protocol link `ms-windows-store://pdp/?productid=9MV82J9G95GS`). Because the store build is an MSIX
  package, its AppData lives under `%LOCALAPPDATA%\Packages\XLBBB.RabbitChatStudio\LocalCache\…` and does
  **not** share config with the NSIS installer build (the workspace `.data` stays shared). New versions
  are submitted by hand (`docs/store/store-publishing.md` §7) or with `msstore publish` from
  `.github/workflows/store.yml` (§12) — that needs four Partner Center secrets, a Manager-role Entra app
  and one earlier manual submission; the workflow skips itself when they are missing.

- MSIX runs the app as a full-trust Desktop Bridge package (`runFullTrust`,
  `EntryPoint="Windows.FullTrustApplication"`): filesystem and process access are unchanged, but writes
  under AppData land in `%LOCALAPPDATA%\Packages\<PFN>\LocalCache\…`, and child processes started by the
  app see the same redirected view — CLI agents therefore do not share the login state of the user's own
  terminal. Do not declare a WebView2 framework package dependency (Store installs with it fail); rely on
  the machine's Evergreen runtime and keep `MinVersion` at Windows 10 2004.
- `update::is_store_packaged()` keeps the GitHub updater out of Store builds: when the exe runs from
  `…\WindowsApps\…`, `check_update` answers "already latest" instead of pointing users at the NSIS
  installer for a second copy.

## Architecture

- **Entry points**: `src/main.tsx` → `src/App.tsx`; Rust `src-tauri/src/main.rs` → `src-tauri/src/lib.rs` (command registration, state, app setup).
- **Streaming chat**: `chat_completion` command opens an SSE connection (`reqwest` + `futures-util`) and emits to the frontend:
  `chat-token`, `chat-reasoning-token`, `chat-done`, `chat-error`, `chat-usage`. Streamed tool calls are normalised before use: an empty or duplicate `id` (some relays omit it) gets a generated `call_…` id, so the assistant `tool_calls` and the following `tool` messages always agree and strict providers (DashScope) accept the next request.
- **Retry** (`retryPendingUserMessage` in `src/App.tsx`): the button is offered only on the last user message of a failed turn. Clicking it truncates that turn *before* the new request — everything after the user row leaves the transcript in one `setMessages` replacement and is deleted from `history` (`db::delete_messages_after`, scoped by session). The turn's pending `saveHistory` write is awaited first, so the partial assistant row the failure persisted cannot land after the DELETE; without the database half a reload would replay the failed rows next to the retried reply. A new message typed after a failure still keeps the interrupted reply as context — only retry removes it.
- **Mid-turn injection** (`inject_user_message` + `AppState::turn_inbox`): the composer stays usable while a turn streams, and Enter then appends the text to the *running* turn instead of starting a new one. A turn is a sequence of requests, so the queue is drained at the top of the main tool loop — the only safe boundary, because an `assistant` message carrying `tool_calls` must stay adjacent to its `tool` results. The text is appended as a `user` message (never `system`: some OpenAI-compatible gateways reject mid-conversation system messages) and announced with `chat-injected`, so the UI can tell "delivered to a request" from "still queued". A reply that already made its last request has no boundary left: the window closes with the turn (`InjectionWindow`, keyed by turn id so a winding-down turn cannot touch a newer one) and the UI re-sends those items as a normal next turn. Deliveries are stored on the assistant row (`history.injections`) and replayed as user messages, since one turn is still one row.
- **Context compression** (`src-tauri/src/llm_complete.rs`): the main chat keeps its prompt inside the model's window in four layers. (1) **LLM structured summary** — when the post-response usage ratio crosses `CONTEXT_COMPRESSION_THRESHOLD` (0.8), the older region is summarized by the main model through a 9-section compact prompt (intent / concepts / files / errors & fixes / problem solving / **all user messages** / pending / current work / next step, adapted from Claude Code's compact prompt); the summary call reuses `stream_llm_request` with every UI event off and passes the turn's cancel flag, and on any failure/cancellation/degenerate answer the mechanical line summarizer runs instead, so compression can never fail the turn. (2) **Tool ledger** — tool rounds are no longer dropped without a trace: the summarizer input and the mechanical fallback both render each round as `name(args) → result preview` (chars-capped). The recent window (`CONTEXT_KEEP_RECENT_MESSAGES` = 12) is always kept verbatim and may only start on a clean round boundary (`is_clean_split_boundary`), so `sanitize_tool_pairs` never has to strip a kept tail. (3) **Summary replacement across turns** — `session_summaries` stores `covered_messages` (how many UI history messages the summary stands in for) plus `boundary_text` (flattened prefix of the last covered message); the next turn verifies the boundary and DROPS the covered prefix of the incoming history (Claude Code's compact semantics: the summary replaces the old transcript instead of being replayed on top of it). A boundary mismatch (edited/restored history) discards the stale summary and replays the full history — the old, always-safe additive behavior. The summary message is a `user` message with "This session is being continued…" framing (never a mid-conversation `system` turn) and sits BEFORE the remaining history, so it is a stable cache prefix. (4) **Predictive + reactive triggers** — a pre-request estimate (≈4 chars/token, tools JSON included; saturated when the static payload itself dominates) compresses before a request that would exceed ~90% of the window, and a provider `context_length_exceeded`-style rejection triggers one hard compression (`CONTEXT_REACTIVE_KEEP_RECENT_MESSAGES` = 6) and a single retry. The sub-agent loop in `agents.rs` has its own LLM episodic summarizer (`summarize_agent_memory`).
- **Evolution maintenance (the empty-state nap face)** (`src-tauri/src/evolution_maintenance.rs`): while `config.self_evolution_mode` is on, the empty-state smiley is a `<button>`; hovering shows a small speech bubble with "点击让我小憩一下" and clicking starts a **silent** maintenance turn. With the mode off the same face is a plain decorative `<div>` — no hint, hover treatment, focus target or click handler. It is deliberately not a chat turn: `start_evolution_maintenance` claims `AppState.evolution_maintenance` (a separate slot from `chat_cancelled`), emits `evolution-maintenance-state` (`running: true` with the live `phase` / `round` / `toolCalls` that replace the empty-state greeting with a status block, then a terminal `done` / `stopped` / `error` with the model's report; a `done` report becomes a clickable result bubble that restores the greeting when dismissed), and never writes history or a `chat-*` event, so the empty state stays visible and a maintenance finish cannot settle a real reply. The loop uses the main model with `memory`, `file_actions` and the maintenance-only `skill_merge`, capped at 20 rounds / 60 tool calls / 15 minutes, with `stream_llm_request` (`emit_tokens: false`, `emit_errors: false`). When the round or tool-call budget is nearly spent the last request gets a `user` budget notice and `tool_choice: "none"`, so the pass ends with a report (and explicitly deferred work) instead of a budget error; the prompt also caps each pass at 3 skill groups / 3 memory clusters, leaving the rest for the next click. A hard allowlist refuses every other tool; `file_actions` may only read freely and write auxiliary files inside `.data/skills` (never `skill.md`, never `.data/memory`/`skills.status`; `delete`/`rename`/`move` are refused). The prompt merges overlapping **self-evolution** skills through `skill_merge`, runs `memory consolidate` `plan`/`apply` per cluster, dedupes evolution entries, and reports what changed; `source: user` and unknown-source skills are off-limits. `skill_merge` (`src-tauri/src/tools/skill_admin.rs`) validates the target/sources, writes and enables the merged skill (`.bak.N` for the old file), then backs up each source folder as `<folder>.bak.N` and deletes it; the dispatcher also requires `mission_id == evolution-maintenance`, so the main agent and sub-agents cannot call it. Cancellation: `stop_evolution_maintenance` (two clicks within 320ms on the napping face; keyboard activation stops immediately), any chat turn start (`chat_completion`), a workspace switch, or turning the mode off. `get_evolution_maintenance_state` restores the napping face after a webview reload. The face parks, closes its eyes and breathes; a 4px bubble shows a **horizontal** random-glyph ticker plus drifting `z`s, all frozen under `prefers-reduced-motion`. A partial pass (user stop, budget exhaustion, upstream error or timeout) writes/updates the `evolution-maintenance-progress` entry in the `evolution` memory scope with the reason, round/tool/token counts and the last tool calls; the next pass's inventory includes it as "Previous maintenance progress" and resumes from it. That entry is excluded from consolidation clusters and cannot be archived or deleted by the `memory` tool; only a completed pass clears it.
- **Agent orchestration** (toggle via `use_agents`): with `auto_configure` on (default), one non-streaming selection call (`select_agents` → `agent-selection`) proposes the roster for this turn; a declined selection (`delegate: false`) skips planning entirely and the main agent answers directly. When selection allows delegation, the planner call itself first answers `delegate` again (`PlanDecision`): an explicit `delegate:false` also skips the mission, returns a declined selection and leaves the answer to the main agent; `delegate:true` plans tasks (a single task is valid). The selection chip is emitted only after the planner confirms, so a declined plan never shows a stale roster. The plan is parsed with one repair retry and sanitized (fence/prose stripping, trailing commas, unknown `agent_id` dropped, duplicate task ids renamed, dangling and cyclic dependencies removed). Execution then runs in dependency waves (parallel, `max_concurrent`) or in list order (sequential). A task that never ran — unknown agent, skipped dependency, or Stop — is reported as `skipped` (`agent-task-skipped`) instead of being dropped silently, so the mission report is never shorter than the plan. The selected roster only narrows what the main session's system prompt advertises; `call_subagent` still accepts any enabled agent id. Events: `agent-selection`, `agent-plan-start`, `agent-task-start`, `agent-task-token`, `agent-task-reasoning`, `agent-task-tool`, `agent-task-done`, `agent-task-error`, `agent-task-skipped`, `agent-aggregate-done`. A task row owns its status: `agent-task-reasoning` (live thinking counter) and `agent-task-tool` (tool activity, phase `start`/`progress`/`done`) only feed the row's activity line, and the generic `tool-call` event is main-chat-only — tool progress inside a mission is routed to `agent-task-tool` through `tools::emit_tool_progress`. Settling a running task row on a main-chat event is what made a working sub-agent show a checkmark and stop updating. `agent-task-done` carries `status` (`success`/`stopped`) so a stopped task renders neutral rather than completed. Sub-agent requests use `emit_errors: false`: `chat-error` closes the user's turn in the UI, so a provider failure must surface as `agent-task-error` only. The aggregation step is instantaneous (the mission report is only rendered for the main agent), so `agent-aggregate-done` reports an already-completed step — never render it as "running".
- **Mission bus (`mbus`, `AgentOrchestration.mbus_enabled`, default on)**: every planner-dispatched batch creates one `MissionBus` (`src-tauri/src/agents/mbus.rs`) for the turn. It is an in-process MQTT-like pub/sub channel: peers are the planner and the plan's tasks; `broadcast` is auto-subscribed by everyone; subscriptions support `+`/`#`; direct messages use a task id, a unique agent id, or `planner`. A sub-agent drains its inbox at the top of a reasoning round (after context compression, before building the request) and appends each message as a `user` message carrying `mbus::MBUS_INJECTION_PREFIX` — the same request-boundary rule as the main agent's mid-turn injection, never mid-stream. The bus also keeps a live status registry (pending/running/completed/error/skipped, rounds, tools, tokens, last tool, queued messages, summaries, objectives, per-pair counts and the mission's active sub-tasks) and bounded message/inbox/rate limits. `cli` / `cloud` peers are status-only while running; they can absorb messages queued before their process starts. A message published by an agent can reach another agent, a topic subscriber, or the planner; the planner is a normal peer with its own inbox.
  - **Per-pair cap (`AgentOrchestration.mbus_pair_limit`, default 4, `0` = off)**: every successful delivery between two sub-agents increments one *unordered* counter (both directions combined); topic/broadcast counts each actual recipient separately, and the planner is exempt. The message that reaches the cap is still delivered and, once per pair, queues a `Mission bus` escalation into the planner's inbox (persisted in `agent_bus_messages` and emitted as `agent-mbus-message`). Later messages between that pair are rejected with an explicit "planner has been notified, do not retry"; a topic publish skips exhausted recipients and lists them under `skipped`. The sender's tool result reports `pair_limits` so it knows which message was the last.
  - The planner can therefore take over: `direct` (`to` + `objective` + optional `done_when`) stores an authoritative objective on the peer (re-rendered in that task's mission snapshot every round, so it survives context compression) and also queues it as a normal bus message; `end_task` (`to` + optional `note`) sets a conclusion the `llm` task notices at its next reasoning boundary — it then reports its current result as a success instead of spending another request. `cli` / `cloud` tasks cannot poll the bus, so `end_task` rejects them.
- **Planner supervisor (`src-tauri/src/agents/supervisor.rs`)**: when `mbus_enabled` is on and the plan contains at least one `llm` task, the planner stays alive concurrently with `execute_tasks` (a `oneshot` cancels its in-flight call when the last task settles). It is event-driven: the initial dispatch, terminal task events, messages addressed to the planner, broadcasts and per-pair limit escalations wake it; a 30 s heartbeat only activates when a running task has been idle for ~90 s. Its only tool is `mbus` (`send`, `status`, `history`, `subscribe`/`unsubscribe`, and planner-only `direct`, `end_task`, `finish`), so it cannot edit files or change the plan. Budget: 10 activations (1 for a single-task plan), 4 tool rounds per activation, 1 024 completion tokens, 60 s per request. Its final note reflects the bus statuses (`N completed / failed / skipped`) instead of assuming every settled task succeeded. Events: `agent-planner-state` (`thinking` / `monitoring` / `done` / `stopped` / `error`), `agent-planner-action` (one tool-group row per planner decision: `schedule`, `send`, `status`, `history`, `subscribe`/`unsubscribe`, `direct`, `end_task`, `finish`; a `running` event creates the row and the matching `done`/`error` event settles it), `agent-mbus-message` (one publish with recipients), `agent-mbus-delivered` (messages injected into a sub-agent round).
- **Sub-agent failure handling / capability fit**: every sub-agent LLM request, tool call and result is logged to `app.log` (model, round, token count, tool name, clipped args/result). Provider balance/quota failures (`Insufficient account funds`, 402, free-usage limits) are classified and surfaced as `Upstream account balance/quota exhausted`, the task fails instead of retrying, and `close_mission` marks the mission's `agent_tasks` `failed`/`stopped` so they disappear from active-task lists; `agent_missions.created_at` is reset on a reused mission id. The selector/planner catalogue includes `mcp=enabled|none` and is instructed never to assign live web/browser/API retrieval to a file-only agent (if no agent has the data channel it declines delegation so the main agent's MCP tools handle it). A sub-agent without the required tool is told to call `ask_main_agent` (when enabled) before spending rounds scanning local snapshots.
- **Composer `+agent` roles** (`src/agentMention.ts`, `src/components/AgentMentionPopup.tsx`): typing `+` at the start of a line in a conversation with **no history** opens the third composer popup (same `.file-mention-*` surface as `@file` / `/skill`); it lists only enabled `llm` sub-agents whose `system_prompt` is non-empty (`list_agent_mentions` — a lightweight roster that never ships the prompts). The line grammar allows only `+token` words, so `2 + 2` and `C++` never trigger it. Selecting inserts `+token` and the token stays in the body. On the first send the frontend passes the selected ids (`embeddedAgentIds`); the backend freezes a `{id,name,description,prompt}` snapshot into `session_meta.embedded_roles` (`db::set_embedded_roles`) and refuses to do so once the incoming history contains an `assistant` row. `run_chat_turn` reads that snapshot every turn and appends `render_embedded_roles(...)` to the END of the main system prompt, so the role survives reload, history reopen and fork (`fork_session` copies the row) without a live agent lookup. Only the prompt is embedded: model, temperature, tools, skills, MCP and approval rules stay the main agent's, and safety/tool rules take precedence. Editing or deleting the agent afterwards never changes a started session. Tokens come from the display name when token-safe, else the md file stem, else a short id fragment, deduped with `-2`; the transcript highlights known `+tokens` the same way it highlights `/skill` names.
- **Mission bus persistence**: `agent_missions.bus_id` links a mission to its orchestration batch, and `agent_bus_messages` stores one row per publish (`bus_id`, sender, target kind/id, topic, body, recipient count, timestamp). `list_mission_bus_messages(mission_id, limit)` backs the “Message bus (mbus)” section of `components/AgentMissionPanel.tsx`; the task rows show live sent/received counts and the last note. Messages are in-memory for delivery and in SQLite for replay, so a bus is discarded with its turn while the Mission panel keeps the history.
- **Turn cancellation** (`stop_chat_completion` + `AppState::chat_cancelled`): every `chat_completion` installs a fresh `Arc<AtomicBool>` as its own cancel flag (a `Mutex<Arc<…>>` slot); the previous turn's flag is set to `true` permanently, so a superseded turn can never be resurrected and Stop pressed while idle cannot leak into the next turn. The turn's flag is threaded through `orchestrate` → `execute_*` → `run_sub_agent` → `cli::run`/`cloud::run` and into the main agent's tool loop: `cli` agents poll it every 250 ms and kill their process tree, `llm` agents break their loop, remaining tasks report as skipped, missions close as "stopped" (not "completed"), and a stop during planning/execution aborts the turn before the final answer streams. Plan-phase LLM calls (`plan_tasks`, `select_agents`) are checked between steps, not cancelled mid-request.
- **Backup**: `src-tauri/src/backup.rs` owns export / import of the application state (app menu `save-backup` / `restore-backup`, commands `app_export_backup` / `app_import_backup`). The zip holds `config.json`, `mcp_servers.json` (panel-owned servers only), `sub_agents.json`, `agents/`, `workspace/{memory,todos,skills,scripts,mcp}/`, `workspace/skills.status`, `workspace/mcp.conf` and a `chat.db` snapshot; every `workspace/...` entry is read from and restored into the hidden `<workspace>/.data` directory of the (possibly switched) active workspace, while `agents/...` entries are merged into the app-global `agents/` definition store. There are no named in-app profiles: the zip is the only way to move a tools/agents/MCP setup between machines, and skill selection stays per-workspace state (`<workspace>/.data/skills.status`), so it rides along inside the workspace snapshot instead of a preset.
- **MCP warmup**: enabled stdio servers in `mcp_servers.json` are spawned at app startup (`mcp::start_stdio_process`). MCP stdio children start with the **active workspace** as their working directory (`current_dir` + `PWD` in `build_stdio_cmd`). `cli` sub-agents start in the **task's** working directory — `Task.cwd` is supplied per delegation by the planner or `call_subagent` (never by the agent definition), sandbox-checked by `resolve_task_cwd` and created when missing; `cli::run` applies it via `current_dir` + `PWD`. A `workspace_dir` switch stops running stdio children so the next tool call respawns them in the new workspace. Sub-agent tasks do **not** use this pool: with `enable_mcp`, each task gets its own `AgentMcpSession` (see the sub-agent definitions section).
- **Self-built MCP servers** (`mcp_self`, self-evolution mode only): the assistant writes a stdio server script under `<workspace>/.data/mcp/<slug>/` and the backend registers it in the **workspace roster** `<workspace>/.data/mcp.conf` (YAML, `version` + `servers[]`, `source: "self-evolution"`, `definition_path` = workspace-relative script, `command` = an interpreter the backend picked from the whitelist `python` / `node` / `shell` — never a model-supplied command, `args` = the relative script path, which resolves because every stdio child starts in the workspace root, so the entry still works after a backup restore). Manually created servers stay in the app-data `mcp_servers.json`; `mcp::load_effective_servers` merges both rosters and is what the chat, the panel, the warmup and the sub-agents read (the app-data entry wins on an id clash). The split keeps the assistant out of the user's config and makes a self-built server follow its workspace — including the backup's workspace snapshot. The tool is the writer because turning code into a running server is more than a file write (whitelisted interpreter, `.bak.<n>` copy, roster upsert, start + `tools/list`, one confirmation, revision bump); `file_actions` may still hand-edit `mcp.conf`, and `restart` picks that up. Actions: `list` / `write` (create or update with a `.bak.<n>` copy, register disabled, then optionally start and run `tools/list`) / `enable` / `disable` / `test` / `restart` / `logs` / `remove`. `write`, `enable` and `remove` ask the user once (`user_software`); a start that fails `tools/list` leaves the entry **disabled** (an enabled server that cannot list would stall every later request); the tool only ever rewrites `mcp.conf`, and the MCP panel edits or deletes a self-built row through the same file (`save_mcp_server` / `delete_mcp_server` route by provenance instead of forking a copy into app data). Every mutation bumps `AppState::mcp_revision`, and `run_chat_turn` compares it at the top of each tool round and rebuilds the whole payload (`build_turn_tools`), so a server created mid-turn is callable in the *same* turn. Sub-agents and the main-agent helper drop the tool (`agents::drop_mcp_self`): they would race on the registry, their `AgentMcpSession` only loads servers at task start, and the confirmation dialog would block a mission.
- **Delay timers** (`src-tauri/src/tools/timer.rs`): the `timer` tool (`timer_set` / `timer_list` / `timer_cancel`, toggled in the Tools panel) lets the assistant wait for slow work instead of polling — the LLM arms a delay and ends its turn; when it fires the backend emits `timer-fired` and the frontend injects the timer's `message` into the same session as a new user turn (`timer-state` keeps the timer bar above the input box in sync). Timers are mirrored to `<workspace>/.data/timers.json` and re-armed at startup, where overdue ones fire immediately. The mirror is workspace-scoped because a timer resumes a session id that only exists in *that* workspace's database: a workspace switch flushes the current set back to the old file and arms the new one (`timer::rebase_workspace`), and a legacy `<app_data>/timers.json` is migrated once at startup. Sub-agents never receive the timer tools (`agents.rs` filters them out). The same file hosts the cross-platform **sleep lock** (`SleepLock`, ref-counted RAII): it is held while any timer is pending **and** for the whole duration of a chat turn (`chat_completion` wrapper in `llm_complete.rs`, released after turn-end serve cleanup), preventing idle system suspend via `SetThreadExecutionState` (Windows), an IOPM assertion (macOS) or a D-Bus inhibit (Linux); `sleep-lock` events + `get_sleep_lock_state` drive the badge above the input box.
- **Background tool tasks** (`src-tauri/src/tools/background.rs`): `run_cmd`, `run_shell` (`run_type: "direct"`), `file_actions` action `search`, MCP tools and `call_subagent` accept `run_in_background: true` (the flag is only advertised while `config.background_tools` is on — Settings → Runtime & Debug → “Background execution”; sub-agents never get it). The call returns a placeholder `tool` result carrying a `bg-…` id immediately, so the model keeps working; the real output is injected at the next request boundary as a `user` message (`[BACKGROUND TASK RESULT …]`) and announced via `chat-injected` with `kind: "background_result"`, so it lands on the assistant row's `injections` and is replayed like a mid-turn injection (tool results themselves are never persisted). The turn is **held open** if the model tries to finish while a task is unsettled (max 3 rounds × 120 s, then the remainder is cancelled). `background_task` (`list`/`wait`/`get`/`cancel`) is the model-side control tool; `list_background_tasks` / `cancel_background_task` back the UI. Tasks are turn-scoped: Stop calls `cancel_session` (running → `cancelled`, entries kept until the turn unwinds) and `end_turn_cleanup` calls `shutdown_session` (set every cancel flag, drop the entries); each runner then kills its process tree, and `process_guard` covers app exit. Both methods **return** the terminal snapshots, because a torn-down runner's `finish()` finds no entry left to report into — teardown is the only thing that can tell the UI a row is gone: every caller emits one `background-task-state` per snapshot plus `background-waiting` with `pending: 0` before the turn returns, and the frontend drops any row still marked `running` once `streaming` ends (a task cannot outlive its turn), so the panel and the transcript row's cancel button can never outlive the task. Background `run_cmd`/`run_shell` run through `process::run_command_timed` (cancellable, tree-killing, 600 s default), a background `file_actions` search polls `SearchOptions.abort` inside the parallel walker, and a background **stdio MCP call gets its own short-lived process** (`mcp::invoke_mcp_tool_isolated`) because the shared pool serialises on `mcp_children` and caps a round trip at 10 s — using it would stall the next request's `tools/list`. Confirmation dialogs are serialised by `AppState.tool_confirm_lock`, and a cancelled task stops waiting for one.
- **Model metadata** (`src-tauri/src/model_metadata.rs`): `fetch_model_metadata` pulls the public basellm/llm-metadata catalogue (6 h in-memory cache) and expands its `tags` into capability flags. `src/utils/modelMetadata.ts` fuzzy-matches remote model ids against it (vendor prefixes, date stamps, modality guards); "Fetch Models From API" stores the matches per model in `config.model_metadata` and uses the catalogue context window when the provider reports none. The chat toolbar renders those flags as icons inside the model picker's options, plus a thinking-depth selector for reasoning-capable models (`config.model_reasoning_effort` → `reasoning_effort`, resolved by `llm_complete::resolve_reasoning_effort` and applied to chat + sub-agent requests). The attachment picker follows the same flags: text is always accepted (inlined into the prompt), images need `Vision` (`image_url` parts), PDFs need `Files` (`file` parts), `wav`/`mp3` need `Audio` (`input_audio` parts); an unmatched model keeps the permissive default. The composer's `@paper.pdf#2` mention does **not** follow that rule — it converts the pages to Markdown text (next bullet), so every model can read it.
- **`@` file mentions** (`src-tauri/src/workspace_files.rs`, `src-tauri/src/pdf_mentions.rs`, `src/fileMention.ts`): the grammar is `@<workspace path>[#<start>[-<end>]]`, plus `@@<name>` for a file in the workspace tmp folder (`.data/tmp`, short because that folder is scratch), and the token stays in the message body, so the model sees which file was quoted. A text file is sliced by *line* (`read_workspace_file_range`), an image/audio file is attached whole, and a **PDF** counts *pages*: `convert_pdf_mention` renders `#2` / `#2-5` / `#2-` with the in-process `pdf2md-rs` library (a workspace member — a library, not a CLI: `src-tauri/src/utils/pdf2md-rs/README.md`), caches the Markdown at `<workspace>/.data/tmp/pdf/<stem>-<digest>.md` (digest over path + range + file size + `pdf2md-rs` version, so the same mention reuses one file while a converter upgrade invalidates it) and returns it; `fileMention.ts` then pushes it as a `kind: "text"` attachment whose `text_content` `buildMessageContent` inlines as a `<details>` text part (the fence tag comes from `fenceLanguage`, so `kk.pdf#2` is fenced as `markdown`, not `pdf#2`). Consequences: no `supports_files` is involved (the popup filters with `supportsMentionName`, not `supportsAttachmentKind`), the Markdown's provenance comment names the cache file so a tool can read the full conversion later, a range-less mention converts at most 60 pages and the prompt keeps at most 60k characters while the cache file always keeps the full text, and failures (encrypted, scanned, page past the end) become per-mention problems that never block the message. Conversion runs in `spawn_blocking`; page range enforcement lives in `pdf2md-rs`'s `Options::page_range`. Progress is a `tauri::ipc::Channel<PdfMentionProgress>` fed from the library's own ticks (deduped on stage + page + total, `percent` monotonic), which the composer renders as a muted strip above the input row (see `DESIGN.md`) and clears in a `finally`; the persisted copy of the message goes through `compactAttachmentsForDb`, which drops `text_content` from any attachment that has a `path` — the Markdown is already in the message `content`, so a stored PDF mention keeps one string plus the cache path, while live attachments keep their text and sending never depends on a cache file that may since have been pruned.
- **Update check** (`src-tauri/src/update.rs`): `check_update` reads the releases of `xlbbb-cn/ai-chat` from the GitHub API, keeps the highest semver (drafts are always skipped, pre-releases behind `include_prerelease_updates`), ranks the attached bundles for the current OS/arch and flags the preferred one as `recommended`. `download_update` streams into the downloads folder while emitting `update-download-progress`; `open_update_file` / `reveal_update_file` / `open_release_page` hand off to the OS (URLs are restricted to this repository). UI: startup probe + banner in `App.tsx`, dialog in `components/UpdatePanel.tsx`, toggles under Settings → About & Updates.
- **API layer**: `src/api.ts` wraps `invoke` + `listen`. `src/types.ts` is the canonical TS shape for `AppConfig`, `Skill`, `SkillsStatus`, `McpServer`, `SubAgent`, `AgentOrchestration`, `AgentMissionSnapshot`, `ModelMetadata`.
- **PDF export writes a file** (`src/utils/pdfExport.ts`, `src/utils/printDocument.ts`, `src-tauri/src/html_pdf.rs`): a reply's export button and the Markdown editor's "Export PDF" share one route — `exportHtmlAsPdf` opens the save dialog, then `app_export_pdf` prints the document with a headless Chromium. What is exported is rendered HTML (a clone of the reply with its figure cards frozen, or the editor's preview), so `buildPrintDocumentHtml({ standalone: true })` makes it self-contained for another process: the KaTeX CSS with its woff2 faces fetched from the bundled assets as data URLs, and system faces instead of the RazerF5 web font, because the file is opened from a temp directory where the app's asset URLs mean nothing. Only the no-engine fallback — `NO_PDF_ENGINE` — goes through `printHtmlDocument`, the hidden-iframe dialog printer; the shared shell (light palette, A4 page box, prose rules) plus each caller's `extraCss` keeps both routes looking the same. Titlebar `⋯` → "Markdown edit…" opens a `.md` in a two-column overlay (`app_open_markdown` → `markdown-edit-open`). Success is confirmed by revealing the file: `ChatNotice` is reserved for warnings and errors.
- **Theming**: three independent dimensions in `AppConfig` — `theme` (`auto` / `light` / `dark`), `palette` (`default` / `sakura` / `cream`) and `glass_effect` (`off` / `subtle` / `standard` / `strong`, the frosted-glass level; missing means `standard`). `applyTheme()` writes the first two to `<html>` as `data-theme` / `data-palette` and `applyGlassEffect()` writes the third as `data-glass`; the token blocks in `src/App.css` do the rest (`--glass-blur`, `--glass-blur-scrim`, `--glass-saturate`, `--glass-backdrop`; `off` swaps the fill to `--c-surface` because a 0px blur over a translucent bar reads as a hole). Settings → Appearance previews all three immediately and persists them on "Save Changes". All three fields live in the Rust `AppConfig` too, so they survive a config write.
- **Workspace state** (`src-tauri/src/workspace.rs`): single source of truth for the per-workspace layout. Everything workspace-scoped (SQLite database, memory, todos, skills, skill status, pending timers) lives in the hidden `<workspace>/.data` directory, so switching `workspace_dir` in config swaps the whole state — `apply_config` closes and re-opens the SQLite connection at `<workspace>/.data/chat.db` and re-points the timer mirror when the workspace changes.
- **Persistence**: SQLite (`<workspace>/.data/chat.db`) for history, API request monitor, interaction logs, and agent missions. `app.log` stays in the app data dir.
- **Multiple windows** (`src-tauri/src/instance.rs`): `single_instance` decides whether a second launch focuses the running window (plugin) or starts a second process. The first process takes the **primary** role via `<app_data>/shadow/primary.lock` (pid liveness; a crashed run's lock is reclaimed) and keeps using the shared `config.json` unchanged. Every later process is a **shadow**: it copies the current config into `<app_data>/shadow/config-<timestamp>-<id>/config.json` — same settings, but `workspace_dir` is rewritten to that directory's own `workspace/` — writes only that copy and deletes it on exit. Clearing `workspace_dir` in a shadow falls back to its own fork (never the shared default workspace), so clearing the workspace cannot put two windows on one database. `collect_garbage` sweeps copies left behind by killed windows at startup, `Instance::write_config` serialises writers of the shared file with `shadow/main-config.lock`, and a shadow merges just its `workspace_history` back into the shared config on exit (its own temporary workspace is filtered out). `get_instance_info` tells the UI which window it is (the titlebar switcher shows a shadow window's note). The pre-Tauri path helper (`app_data_dir_before_tauri`) must stay `dirs::data_dir()/<identifier>` — Tauri's `app_data_dir()` uses the Roaming directory on Windows, not `%LOCALAPPDATA%`; `setup` re-claims if the two ever disagree.

## On-disk layout (runtime)

Application files live in the OS app data dir (`name` from `tauri.conf.json` identifier `com.leonard.aichat`):

- macOS: `~/Library/Application Support/com.leonard.aichat/`
- Linux: `~/.local/share/com.leonard.aichat/`
- Windows: `%APPDATA%/com.leonard.aichat/` (Roaming — Tauri's `app_data_dir()` is `dirs::data_dir()/<identifier>`, *not* `%LOCALAPPDATA%`)

App-data contents: `config.json`, `mcp_servers.json`, `sub_agents.json`, `app.log`, a `workspace/` dir (default — overridable via `workspace_dir` in config), an `agents/` dir holding the `llm` sub-agent definitions plus the `index.yaml` discovery manifest, and a `shadow/` dir (the primary lock plus one temporary `config-<timestamp>-<id>/` per extra window, deleted when that window closes).

```text
<app_data>/agents/
  <category>/<slug>.md   # imported/library definitions (read-only from the panel)
  custom/<slug>.md       # agents created from the Sub Agents panel
  index.yaml             # discovery manifest, replaced on Refresh
```

### Sub-agent definitions (`llm`)

`sub_agents.json` is **configuration only**. For an `llm` agent it stores the runtime knobs (`enabled`, `model`, token limits, `allowed_tools`, `allowed_skills`, `max_iterations`) plus a `file` reference; `cli` / `cloud` agents keep their full definition there. An `llm` agent's `name`, `description`, `emoji`, `color` and system prompt live in its markdown file (YAML frontmatter + body), mirroring the skill format. `src-tauri/src/agents/files.rs` owns parsing, serialization (unknown frontmatter keys are preserved), scanning, path safety and write/delete.

- Discovery runs **only from the panel's Refresh** (`refresh_agent_index`): it scans the `agents/` tree for `.md` files (`.bak.*` and hidden entries skipped) and **replaces** `agents/index.yaml` with the list. Opening the panel reads that manifest instead of scanning, so a file added after the last refresh stays invisible until the next one. A discovered file with no config entry is returned as a disabled **virtual** agent (`configured: false`) and is never written to `sub_agents.json` until the user enables or edits it.
- `agents/index.yaml` is a derived manifest (`version`, `refreshed_at`, `agents[]` with `id`, `file`, `name`, `description`, `emoji`, `color`, optional `error`). The markdown files stay authoritative for the prompt; the manifest decides which files are listed. Delete it (or press Refresh) to rebuild.
- Only `agents/custom/**` may be deleted from the panel. Library files (`engineering/…`, other imported collections) are read-only there: disable the agent instead. A panel save rewrites a file only when its parsed definition actually changed, and keeps a `.bak.<n>` copy before overwriting.
- `enable_mcp` is runtime config for `llm` agents (default off; panel toggle under Capabilities; ignored and never persisted for `cli` / `cloud`). When on, the agent receives the tools of every **enabled** MCP server in `mcp_servers.json`, using the same `mcp::adapt_tool_for_llm` adapter as the main agent — identical `mcp_<server-hash>_<name>` function names and `[MCP: server]` descriptions.
- **Shared sub-agent memory (default on).** Every `llm` sub-agent starts with the `memory` tool (v5 config migration adds it once; the panel offers it and the user can uncheck it per agent). The scopes are shared: `session` is keyed by the main chat's `session_id` (main agent + every sibling task), `user` / `repo` are workspace files under `<workspace>/.data/memory`, and `evolution` exists in self-evolution mode. The sub-agent static prompt tells it to search before starting, add one concise conclusion before finishing, use a task-specific key prefix for mission notes, never store credentials and never run `consolidate`. `cli` / `cloud` agents cannot call app tools, so they do not receive a memory digest.
- **Working directory is per task, never per agent.** `Task.cwd` (workspace-relative; `None` = workspace root) is produced by the planner (`plan_tasks` sees the workspace root and the conversation) or passed by the main agent as the `cwd` argument of `call_subagent`. `run_sub_agent` resolves it once with `resolve_task_cwd`: `tools::resolve_safe_path` enforces the workspace sandbox and a missing directory is created. A `cli` agent starts its process there (`current_dir` + `PWD`), a `cloud` agent receives it through the `{cwd}` body placeholder, and an `llm` agent gets it in its static system prompt while `run_cmd` / `run_shell` / `serve` start there. `file_actions`, memory and todos stay rooted at the workspace (`.data` must not move). `CliAgentSettings` deliberately has no `cwd` field.
- **Main-agent assistance (`ask_main_agent`, `config.sub_agent_main_help`)** — an `llm` sub-agent may request material it cannot obtain itself. The call is handled inside `run_llm_agent_body` by `run_main_agent_helper`: a bounded helper run with the **main model** (`config.model`), the real session history from `history`, the enabled workspace skills, the main `effective_tools()` selection (minus `timer`) and every enabled MCP server on the task's private `AgentMcpSession`. It returns the material as the tool result and the sub-agent continues its own loop. Bounds: 3 requests per task, 8 tool rounds and 180 s per request. The helper never receives `ask_main_agent`, `call_subagent` or mission tools, so it cannot recurse. `agent-help-start` / `agent-help-done` / `agent-help-error` drive the chat task row, and one line per exchange is appended to `agent_missions.help_notes` for the mission panel. `cli` / `cloud` agents cannot use it (external processes cannot call app tools). The Settings → Runtime & Debug switch disables the tool globally (it is then neither advertised nor executable).
- Each **task** owns an `mcp::AgentMcpSession` with its own stdio process pool. Agent processes never enter `AppState.mcp_children` (the main agent's warmup pool), so the main chat and every parallel task are isolated. SSE / HTTP / Streamable HTTP servers have no long-lived process.
- `run_sub_agent_inner` creates the session, runs `run_llm_agent_body`, and calls `AgentMcpSession::shutdown` on every return path (success, error, max iterations, Stop); `Drop` kills anything left on unwind. Every child is also tracked by `process_guard`, so app exit kills it. MCP logs from an agent are prefixed `[agent:<name>]`.
- MCP tools must be advertised before the agent's first request (`tools/list`), so enabling MCP spawns every enabled stdio server at task start. A server whose `tools/list` fails is logged and skipped; it does not block the task.
- Legacy inline `llm` prompts (old `sub_agents.json` bodies) are migrated when configured agents are resolved and during Refresh. `load_agents_config` reads the raw config; `load_configured_agents` resolves only the files referenced by configured entries (no directory scan) and is what orchestration/chat use; `load_sub_agent_list` adds the manifest's virtual agents for the panel.

Everything that belongs to the *current workspace* lives in a hidden `.data` directory inside it (see `src-tauri/src/workspace.rs`):

```text
<workspace>/.data/
  chat.db                  SQLite: history / API monitor / interaction log / agent missions
  memory/{user,repo,evolution}/…  memory tool file backend (evolution has front matter + archive/)
  todos/<session>/…        todos tool
  skills/<name>/skill.md   the only skills root
  scripts/<name>.{ps1,sh,py,js,…}  run_cmd script library (created at startup, on the child PATH)
  scripts/.index.json      app-managed use stats + approved script content hashes
  tmp/<batch-id>/          sub-agent deliverable exchange area (shared/ + one dir per task)
  mcp/<slug>/server.{py,js,sh,ps1}  self-built MCP servers (evolution mode, `mcp_self`)
  mcp.conf                 roster of those servers (YAML), merged with the app-data
                           mcp_servers.json into the effective server list
  skills.status            per-workspace skill enablement + metadata (JSON)
```

- `.data` is hidden (Windows: file-system hidden attribute) but it is **part of the workspace**: `file_actions` lists, searches, reads and writes it like any other folder (skills, scripts, memory, todos, skill status). The one exception is the SQLite database — see the path policy below.
- **Self-evolution mode** (`config.self_evolution_mode`):
  - **Skill edits are restricted to `<workspace>/.data/skills`** — the one and only skills root, produced by `skills::self_evolution_skill_root` (a single `Option<PathBuf>`, never a list: a second skills location cannot be introduced). `tools/paths.rs` refuses to delete the skills root itself, and only that folder gets the automatic `.bak.<n>` backups.
  - **The main chat and the sub-agents both get that root.** `llm_complete.rs` / `agents.rs` pass it to `tools::execute_tool` as `protected_skill_root`; without it every skill write is rejected.
  - **`file_actions` and `memory` are forced on.** `AppConfig::effective_tools()` adds them whenever the mode is on, and `apply_config` / the startup load persist them — so the Tools panel, a backup restore or a hand-edited `config.json` cannot switch them off. The Tools panel shows them locked.
  - **A dedicated `evolution` memory scope** (`tools/memory.rs`, `EVOLUTION_SCOPE`) holds verified, reusable facts (default interpreter / runtime environment, the correct way to operate a tool, frequently used file locations). It is file-backed at `<workspace>/.data/memory/evolution`, only exists while the mode is on, and receives the automatic conclusion recording. **Nothing is preloaded into the prompt**: a `VERIFIED FACTS` block used to dominate the first request's prefill, so the prompt now only *points* at the scope ("search it when a problem needs earlier experience") and the model queries it on demand (`memory list` / `get` / `search`). Entries carry YAML front matter (`key`, `title`, `kind`, `tags`, `importance`, `confidence`, `evidence`, `uses`, `pinned`, `source`, timestamps) and are ranked by `importance + confidence + ln(evidence) + ln(uses) + recency`, so a search returns them experience-weighted instead of alphabetically. `render_ranked_entries` still renders the three tiers (full distilled fact → title-only → a `+ N lower-ranked` pointer) inside `EVOLUTION_CONTEXT_BUDGET_CHARS`; that budget now only drives the panel's top-tier marking and the consolidation planner, not a request. Re-adding a key is an upsert (`evidence += 1`), similar titles merge into the existing entry, and identical bodies are collapsed at read time. Legacy files (`# key` + free text) are upgraded lazily by `persist_evolution_migration`; the prompt builder never writes. Automatic conclusion recording distils (first sentence + up to three bullets, ≤320 chars) instead of dumping the answer, and caps `source: auto` entries.
  - **Memory consolidation** (`memory` action `consolidate`, only in this mode): `phase: plan` clusters the hot entries by tags/title tokens/kind and reports the blocks that occupy ≥20% of the prompt budget (≥4 entries); the model then writes one skill whose front matter `source-memory` lists every archived key and calls `phase: apply` with the full `skill_md`. `apply` is a single transaction in a fixed order — validate name → parse skill → verify coverage → write the skill (`.bak.<n>`) → enable it in `skills.status` → move the entries to `<workspace>/.data/memory/evolution/archive/<skill>/`. The archive is excluded from injection/`list`/`search`, while `memory get` still resolves it and `phase: restore` moves entries back. A consolidated skill is enabled automatically so its one-line description reaches the prompt; its body is loaded on demand via `use_skill`, and `allowed-commands` is deliberately left empty (enabled skills merge their command allowlist globally). The read-only panel (`components/MemoryPanel.tsx`) is opened from Settings → Runtime & Debug, directly below the agent missions monitor (the row only appears while the mode is on); it renders the same ranking and marks which entries fit the current budget.
  - **Self-built MCP servers** (`mcp_self`): the third capability the mode owns, next to skills and the evolution memory. The assistant writes a stdio server script under `<workspace>/.data/mcp/<slug>/` and the backend registers + starts it (roster entry lands in the workspace file `<workspace>/.data/mcp.conf`, merged into the effective list — the app-data `mcp_servers.json` is left to the panel). See the tools section for the actions, the confirmation kind and the mid-turn `mcp_revision` rebuild. The capability exists only while the mode is on: the tool is injected into the main agent's payload from `config.self_evolution_mode`, never stored in `selected_tools`, and sub-agents never see it.
  - **Script library** (`<workspace>/.data/scripts`, `tools/scripts.rs`): in this mode the prompt instructs the model to save a multi-step command as a script once it has succeeded at least twice, or whenever the user asks to keep/reuse it. Prefer a shell script (`.ps1` on Windows, `.sh` elsewhere), give it an `@description` / `@usage` header, make it argument-driven and self-contained, then run it once by name to verify. Scripts are shared by the whole workspace; never store credentials in them. The library is also listed to the model in normal mode (compact block) so an existing script is reused instead of retyped.
- `chat.db` moves with the workspace: `apply_config` re-opens the SQLite connection when `workspace_dir` changes, so history, monitor logs and missions are per workspace.
- **Workspace history** (`config.workspace_history`): `apply_config` records the *resolved* workspace path before `config.json` is written (newest first, deduped case-insensitively, capped at `WORKSPACE_HISTORY_LIMIT` = 10), so a Settings save, a titlebar switch and a backup restore all feed the same list. The list belongs to `config.json`, so it travels with a backup, and it never switches a workspace by itself. The **titlebar workspace indicator** is the only picker: clicking the label opens the recently used workspaces and applies the chosen workspace immediately (closing the sidebar first — every panel reads workspace-scoped state, so none of them repaints against the workspace being replaced). Every Settings save path (`handleSave`, `handleLanguageChange`, `applyMessageEditor`) takes `workspace_dir` from a fresh `getConfig()` instead of writing the copy it loaded, for the same reason `selected_tools` comes from there. The switch itself goes through `set_workspace_dir`, never through `save_config` — the command writes that one field onto the live `AppConfig`, because a UI copy that predates another panel's edit must not be round-tripped back — and it is refused while `active_turn` is set (a streaming reply owns the paths and the database handle of the workspace it started in; the UI disables the rows for the same reason). `workspace_history_entries` is the popup's single read: deduped history plus the *resolved* current path (`current`) and a `Path::is_dir()` check per entry (`exists`), so the UI never reconstructs the list from `AppConfig` — that only knows `workspace_dir: None` for the default workspace. A switch from a shadow window is window-local like every other setting of that window; only the history merges back on exit.
  Startup also seeds it with the workspace it opens (`remember_workspace` returns whether the list changed, so an already-newest entry costs no write), which means one switch is enough to make the previous workspace selectable.
- `.data/skills` is **not** created automatically; skill listing and the memory store create what they need on demand. `.data/scripts` and `.data/tmp` **are** created at startup (`ensure_data_layout`), so the script library and the deliverable exchange root exist from the first launch.
- **Sub-agent deliverable exchange area** (`<workspace>/.data/tmp`, `src-tauri/src/agents/exchange.rs`): every planner-dispatched mission and every `call_subagent` call gets one batch directory `<workspace>/.data/tmp/<batch-id>/` with `shared/` plus one directory per task id (sanitized, deduplicated). The sub-agent's static prompt names its own directory and the shared directory; large deliverables go there instead of into the answer, and a dependent task reads `<exchange-root>/<task-id>/<file>`. The mission report and the `call_subagent` tool result list the files and their sizes, so the main agent can read them with `file_actions`. `cli` agents receive the same paths; `cloud` agents cannot access the local workspace and return deliverables inline. The area is **permanent** (no automatic cleanup) and is deliberately **not** part of the backup; the titlebar app menu (⋯) → “Open deliverables folder” (`app_open_workspace_tmp_dir`) opens it for manual cleanup, and the mission monitor repeats the same action next to its refresh button. It is a folder action, not a preference, so it lives outside Settings.
- `skills.status` is the source of truth for which skills are enabled. It is per workspace and entries are never pruned automatically — a skill folder that disappears stays recorded (and simply stops reaching the model) until the folder returns. `config.selected_skills` no longer exists.

## Skills — path isolation rule

> Except for explicitly requested paths, any operation executed by a skill MUST treat the directory containing the skill's `SKILL.md` as its root. Operating outside this root is forbidden; all in-skill paths are evaluated relative to it.

This is enforced by the skills/tools layer. Don't add code that lets a skill escape its `SKILL.md` directory.

## Tools & dangerous commands

- Tools: `run_cmd`, `run_shell`, `file_actions`, plus the `memory`, `todos` and `timer` tools — all in `src-tauri/src/tools/` (`skill_read` is auto-injected when skills are active). The former `knowledge_graph` tool is retired for now: its client is the standalone `knowledge-graph` crate at `src-tauri/src/utils/knowledge_graph/` (a workspace member with its own `Cargo.toml`; module-owned `Settings`, no `AppConfig` fields). The app crate does **not** depend on it, so `neo4rs` is not linked into the binary. It is neither advertised nor dispatchable until it is wired back: add `knowledge-graph = { path = "src/utils/knowledge_graph" }` to `src-tauri/Cargo.toml` plus a tool definition and a dispatch arm in `tools/mod.rs`.
- `mcp_self` belongs to the same family but is the only tool that writes **app-data** state (the MCP registry) instead of workspace state. It is advertised only while `config.self_evolution_mode` is on (injected by `tools::get_all_tools`, never part of `selected_tools`), and its dispatch arm in `tools/mod.rs` re-checks the flag, so a hand-crafted call is refused even when the tool was not advertised. Sub-agents and the main-agent helper strip it (`agents::drop_mcp_self`).
- **`run_shell` run types**: `direct` (default) waits for the script to exit and returns its output; `serve` starts a long-lived background child (HTTP server, watcher…) and returns a `serve_id` immediately. The same tool manages them: `action: "list"` shows running/finished entries with recent output, and `action: "stop"` with `serve_id` (or `"all"`) kills the whole tree. Serve state lives in `tools/serve.rs`; stopping a serve process never asks for confirmation because it only targets children this app started. **Serve processes live only for the chat turn that spawned them**: the `chat_completion` wrapper calls `ServeRegistry::shutdown_all` after every turn (final answer, error or Stop), which drains the registry, kills each tree, polls until the pids are confirmed gone — escalating with a second whole-tree kill once — and logs the verified summary (`exit NOT confirmed` on the pathological leftover).
- **Child-process cleanup** (`src-tauri/src/process_guard.rs`): every long-lived child (stdio MCP server — the main pool or an `llm` agent task — `serve` process, `cli` sub-agent) is registered by pid. `RunEvent::Exit` and the main-window `CloseRequested` hook call `kill_all()`, which terminates each process tree. On Windows children are also assigned to a job object with `JOB_OBJECT_LIMIT_KILL_ON_JOB_CLOSE`, so even a hard crash cannot leave MCP servers / CLI agents / serve processes running. On Unix children opt into their own process group (`process_group(0)`) so `kill(-pid)` reaches grandchildren.
- **Path policy** — the three execution tools have deliberately different scopes:
  - **`file_actions`** is strictly workspace-scoped — any path that resolves outside the workspace root is rejected outright, with no confirmation override. The workspace **includes the hidden `.data` state folder** (skills, scripts, memory, todos, skill status): it is listed, searched, read and written like any other folder. The single exception is the SQLite database (`.data/chat.db` and its `-wal`/`-shm`/`-journal` sidecars) — `file_actions` can only truncate or delete it, never rewrite it, so it would destroy the chat history, the API monitor, the interaction log and the agent missions; `tools/paths.rs::is_workspace_database` rejects it.
  - **`run_cmd`** runs a *program* or a *library script*, not an arbitrary file. The first word is resolved against `<workspace>/.data/scripts` by bare name (extension optional, so `build-frontend` finds `build-frontend.ps1`), and the library directory is prepended to the child's `PATH`, so a script wins over a PATH program with the same name. Otherwise it must be a bare name the OS resolves through `PATH` (`python`, `python3`, `git`, …). Absolute and relative paths are refused (`tools/process.rs::validate_path_resolved_program`, enforced both in the tool handler and in `build_command`). Use `run_shell` when a path is really needed. It starts in the caller's working directory (`current_dir` + `PWD`) — the workspace root for the main chat, the task's `cwd` inside a sub-agent mission. `action: "list"` returns the library (interpreter, `@description`, `@usage`, use count, safety status) without executing anything. The script body is scanned by `tools/risk.rs::scan_script_body`; a hit asks for confirmation once and the approved content hash is stored in `.data/scripts/.index.json`, so an edit re-prompts. Script metadata comes only from header comments (`#`, `//`, `REM`, `::`) — no sidecar or manifest.
  - **`run_shell`** has full freedom: it starts in the caller's working directory (workspace root or the task's `cwd`) but its working directory is **not** restricted — scripts may `cd` anywhere and run anything. Every script is audited by `tools/risk.rs` (risk score, syntax gate, confirmation for L0–L4) before it runs.
- **Sub-agents are typed** (`agent_type` in `sub_agents.json`): `llm` runs the built-in autonomous loop, `cli` launches a headless coding CLI installed on this machine (`agents/cli.rs`: PATH + `PATHEXT` resolution, Windows `.cmd`/`.bat`/`.ps1` wrapping, output streaming on `agent-task-token`, process-tree kill on timeout/Stop; `default_timeout_seconds`, 0 = no timeout), `cloud` posts the task to a remote HTTP endpoint with optional job polling (`agents/cloud.rs`; `timeout_seconds`, 0 = no timeout). An `llm` agent's definition is the markdown file under `agents/` (see above); with `enable_mcp` on it also receives every enabled MCP server's tools, each task owning its own MCP processes (see the definitions section). The panel lists all three by name/description, grouped by category: panel-created agents (`custom/` definitions plus the file-less `cli` / `cloud` agents) come first, library folders follow, and top-level markdown files that belong to no category come last. All three are reachable from the main agent through `call_subagent` **only while the `use_agents` (自动编排) switch is on** — with it off the tool is neither advertised nor callable, and the main agent answers directly. `cli`/`cloud` agents ask for approval once per app session unless their `require_approval` switch is off (kind `external_agent`). A `cli` agent's `model_args` are appended on every run — the model id is written there directly (`-m` and `opencode-go/…` on separate lines), nothing is inherited from the main config. Every run starts a fresh CLI session; no session state is carried across calls. Only a CLI process that exits 0 is a success: a non-zero exit or a timeout closes the mission as `failed` and emits `agent-task-error` instead of a green "done" badge.
- Some command patterns raise a frontend confirmation dialog. The Rust side blocks on `confirm_command` until the user replies. **If a tool call appears to hang, check the React tree for a pending `ConfirmDialog` / dangerous-command prompt before debugging the Rust side.**
- `ConfirmKind` values: `dangerous` (L0), `system_config` (L1), `user_software` (L2), `user_data` (L3), `external_agent` — the L0-L3 kinds mirror `RiskLevel::confirm_kind()` in `tools/risk.rs` (L4-L6 never prompt). Users can auto-accept kinds via `auto_accept_confirm_kinds` in config; the Tools panel only offers kinds the backend can actually emit (`external_agent` is approved per agent in the Sub Agents panel instead), plus a one-click master switch that stores the `"*"` wildcard (matches every kind, including future ones).

### Turn guards — rounds, tool calls, repeated tool failures

- `src-tauri/src/turn_guard.rs` holds both guards; `chat_completion` → `run_chat_turn` is the only loop that spends a `TurnBudget`.
- **Round / tool-call budget** (`config.main_agent_max_rounds`, `config.main_agent_max_tool_calls`, Settings → Advanced; `0` = unlimited, hard caps 1000 / 5000 clamped by `AppConfig::normalize_turn_limits`): `begin_round()` counts every request, `record_tool_call()` every tool that actually runs. When either limit is spent the loop does **not** stop mid-flight: it sets `wrap_up`, emits `chat-notice {kind: "budget_exhausted"}`, appends `CONTEXT_BUDGET_MARKER` as a **`user`** message at the tail, and sends **one more request with the identical `tools` array but `tool_choice: "none"`**, so the model must answer with what it already collected (`BUDGET_FALLBACK_ANSWER` when that answer is empty). The remaining calls of the round are answered with `turn_guard::budget_notice`, so every `tool_call_id` still receives a `tool` message.
- **Prompt-cache invariant (why the wrap-up keeps `tools`)**: `tools` is rendered *before* the messages, so any change to that array — dropping it, adding a tool, filtering one out — moves every following token and invalidates the whole KV / prefix cache for that request. Keep the array byte-identical within one run and change it only at request-boundary-free moments (i.e. between turns). `tool_choice: "none"` still forbids calls, and the budget short-circuit answers a call that a gateway lets through anyway.
- **Tool failure guard** (`config.tool_failure_limit`; `0` = off, hard cap 50): consecutive failures per `(session_id, tool_name)`, kept in `AppState::tool_guard`. A success resets the counter; the failure that reaches the limit disables the tool for the rest of the session, appends `turn_guard::disabled_notice(…, just_now = true)` to that same result and emits `chat-notice {kind: "tool_disabled"}` (shown by `App.tsx` as a warning notice). **Removal from the payload is deferred**: all three loops snapshot `disabled_tools()` once at the start of the turn / helper run / agent run and filter `tools` from that snapshot, so a tool disabled *mid-run* stays advertised (cache-stable) and is only short-circuited with the same notice; it disappears from the payload on the next turn or run. The main agent, the sub-agent loop and `run_main_agent_helper` share one guard, so "disabled for this session" holds across all of them; `apply_config` calls `reset_all()` when the limit changes, because raising it is how a user releases tools without restarting.
- Failure detection is `turn_guard::tool_output_is_error` (`⛔`, `Error`, `MCP tool error`). Use it instead of a hand-written prefix check, so the interaction log's `tool_error` rows, the UI's `ok` flag and the guard all agree.

- **Rejected wrap-up**: a gateway that refuses `tool_choice: "none"` must not turn the end of a turn into an error bubble — the failed request is logged as `WARN` and `final_answer` falls back to `BUDGET_FALLBACK_ANSWER` instead of propagating the error.

- **Vite watcher ignores** `**/src-tauri/**` (so Rust edits don't trigger Vite reloads — recompile via `cargo`).
- **Commands return** `Result<T, String>` (or another `Serialize` error). Frontend `invoke()` rejects on `Err` — always `await`.

## Composer attachments (paste / drop)

- **A pasted or dropped file is a workspace file plus a mention.** `save_pasted_file` (clipboard bytes from `Ctrl+V`) and `import_workspace_paths` (real OS paths from Tauri's native drag-drop — `dragDropEnabled` swallows HTML5 drops, so `onDragDropEvent` is the only source) copy into `<workspace>/.data/tmp/<name>.<ext>` — the file's own name, `-2`/`-3` on a collision — and return that relative path; `src/composerFiles.ts` splices the short `@@<name>` form into the draft at the caret, and the normal mention pipeline attaches it at send time. There is no second attachment channel, so `buildMessageContent` stays the only place an attachment becomes a content part. A dropped file that already lives in the workspace is the one exception: `mentionable_workspace_path` returns it *where it is* instead of copying, so a project file is never duplicated and never lands on the paste clock — only a drop from outside (or a path the mention grammar cannot carry: space, `#`, `@`) is copied.
- **`.data/tmp` is the one state folder the composer may read and write.** `resolve_in_workspace` (`workspace_files.rs`) rejects `.data` with a *component-wise* exception for a leading `.data/tmp`, so a paste written there can be read back by its own `@` mention while the database, skills, scripts and memory stay unreachable — and a lookalike sibling (`.data/tmpx/…`) is still refused. It is also the folder the Settings panel's "open temp dir" button shows and where `convert_pdf_mention` caches its Markdown, so the area is already part of the app's contract rather than a new convention. The scratch root has three writers with three lifetimes: `<stamp>-<8hex>/` is a sub-agent deliverable batch (permanent, cleaned by hand through "open the exchange folder"), `pdf/` is the PDF mention cache (entries older than a week are dropped when the next conversion runs) and `<name>` (the file's own name, `@@<name>` in a message) is a composer paste, swept after 24 h. That sweep only ever deletes *files* sitting directly in the folder and older than a day, so a batch directory or the `pdf/` cache — both directories — can never be removed by it.
- **Anything new in `.data/tmp` must own its expiry.** Anything that must outlive a day goes into a *subdirectory* — `pdf/` is the model to copy — because every plain file sitting directly in `.data/tmp` is treated as scratch and swept on the next paste.
- **Names are rebuilt, not escaped.** The mention grammar (`@@?[^\s@#<>]+`) ends a token at whitespace, `#`, `@`, `<` and `>`; `sanitize_tmp_name` (`workspace_files.rs`) keeps letters/digits/`-`/`_`/`.` (CJK included) and collapses everything else, so `my screenshot #2.png` cannot split its own token.
- **A reply and a user body are rendered by different markdown profiles.** `ChatMessage.tsx` builds `md` (reply: figures, KaTeX, `image` restricted to `https?:` / `data:image/<raster>;base64,`) and `mdLiteral` (the user's own text, `image` rule disabled). Raw HTML is off in both. Enabling image syntax for the user body — or raw HTML anywhere — turns typed text into live elements (`![a](b)` → `<img>`), which is the HTML-leak hole this split closes.
- **Rendering failures cost one row.** `renderMarkdown` catches a throwing renderer and degrades to escaped literal text; `ChatMessageBoundary` wraps every message, so a component-level throw shows a readable row instead of blanking the transcript.
- **The sent message never carries a paste path.** the draft already carries the short `@@<name>` form (`mentionTokenForPath`), and `canonicalTmpMentions` (`src/composerFiles.ts`) collapses a hand-typed `@.data/tmp/<name>` to it — keeping a `#12-24` range, because the inlined copy holds only those lines — before `buildMessageContent` sees the text, and the inline summary reads `Attached File: @@name.ext — already provided below`. Both exist for one reason: a path the model can open is an invitation to `file_actions read` a file whose bytes are already in the request, which is one wasted tool round per attachment. Mentions outside the tmp folder keep their path (`src/App.tsx` is meaningful, and the model may need the rest of it), so the rewrite is keyed on the tmp folder rather than on "was it attached".
- **An attachment is named, never listed.** The transcript has no "Attached Files:" chip row: a file is represented by its accent `@name` token in the body (`highlightFileMentions` paints it in the colour a path mention wears), which is why the rewritten token keeps its `@`. A chip row repeats that name — and, before the rewrite existed, dragged the machine path back into the conversation, which is what the row was showing. The one exception is an image: it is the content rather than a reference to it, so it stays visible as a thumbnail (`ChatMessage.tsx`'s `imageAttachments`, no caption, since the body already names it).

## Common gotchas

- **Production build fails on missing git tag.** `npm run build` → `sync-version:git-tag` calls `git tag --sort=-creatordate`; no tag = hard error. Tag first or use `--version x.y.z`.
- **Tauri 2 permissions are runtime, not compile-time.** A new `fs`/`shell`/`http` call will fail at runtime if the permission is missing from `capabilities/default.json`.
- **`async` commands returning `Result<T, E>`** — `E` must be `Serialize`. Use `String` for ad-hoc errors.
- **Vite `strictPort: 1420`** — don't change the port; Tauri expects it.
- **Workspace dir** is mutable at runtime via `get_workspace_dir` / config; skills and the in-app browser operate on it. Hot-swap carefully — open handles may be invalidated.
- **Tauri codegen**: `src-tauri/gen/` is auto-generated (gitignored). If IPC types look stale, run `npm run tauri dev` once to regenerate.
- **Two windows should not share a workspace.** Every database is `<workspace>/.data/chat.db`; `db::open_db` waits up to 5 s for another connection's write lock (`busy_timeout`) and startup still `.expect`s the open, so two live windows on one directory survive the lock but show interleaved sessions, each with its own in-memory state. That is why a shadow window forks its own `workspace/`; only the user can still point two windows at the same directory on purpose.
- **A shadow window's settings are temporary.** They live in `shadow/config-<id>/config.json` and are deleted on exit; only `workspace_history` is merged back (and its own fork path is filtered out). Do not "fix" that by letting a shadow write the shared config — moving another window's workspace is exactly what the roles prevent.
- **`timers.json` is workspace-scoped, not app-data.** A timer resumes a session id that only exists in its workspace's database, so the mirror lives in `<workspace>/.data` and moves with `apply_config`; a legacy `<app_data>/timers.json` is migrated once at startup (`timers.json.migrated` when the target already exists).
- **Draft releases are invisible to the update check.** `GET /releases` never returns drafts, so an in-app “update available” only shows up after the draft created by CI is published.
- **A figure never reaches the DOM through markdown.** `html: false` is the injection boundary, so `svg` / `carve` / `html-fig` blocks are cut out of the reply *before* `md.render` (`utils/figures.ts`) and replaced by an invisible U+2063 slot token; `mountFigures` swaps the token for a sanitised card in the `useLayoutEffect` right after `innerHTML`. Removing the sanitizer or enabling raw HTML undoes the only defence a reply has.
- **Figure cards are cached by source hash, not rebuilt.** The transcript subtree is replaced on every streamed token; a card that were rebuilt would drop three.js pixels and the orbit angle the user just dragged. The cache *moves* the same element back into the new tree — extend `mountFigures` rather than mounting in React.
- **A dynamic figure runs in a frame, never in the transcript.** `utils/htmlFigure.ts` assembles an `html-fig` fragment into a complete document and hands it to `<iframe sandbox="allow-scripts">` — `allow-same-origin` must never be added, because the pair together is same-origin access to the app. The wrapper carries `default-src 'none'` (inline style/script open, `img-src data: blob:`), which refuses every request the fragment makes — fourteen channels measured on WebKitGTK, zero hits. Navigation is *not* covered by CSP (`navigate-to` never shipped), so `figureCard.ts` counts the frame's loads and closes a figure on the second one; `parent.document` and `localStorage` throw in the frame, and the two channels across the boundary are `postMessage` height reports and token updates, both checked against `event.source` on the parent side.
- **Execution is tiered by script, and consent is per session.** A sandboxed frame shares the web process with the transcript in both engines (measured: a 2 s `while` left a ~2 s hole in the parent's 50 ms timer on WebKitGTK *and* Chromium), so `htmlFigure.hasInlineScript` decides: no script — CSS/SVG animation — runs on the settle commit without a click; script waits for a click on the poster, or for the `sessionStorage` consent its `Play automatically this session` button records. Do not auto-run script without that record, do not move consent to `localStorage`, and do not add a watchdog that "stops" a runaway fragment — it would run on the frozen thread. Mid-stream even a safe frame waits: a re-inserted frame reloads, so it mounts on the settle commit, and a cached card's load counter resets in `beforeMount` because that move-reload is not a navigation.
- **A frame is mounted on the settle commit, not while streaming.** Chromium reloads a frame whenever the element is re-inserted, and every commit replaces the transcript subtree: a frame mounted mid-stream restarts on each token. `mountFigures` takes `streaming` and `buildHtmlCard` shows `Plays when the reply finishes` until it is false; `ChatMessage` forces one extra rebuild when the flag flips, because the slots a card needs only exist in a freshly written tree. Do not "optimise" that rebuild away.
- **A dynamic figure is saved as `.html`, not PNG.** The pixels live in a cross-origin frame that cannot be captured, and an animation has no single frame; `figures::save_figure_html` validates (`<!doctype`, 2 MiB cap, whitelisted slug) and writes the standalone document to `<workspace>/figures/<slug>.html` with the tokens baked in. The PDF export keeps the live frame and pins its measured height onto the clone.
- **The PDF engine is a launcher that exits at once.** `msedge.exe --headless=new --print-to-pdf` returns in ~50 ms with status 0 while the real browser writes the file a second later, so waiting for the child yields an empty export. `html_pdf::run` polls the target instead, and only accepts it once it ends with `%%EOF` (45 s cap) — that is also why the temp document and profile are deleted after the poll, never before. The `--user-data-dir` must be a fresh directory per run: pointed at the default profile, a running browser accepts the command line, prints nothing and exits 0.
- **Three.js is a lazy chunk with exactly one renderer.** `utils/carve3d.ts` dynamic-imports `three` and owns the single off-screen `WebGLRenderer` that blits into each figure's 2D canvas; a renderer per card hits WebView2's context limit after a few scenes. A conversation without `<carve>` never loads the chunk (it builds as its own ~750 kB asset).
- **Rust never encodes a figure PNG.** The pixels only exist in the webview, and there is no `image`/`resvg` dependency: the frontend rasterises and sends base64, `figures::save_figure` validates (PNG magic, 12 MiB cap, whitelisted slug) and writes `<workspace>/figures/<slug>.png` — never `<workspace>/.data`.
- **The drawing toggle changes the prompt, not the renderer.** `enhanced_figures` (Settings → Advanced, on by default) picks between `figures::prompt_block()` (`svg` / `carve` / `html-fig`) and `figures::mermaid_prompt_block()`; the transcript renders all four kinds either way, so flipping it never orphans an earlier reply.
- **A Mermaid diagram is a figure card with a second renderer.** `utils/mermaidDiagrams.ts` cuts `mermaid` fences out with the same U+2063 slot token and renders them asynchronously with `securityLevel: "strict"` + `htmlLabels: false`, pruning the SVG again (`script` / `foreignObject` / `on*` / external `url()`); Mermaid's id-scoped `<style>` survives, which is why the SVG is not run through `svgSanitize.ts`. Colours are baked into the SVG, so a theme or palette change re-renders instead of repainting, and a graph wider than ~2.5× the card keeps its natural width and scrolls.
- **Both extractors read fences through `utils/fenceLines.ts`; never re-declare a fence regex locally.** Two shapes break a flat `^ {0,3}` scan and turn a diagram into a code block: a reply with CRLF line endings (`\r` is not part of a closing fence, so every block looked unclosed) and a fence indented by the list item that holds it (markdown-it reads a fence there, a flat scan read an indented code block). `splitLines` normalises, `fenceIsOpen` honours a list container up to 8 spaces, the body is dedented before the renderer sees it, and the slot token keeps the fence's column capped at three spaces so it never lands inside `<pre><code>`. A fence that really is code — a `mermaid` example inside a ```` ```markdown ```` block, or a 4-space indented block outside any list — still stays code.
- **A card that cannot be drawn states it; it does not dump its source.** `figureCard.showUnrenderable` (shared with the Mermaid card) shows one line, a copy button and the markup behind a fold, and every failure path logs `console.warn("[figures] <kind> not drawn (<reason>)")` first — a diagram silently turning into a code block is the bug this replaces. The fold keeps the text because it is the only way to see what went wrong.
